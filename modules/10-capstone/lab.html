Lab · Module 10

Capstone Project — สร้าง Agent จริงตั้งแต่ต้นจนจบ

Lab นี้ไม่มีคำตอบสำเร็จรูป — คุณจะเลือกโจทย์เอง, สร้าง repo จริง, ใช้ Claude Code สร้าง core feature จริง, ใส่ hook ป้องกันความเสี่ยงจริง, test จริง และ ship เป็น artifact ที่ demo ได้จริงในเวลาจำกัด ทุก phase ต้องมีหลักฐาน (evidence) ที่จับต้องได้

⏱ ระยะเวลา: 1 sprint (แนะนำ 5–7 วัน ทำงานจริง) / ในคลาส: 3–4 ชม. 🎯 ระดับ: รวมทุก module 01–09 🖥 เครื่องมือ: Claude Code CLI, git, terminal, editor

Prerequisites

  • เรียนจบ module 01–09 ของคอร์สนี้ (หรืออย่างน้อยอ่าน slides ของทุก module ผ่านมาแล้ว)
  • ติดตั้ง Claude Code CLI และ login สำเร็จแล้ว (module 03)
  • มี git และ terminal ใช้งานได้ในเครื่อง
  • เข้าใจพื้นฐาน hooks/permissions (module 06) และ governance checklist (module 08)

Learning Objectives

  • เลือกและ scope โจทย์ capstone ให้ทำเสร็จได้จริงในเวลาที่มี
  • ตั้งค่าโปรเจกต์ agent จริงพร้อม CLAUDE.md และ permissions ที่เหมาะสม
  • ใช้ Claude Code สร้าง core agentic loop ของ use case ที่เลือก
  • เพิ่ม hook ป้องกันความเสี่ยงและพิสูจน์ว่ามันทำงานจริง
  • ผลิต evidence (test output, README, demo) ที่ครบตาม rubric ของคอร์ส

1Phase 1: เลือกโจทย์ + เขียน spec สั้น

เลือกโจทย์หนึ่งข้อจาก 4 ตัวอย่างใน slides (presale proposal generator, automated PR reviewer, internal doc/runbook agent, monitoring/alert agent) หรือเสนอโจทย์ของทีมตัวเองที่ scope ใกล้เคียงกัน — สำคัญคือต้อง เล็กพอทำเสร็จได้จริงใน 1 sprint เขียน spec เป็นไฟล์ markdown ก่อนแตะโค้ดแม้แต่บรรทัดเดียว 

mkdir capstone-agent && cd capstone-agent
touch spec.md

เนื้อหาขั้นต่ำใน spec.md:

# Capstone Spec: PR Review Agent

## Problem
ทีม backend มี PR เฉลี่ย 15 ใบ/สัปดาห์ reviewer คนเดียวดู coding
standard + security pattern ไม่ทัน อยากได้ automated first-pass reviewer

## Users
Backend engineer ที่เปิด PR, tech lead ที่ approve

## Core agentic loop
1. Observe: อ่าน diff ของ PR ผ่าน `gh pr diff`
2. Plan: เทียบกับ coding standard ใน CLAUDE.md
3. Act: comment กลับใน PR ผ่าน `gh pr comment`
4. Verify: เช็คว่า comment โพสต์สำเร็จ, log ผลไว้

## Out of scope
ไม่ auto-merge, ไม่แก้โค้ดเอง, ไม่ review infra/Terraform
Verify: มีไฟล์ spec.md ที่มีหัวข้อครบ 4 หัวข้อ (Problem / Users / Core agentic loop / Out of scope) และ core loop เขียนเป็น observe → plan → act → verify ชัดเจน อ่านแล้วคนอื่นเข้าใจโจทย์ได้ภายใน 1 นาที
Troubleshoot: เลือกโจทย์แล้วรู้สึกว่ากว้างเกินไป ทำไม่ทันแน่ ๆ

ตัดขอบเขตลงเหลือ "1 use case, 1 data source, 1 output channel" เช่นแทนที่จะทำ "PR reviewer ที่เช็คทุกอย่าง" ให้ทำ "PR reviewer ที่เช็คแค่ secret leak กับ missing test" ก่อน — เขียนใน spec.md ว่าอะไรคือ v2 ที่ตั้งใจไม่ทำรอบนี้ scope เล็กแต่ทำงานจริงดีกว่า scope ใหญ่แต่ demo ไม่ได้

2Phase 2: Setup Project + CLAUDE.md + Permissions

Init git repo จริง เขียน CLAUDE.md ที่อธิบายบริบทโปรเจกต์ให้ Claude Code เข้าใจ แล้วตั้งค่า .claude/settings.json จำกัด tool ที่ agent ใช้ได้ ตามหลัก least-privilege (module 06) 

git init
git add spec.md
git commit -m "docs: capstone spec"

mkdir -p .claude
touch CLAUDE.md

CLAUDE.md ตัวอย่าง:

# CLAUDE.md — PR Review Agent

## What this project does
Automated first-pass PR reviewer: อ่าน diff, เช็ค secret leak
กับ missing test, comment กลับใน PR ผ่าน gh CLI

## Coding standard to enforce
- ห้าม commit secret/API key (เช็คด้วย regex pattern ใน checklist.md)
- ทุก PR ที่แก้ src/ ต้องมี test แนบมาด้วย
- ใช้ conventional commits

## Constraints
- ห้าม auto-merge หรือแก้โค้ดในนามผู้ใช้อื่น
- ทำงานกับ repo นี้เท่านั้น ห้ามแตะ repo อื่น

.claude/settings.json:

{
  "permissions": {
    "allow": [
      "Read",
      "Bash(gh pr diff:*)",
      "Bash(gh pr comment:*)",
      "Bash(git log:*)",
      "Bash(git diff:*)"
    ],
    "deny": [
      "Bash(rm -rf *)",
      "Bash(git push --force*)",
      "Bash(curl *)"
    ]
  }
}
Verify: รัน git log --oneline ต้องเห็น commit อย่างน้อย 1 อัน, ไฟล์ CLAUDE.md มีอยู่จริงและไม่ว่างเปล่า, ไฟล์ .claude/settings.json เป็น JSON ที่ valid (เช็คด้วย python3 -m json.tool .claude/settings.json) และมีทั้ง allow กับ deny list

3Phase 3: Build Core Agentic Loop ด้วย Claude Code จริง

ใช้ Claude Code print mode (claude -p) สั่งสร้าง core feature ตาม spec จริง ไม่ใช่เขียนมือทั้งหมด — นี่คือจุดที่เอา module 03/04 มาใช้ตรง ๆ 

claude -p "read spec.md and CLAUDE.md, then implement
the core agentic loop: a Python script review_pr.py that
takes a PR number, runs 'gh pr diff', checks for hardcoded
secrets and missing tests, then posts a summary comment
via 'gh pr comment'. Follow the allowed tools in
.claude/settings.json. Write a basic test file too." \
  --allowedTools "Read,Write,Edit,Bash(gh pr diff:*)"

ตรวจว่าไฟล์ที่ generate มาทำงานได้จริง:

python3 review_pr.py --help
git add -A
git commit -m "feat: core PR review loop (observe/plan/act/verify)"
Verify: มีไฟล์ source code จริง (เช่น review_pr.py) ที่ถูก generate โดย Claude Code, รันแล้วไม่ error ทันที (อย่างน้อย --help หรือ dry-run ผ่าน), และมี commit history ใน git ที่แสดงว่า core loop ถูกสร้างขึ้นเป็นขั้นเป็นตอน (ไม่ใช่ commit เดียวยัดทุกอย่าง)
Troubleshoot: Claude Code สร้างโค้ดที่พยายามเรียก tool นอก allowedTools

นี่คือพฤติกรรมที่ถูกต้อง — permission system (module 06) จะ block และถาม confirm หรือ deny ตาม settings.json ถ้า agent ต้องการ tool เพิ่ม ให้พิจารณาว่า จำเป็นจริงไหม ถ้าจำเป็นให้เพิ่มเข้า allow list อย่างเจาะจง (เช่น Bash(gh pr comment:*) ไม่ใช่ Bash(*)) แล้วรันใหม่ อย่าเปิด permission กว้างเกินเพื่อความสะดวก

4Phase 4: เพิ่ม Hook ป้องกันความเสี่ยง

อ้างอิง pattern จาก module 06 (hooks) และ module 08 (governance) — เพิ่ม PreToolUse hook ที่ block คำสั่งอันตรายก่อนที่ agent จะรันจริง เช่น ป้องกันการ commit secret หรือรันคำสั่ง destructive 

mkdir -p .claude/hooks
touch .claude/hooks/block-secrets.sh
chmod +x .claude/hooks/block-secrets.sh

.claude/hooks/block-secrets.sh:

#!/usr/bin/env bash
# PreToolUse hook: block Bash commands that look like they
# would commit a secret or run a destructive git operation
INPUT=$(cat)
CMD=$(echo "$INPUT" | python3 -c "import json,sys; print(json.load(sys.stdin).get('tool_input',{}).get('command',''))")

if echo "$CMD" | grep -qE "(AKIA[0-9A-Z]{16}|api[_-]?key\s*=|push --force)"; then
  echo '{"decision":"block","reason":"blocked: potential secret leak or force-push detected"}'
  exit 0
fi

echo '{"decision":"approve"}'

ผูก hook ใน .claude/settings.json:

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": ".claude/hooks/block-secrets.sh" }
        ]
      }
    ]
  }
}

พิสูจน์ว่า hook block จริง ด้วยการจงใจสั่งคำสั่งเสี่ยง:

claude -p "run this exact bash command: git push --force origin main"
# ต้องเห็น hook แจ้ง block ไม่ใช่รันจริง
Verify: ไฟล์ .claude/hooks/block-secrets.sh มีสิทธิ์ executable (ls -l ต้องมี x) และเมื่อสั่ง Claude Code รันคำสั่งเสี่ยง (เช่น git push --force) ต้อง capture log/screenshot ที่แสดงว่า hook สั่ง block คำสั่งนั้นจริง ไม่ใช่แค่บอกว่า "hook มีอยู่"
ข้อควรระวัง: hook แบบ regex block ได้แค่ pattern ที่คาดเดาได้ ไม่ใช่ security boundary ที่สมบูรณ์ — ของจริงควรมี secret scanning tool (เช่น gitleaks) รันใน CI ด้วย (module 09) ไม่ใช่พึ่ง hook อย่างเดียว

5Phase 5: Test + Verify จริงด้วย Evidence

รัน test suite จริง capture output เป็นไฟล์ log ไม่ใช่แค่บอกว่า "test ผ่านแล้ว" — evidence ต้องจับต้องได้และตรวจสอบย้อนหลังได้ 

pip install pytest
pytest -v tests/ 2>&1 | tee test-output.log

ตัวอย่าง output ที่ต้องมีจริงในไฟล์ log (ตัวอย่างรูปแบบ ไม่ใช่ fabricated):

tests/test_review_pr.py::test_detects_hardcoded_secret PASSED
tests/test_review_pr.py::test_flags_missing_test_file PASSED
tests/test_review_pr.py::test_comment_format_valid PASSED

3 passed in 0.42s

commit evidence เข้า repo:

git add test-output.log
git commit -m "test: capture pytest evidence for core loop"
Verify: มีไฟล์ test-output.log (หรือเทียบเท่า) ที่เป็น output จริงจากการรัน test ครั้งล่าสุด แสดงจำนวน test ที่ผ่าน/ไม่ผ่าน และไฟล์นี้ ถูก commit เข้า git แล้ว — ห้ามพิมพ์ log มือหรือ mock ผลลัพธ์
Troubleshoot: ไม่มีเวลาเขียน test ครบทุก edge case

ไม่ต้องครบ 100% — สำหรับ capstone ขอแค่ test ที่ cover "happy path" หลัก 1 เส้น และ "risk path" อย่างน้อย 1 เส้น (เช่น เจอ secret แล้วต้อง flag ได้จริง) เขียนใน README ว่า edge case ไหนยังไม่ cover เพื่อความโปร่งใส ดีกว่าไม่เขียน test เลย

6Phase 6: Deploy/Demo + เขียน README สรุป

เขียน README.md ที่มี output จริงที่ copy มาจากการรันคำสั่งจริง (ไม่ใช่ ตัวอย่างสมมติ) แล้วเตรียม demo สด — ถ้าเป็นไปได้ ให้ automate การรันผ่าน CI (module 09) เป็นขั้นบวก 

touch README.md

โครงสร้าง README ขั้นต่ำ:

# PR Review Agent — Capstone Project

## What it does
Automated first-pass PR reviewer built with Claude Code.
เช็ค hardcoded secret และ missing test ก่อน human reviewer จะดู

## Setup
\`\`\`
git clone 
cd capstone-agent
pip install -r requirements.txt
\`\`\`

## Usage
\`\`\`
$ python3 review_pr.py --pr 142
Fetching diff for PR #142...
Checking for secrets... none found
Checking for missing tests... src/auth.py changed, no test found
Posted review comment on PR #142
\`\`\`

## Safety
- PreToolUse hook blocks force-push and hardcoded-secret patterns
  (see .claude/hooks/block-secrets.sh)
- Tool permissions scoped to gh pr diff/comment only (see .claude/settings.json)

## Test evidence
See test-output.log — 3 passed in 0.42s (last run: Phase 5)

## Known limitations
- Regex-based secret detection, not a full secret scanner
- Does not auto-merge or modify code

ถ้าจะ automate เพิ่ม (ทางเลือก) ผูกเข้า GitHub Actions ตาม pattern module 09:

# .github/workflows/pr-review.yml (ตัวอย่างแนวคิด)
on: pull_request
jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: claude -p "run review_pr.py against this PR" \
          --allowedTools "Bash(python3 review_pr.py:*)"
Verify: มีไฟล์ README.md ที่มี section Setup/Usage/Safety/Test evidence/Known limitations ครบ และ "Usage" section แปะ output จริงที่ copy มาจากการรัน คำสั่งจริงในเครื่อง (ไม่ใช่ตัวอย่างที่แต่งขึ้น) — พร้อม demo สดได้ภายใน 5–10 นาที โดยไม่ต้องเปิด slide อธิบายก่อน

Next steps ที่แนะนำหลังจบคอร์ส:

  • อ่าน resource เพิ่มเติม: ติดตาม Claude Code documentation และ Anthropic engineering blog สำหรับ pattern ใหม่ ๆ, สำรวจ Hermes skill/plugin ecosystem เพื่อ reuse งานที่ทีมอื่นเคยทำไว้แล้ว แทนที่จะเริ่มจากศูนย์ทุกครั้ง
  • เก็บ capstone นี้ไว้ใน git ของทีม (ไม่ใช่แค่ local) พร้อม README ที่ชัดเจน เพื่อให้คนอื่นต่อยอดได้ — นี่คือจุดเริ่มต้นของ internal tool ที่มีคนใช้จริง ไม่ใช่แค่ side project ที่ทำแล้วทิ้ง
  • ทบทวน module ไหนก็ได้ที่ยังไม่มั่นใจ: ทุก slide/lab ยังอยู่ใน course home — กลับไปดูซ้ำได้ตลอด โดยเฉพาะ module 06 (hooks/permissions) และ module 08 (governance) ก่อนเอา agent ไปใช้กับงาน client จริง
