Module 02

Hermes Agent Platform

Architecture: Profiles · Skills · MCP Tools · Connectors · Subagents

AI Agent Engineering Course

ทำไมต้องเข้าใจสถาปัตยกรรมของ Hermes?

  • Hermes คือ platform ที่กำลังรันคอร์สนี้อยู่จริง — สิ่งที่คุณคุยกับ Claude Code ผ่าน Discord ตอนนี้คือ Hermes instance หนึ่ง
  • เข้าใจ architecture → debug ได้เร็วขึ้น, เขียน skill ได้ตรงจุด, ออกแบบ automation ได้ปลอดภัยขึ้น
  • Module นี้เป็นพื้นฐานก่อนไป Module 03: Claude Code Fundamentals

ภาพรวมสถาปัตยกรรม

Layer stack

  1. Profiles — แยก workspace ต่อบริบท (memory, skills, cron แยกกัน)
  2. MCP Tools layer — terminal, file I/O, browser, web_search, delegate_task, cronjob ฯลฯ
  3. Connectors — ช่องทางสื่อสารจริง: Discord, Telegram, Email
  4. Skills system — procedural knowledge ที่โหลดเฉพาะเมื่อ relevant
  5. Subagent orchestration — delegate_task สำหรับงานที่ต้อง isolate context

Diagram: TumEzZ Hermes System (ภาพรวมจริง)

ตัวอย่าง deployment จริง: Users & Channels (LINE/Discord) → Hermes Agent (Claude Sonnet + MCP) → Knowledge Layer (Google OKF/Local Files/Notion) + CI Pipeline (GitHub Actions) — รันบน Tailscale mesh เชื่อม Home/IDC ESXi

Integration Tools: 3 กลุ่มหลักจาก diagram

Diagram ก่อนหน้าแสดง integration จริงที่ deploy ใช้งาน — แบ่งได้เป็น 3 กลุ่มที่จะลงรายละเอียดต่อในสไลด์ถัดไป:

1. Skills & Tools (MCP)

ความสามารถของ agent เอง: Search, Summarize, Analyze, Code, Operate, Manage, Integrate

2. Knowledge Layer

แหล่งข้อมูลที่ agent อ่าน/เขียนได้: Google OKF, Local Files, Notion (optional)

3. Channels & CI Pipeline

ทางเข้า-ออกของ agent กับโลกภายนอก: LINE, Discord (user-facing) + GitHub Actions (automated commit → validate → deploy)

Categoryตัวอย่าง MCP tool จริงใช้ทำอะไร

Summarize / Analyzeweb_extract, read_fileดึงเนื้อหา อ่าน/สรุปเอกสาร

2. Knowledge Layer — แหล่งข้อมูลที่ agent เข้าถึงได้

Google OKF (Team Knowledge Base)

  • Structured knowledge, team documentation
  • Search & retrieval แบบ semantic
  • Version controlled — เห็น history การแก้ไข

Local Files (on Hermes host)

  • Configs, scripts, logs, reports
  • เข้าถึงตรงผ่าน read_file/write_file/search_files
  • เร็วที่สุด — ไม่มี network round-trip

Notion (Optional)

Team wiki / project docs — sync ผ่าน MCP connector, ใช้เก็บ knowledge ที่ non-technical stakeholder ต้องอ่านง่าย (เช่น presale proposal notes)

หลักการเลือกแหล่งข้อมูล: Local Files สำหรับ code/config ที่ agent แก้บ่อย, Google OKF สำหรับ knowledge ที่ทีมต้อง search ย้อนหลัง, Notion สำหรับเอกสารที่ non-engineer ต้องอ่าน/แก้ร่วม

3. Channels & CI Pipeline

User-facing Channels

  • Discord — team collaboration, multiple servers, bot commands (แบบที่ใช้คุยตอนนี้)
  • LINE — chat กับ Hermes, ask/request, get notification (เหมาะกับ non-technical user ในองค์กรไทย)

CI Pipeline (GitHub Actions)

  1. Commit changes — update docs/configs/prompts
  2. GitHub Actions — validate & test, build knowledge package
  3. Deploy/Sync — update Google OKF, sync ไป OneDrive/local, notify Hermes agent

ทำไม CI pipeline ถึงสำคัญสำหรับ knowledge base

Knowledge base ที่ agent อ้างอิง (Google OKF) ควรผ่าน version control + validation เหมือน code — กัน "แก้ผิดแล้ว agent ตอบผิดตาม" ได้ audit trail และ rollback ได้ถ้า sync พัง (โยงกับหลักการ verify evidence จาก Module 08)

Profiles: แยก workspace ต่อบริบท

Profile คือ "ห้องทำงาน" แยกกันโดยสมบูรณ์:

  • คนละ memory
  • คนละ skills
  • คนละ cron jobs

ตัวอย่าง: profile tumps สำหรับงานส่วนตัว แยกขาดจาก profile ของทีม KDX — ไม่มี data leak ข้ามบริบท

Path convention

/home/ubuntu/.hermes/profiles/<name>/
  ├── skills/
  ├── memories/
  ├── cron/
  └── plugins/ (ถ้ามี)

# default profile (ไม่ระบุชื่อ):
/home/ubuntu/.hermes/skills/
/home/ubuntu/.hermes/memories/
/home/ubuntu/.hermes/cron/

Terminology: Profile vs Agent vs Bot vs Subagent

Official docs แยก 5 คำนี้ชัดเจน — สับสนกันบ่อยในทีม ควรใช้ให้ตรง:

คำความหมาย
Profilepersistent home directory สำหรับ config+data ของ assistant หนึ่งตัว
Agentrunning instance ที่ใช้ profile นั้นอยู่ ณ ขณะนั้น
Botprofile ที่ถูก present เป็น roster entry ใน Bot Mode พร้อม avatar — ไม่ใช่ทุก profile จะเป็น Bot
Platform accountaccount จริงบน Telegram/Discord/ฯลฯ ที่ผูกกับ gateway ผ่าน bot token
Subagentchild assistant จาก delegate_task — conversation แยก ไม่ใช่ profile แยก
Official safety warning: "Never point two agent processes at the same profile" — สอง process ที่เขียน memory เข้า home เดียวกันจะโหลด write ของกันและกันเข้า system prompt ทุก session start จนสถานะพัง ควรใช้ external memory provider แทนถ้าต้องการ shared memory จริง

Memory vs Skills: ต่างกันตรงไหน

คุณสมบัติMemorySkills
Inject เมื่อไรทุก turn (persistent)เฉพาะเมื่อ relevant (on-demand)
เนื้อหาFacts ข้าม sessionProcedural knowledge / workflow
ข้อจำกัดมี char limit ต้องจัดการเมื่อเต็มไม่จำกัดจำนวน skill (โหลดทีละตัว)
ตัวอย่าง"ชื่อโปรเจกต์คือ X", "user ชอบภาษาไทย""วิธี deploy บน ESXi", "วิธีใช้ xurl"
ข้อควรระวัง: Memory เต็ม char limit ต้อง prune/summarize เอง — อย่าปล่อยให้ log สะสมจนล้น

Nous Portal / Tool Gateway

ฟีเจอร์ที่ Hermes ไม่ได้บังคับให้ทุกคนหา API key เอง — paid subscriber ใช้ web search/image gen/TTS/browser ผ่าน Tool Gateway โดยไม่ต้องมี API key แยกต่างหาก

เทียบกับสถานการณ์จริงของทีม

คล้ายกับ subscription ที่หลายคนมีอยู่แล้ว (เช่น ChatGPT Enterprise, Gemini Plus) — มี subscription ไม่ได้แปลว่ามี API access อัตโนมัติ ต้องแยกสมัคร API key ต่างหากเสมอ เว้นแต่ผู้ให้บริการมี "gateway" แบบเดียวกับ Nous Portal ที่ bridge ให้

Pattern: tool_search + tool_describe + tool_call

ปัญหา: มี MCP tools เยอะมาก ถ้าโหลด schema ทุกตัวทุก turn → context overhead สูง

// 1. ค้นหา tool ที่ต้องการ (ยังไม่รู้ schema)
tool_search({queries: ["send discord message", "read airtable record"]})

// 2. โหลด full schema เฉพาะ tool ที่จะใช้จริง
tool_describe({names: ["discord_send", "airtable_get"]})

// 3. เรียกใช้งานจริง
tool_call({calls: [{name: "discord_send", arguments: {...}}]})

แนวคิด: tool ที่ไม่ค่อยได้ใช้ถูก "deferred" — โหลดตามต้องการ ไม่ inject schema ทุกตัวตลอดเวลา ลด token cost ต่อ turn

Connectors: ช่องทางสื่อสารจริง

  • Hermes ไม่ได้ผูกกับ UI เดียว — official docs ของ Nous Research ระบุว่ารองรับ 20+ platforms จากตัว gateway เดียวกัน ไม่ใช่แค่ 2-3 ตัวที่คนทั่วไปคุ้นเคย
  • Multi-user thread — หลายคนคุยใน channel เดียวกันได้ Hermes ต้องแยกแยะว่าใครพูด
  • Sender prefix — ข้อความ inbound ถูก tag ด้วยชื่อผู้ส่ง เพื่อให้ agent ตอบถูกคน/บริบทถูก
  • Home channel — concept ของช่องทางหลักที่ agent "รายงานกลับ" หรือส่ง notification โดยดีฟอลต์

ตัวอย่างในคอร์สนี้

คุณกำลังคุยกับ Claude Code ผ่าน Discord connector — ข้อความของคุณถูก route เข้า Hermes, ประมวลผลด้วย profile ที่กำหนด, แล้วตอบกลับผ่าน connector เดิม

Connectors: ลิสต์เต็มจาก official docs

Hermes Agent รองรับ platform ต่อไปนี้จาก gateway process เดียว (ที่มา: hermes-agent.nousresearch.com):

Chat/Messaging ที่คุ้นเคย

Telegram, Discord, Slack, WhatsApp, Signal, Matrix, Mattermost, Email, SMS

Enterprise/ภูมิภาคเฉพาะ

Microsoft Teams, Google Chat, DingTalk, Feishu, WeCom, Weixin, QQ Bot, Yuanbao, BlueBubbles, Home Assistant, และอื่นๆ

ข้อควรระวัง: อย่าอธิบาย Hermes ว่า "Discord bot ที่มี AI" กับลูกค้า/ทีม — มันคือ multi-platform gateway จริงจัง เหมาะกับองค์กรที่ทีมกระจายใช้หลาย platform (เช่น ทีมไทยใช้ LINE คู่กับ Teams ของฝั่ง global)

Skills System: โครงสร้าง SKILL.md

---
name: my-skill-name
description: Use when <trigger condition>. <one-line behavior>.
version: 1.0
---

# My Skill Name

## When to use
...

## Steps
1. ...
2. ...

## Pitfalls
- ...

Frontmatter (YAML) + markdown body — description คือ trigger หลัก: ต้องขึ้นต้นด้วยวลีที่ self-contained ภายใน ~60 ตัวอักษรแรก (house authoring standard ของ Hermes) เพื่อให้ระบบ keyword-match แล้วโหลด skill ได้ถูกต้อง

Skills: linked_files & keyword trigger

Keyword-based trigger: agent เห็นรายชื่อ skill + description ทั้งหมดก่อน แล้วเลือกโหลด (skill_view) เฉพาะตัวที่ relevant กับ task ปัจจุบัน — ไม่ inject เนื้อหาเต็มทุก skill ทุก turn

linked_files structure

my-skill/
  SKILL.md
  references/   # เอกสารอ้างอิงยาว
  templates/    # ไฟล์ template ให้ copy
  scripts/      # helper scripts
Write lessons, not logs: skill ควรบันทึก imperative rule + เหตุผล ("ทำแบบนี้เพราะ X") ไม่ใช่ log เหตุการณ์ ("วันที่ Y แก้ bug Z") — log ไม่ generalize ข้าม task ในอนาคต

ทางลัด: /learn และ Autonomous Curator

/learn — สอน skill โดยไม่ต้องเขียน SKILL.md เอง

บอก agent ว่า "อยากให้รู้เรื่องอะไร" หรือชี้ไปยังเอกสารอ้างอิง agent จะ gather material ด้วย tool ที่มีอยู่แล้ว แล้ว author skill ให้เองตาม house standard

/learn filing an expense: open the portal,
New > Expense, attach the receipt, submit

Autonomous Curator

hermes curator รีวิว skill ที่ agent สร้างเอง, consolidate ที่ซ้ำซ้อน, archive ที่ล้าสมัย — ส่วนหนึ่งของ "closed learning loop" ที่ทำให้ Hermes ต่างจาก agent framework ทั่วไป

Subagent Orchestration: delegate_task

  • Subagent แต่ละตัวมี isolated context — ไม่เห็น conversation หลักของ parent agent
  • Parent ต้องส่ง context ที่จำเป็น ทั้งหมด เข้าไปใน task description เอง (path, spec, constraints)
  • ผลลัพธ์ที่ subagent ส่งกลับคือ self-report — ข้อความบรรยายว่าทำอะไรสำเร็จ
อย่าเชื่อ self-report เฉยๆ: ต้อง verify ด้วย evidence จริง เช่น เปิดไฟล์ดูเอง, เช็ค URL จริง, รัน command ตรวจสอบ — ไม่ใช่เชื่อคำอ้างของ subagent ว่า "ทำเสร็จแล้ว"

ตัวอย่าง delegate_task ในทางปฏิบัติ

delegate_task({
  task: "Build slides.html และ lab.html สำหรับ module 02 ...",
  context: "spec เต็ม + content brief + path ที่ต้องใช้ ...",
  // subagent ไม่เห็น conversation ก่อนหน้า ต้องใส่ context ครบ
})

// หลัง subagent รายงานว่า "สร้างไฟล์เสร็จแล้ว":
// → parent ต้อง read_file / ls -la ยืนยันเองเสมอ

Pattern นี้เหมาะกับงานที่แยก context ได้ชัดเจน (เช่น build 1 module ต่อ subagent) เพื่อไม่ให้ context หลักบวมจากรายละเอียดที่ไม่เกี่ยว

สรุป Module 02

  • Profiles แยก workspace สมบูรณ์ต่อบริบท — memory/skills/cron คนละชุด, ห้ามสอง process ชี้ profile เดียวกัน

  • delegate_task = isolated subagent — ต้อง verify ผลลัพธ์ด้วย evidence เสมอ
