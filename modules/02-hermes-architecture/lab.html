Hermes Agent Platform — Architecture

สำรวจโครงสร้างจริงของ Profiles, Skills และ MCP tools บนเครื่องที่รัน Hermes อยู่ พร้อมออกแบบ SKILL.md ของตัวเอง

⏱ ระยะเวลา: 45-60 นาที 🎯 ระดับ: Beginner–Intermediate 📋 Prereq: เข้าถึง Claude Code / Hermes ผ่าน terminal ได้

สิ่งที่ต้องมีก่อนเริ่ม

  • เข้าถึง terminal ของเครื่องที่รัน Hermes (หรือคุยกับ Claude Code ที่มี tool terminal อยู่แล้ว เช่นตอนนี้)
  • เข้าใจพื้นฐาน command line: ls, find, mkdir, text editor เช่น nano
  • อ่าน slides.html ของ Module 02 มาก่อน (โดยเฉพาะเรื่อง Profiles และ Skills system)

Learning Objectives

  • อธิบายได้ว่า profile หนึ่งมีโฟลเดอร์อะไรบ้าง และทำไมต้องแยกจาก profile อื่น
  • สำรวจโครงสร้าง skill directory จริง (หรือจำลองถ้าไม่มีสิทธิ์เข้าถึง)
  • เขียน SKILL.md ของตัวเองที่มี frontmatter ถูกต้อง (name + description) ตาม format ที่สอน
  • ตรวจสอบว่า description ของ skill ขึ้นต้นด้วย trigger phrase ที่ self-contained ภายใน ~57 ตัวอักษร
  • อธิบาย pattern tool_search → tool_describe → tool_call ได้ด้วยคำพูดตัวเอง

Diagram: ภาพรวม Deployment จริง

ตัวอย่าง production deployment: Users/Channels (LINE, Discord) → Hermes Agent (Claude Sonnet + MCP tools) → Knowledge Layer (Google OKF, Local Files, Notion) + CI Pipeline (GitHub Actions) บน Tailscale mesh network — ใช้เป็น reference เทียบกับโครงสร้างที่สำรวจใน step ถัดไป

1 สำรวจโครงสร้าง Hermes profile directory

ลองรันคำสั่งนี้ผ่าน terminal (ถ้าคุณกำลังคุยกับ Claude Code/Hermes อยู่ ให้ขอให้มันรันคำสั่งนี้ให้ หรือรันเองถ้ามี shell access):

find ~/.hermes -maxdepth 3 -type d 2>/dev/null | head -30

คำสั่งนี้ปลอดภัย (read-only, จำกัดความลึกแค่ 3 ระดับ) และจะโชว์โครงสร้างโฟลเดอร์ระดับบนของ Hermes เช่น profiles/, skills/, memories/, cron/

Verify: คุณควรเห็น path รูปแบบ ~/.hermes/profiles/<ชื่อ profile>/ อย่างน้อยหนึ่งรายการ หรือ ~/.hermes/skills/ ถ้าเป็น default profile — จดชื่อ profile ที่เจอไว้
ถ้าไม่มีสิทธิ์เข้าถึงเครื่อง Hermes จริง: ข้ามไป Step 2 และทำ lab แบบ "design a skill" แทน (ไม่ต้องพึ่ง shell access จริงของ Hermes host)

2 เจาะดูภายใน profile หนึ่ง

เลือก profile ที่เจอจาก Step 1 แล้วดูรายละเอียดของ skills ที่มีอยู่:

# แทน <profile> ด้วยชื่อ profile จริงที่เจอ (หรือข้าม path profiles/<profile> ถ้าใช้ default profile)
find ~/.hermes/profiles/<profile>/skills -maxdepth 2 2>/dev/null

# หรือ default profile
find ~/.hermes/skills -maxdepth 2 2>/dev/null

สังเกตว่าแต่ละ skill เป็นโฟลเดอร์ที่มีไฟล์ SKILL.md อยู่ข้างใน และบางตัวมี subfolder references/, templates/, หรือ scripts/ เพิ่ม

Verify: คุณสามารถชี้ได้ว่า skill กี่ตัวที่เจอ และมีตัวไหนบ้างที่มี linked_files (references/templates/scripts) เพิ่มเติมนอกเหนือจาก SKILL.md เปล่าๆ

3 อ่าน SKILL.md ตัวจริงหนึ่งไฟล์

เปิดไฟล์ SKILL.md ของ skill ใดก็ได้ที่เจอ แล้วสังเกต frontmatter (YAML ระหว่าง ---) กับ body:

cat ~/.hermes/profiles/<profile>/skills/<skill-name>/SKILL.md
# หรือใช้ text editor เช่น
nano ~/.hermes/profiles/<profile>/skills/<skill-name>/SKILL.md

ตรวจดูว่า description field ขึ้นต้นด้วยประโยคที่บอก trigger condition ชัดเจน (เช่น "Use when...") และมี behavior สั้นๆ ต่อท้าย

Verify: คุณระบุได้ว่า field name และ description ของ skill ที่เปิดดูคืออะไร และ description ยาวกี่ตัวอักษร (ควรสื่อ trigger ได้ภายใน ~57 ตัวอักษรแรก)

4 ออกแบบ SKILL.md ของตัวเอง (Design a Skill)

เลือก use case จริงจากงาน presale หรือ engineering ของคุณเอง (เช่น "การเตรียม proposal", "การ deploy ESXi lab", "การเขียน incident report") แล้วออกแบบ skill ตาม template ด้านล่าง:

---
name: my-presale-proposal-skill
description: Use when preparing a customer proposal for NTT presales engagements. Structures scope, pricing tiers, and technical assumptions consistently.
version: 1.0
---

# My Presale Proposal Skill

## When to use
Use this skill when a presale engineer needs to draft a customer-facing
technical proposal that must follow NTT's standard structure.

## Routing table
| Situation                          | Action                          |
|-------------------------------------|----------------------------------|
| New proposal from scratch           | Use templates/proposal.md       |
| Revising existing proposal          | Diff against previous version   |
| Pricing needs approval              | Escalate via clarify tool        |

## Steps
1. Gather customer requirements and constraints
2. Fill templates/proposal.md section by section
3. Validate pricing tiers against references/pricing-rules.md
4. Review with imperative checklist before sending

## Pitfalls
- Never quote pricing without checking references/pricing-rules.md first —
  stale pricing causes contract disputes.
- Always confirm scope boundaries explicitly — ambiguous scope is the
  #1 cause of scope-creep escalations in past engagements.

สร้างไฟล์จริงด้วย terminal:

mkdir -p ~/my-skill
nano ~/my-skill/SKILL.md
# วางเนื้อหา template ด้านบน (แก้ name/description ให้ตรงกับ use case จริงของคุณ) แล้ว save (Ctrl+O, Enter, Ctrl+X)
Verify: รันคำสั่งด้านล่างเพื่อยืนยันว่า YAML frontmatter valid และมี field ที่จำเป็นครบ: 
head -6 ~/my-skill/SKILL.md
# ควรเห็น --- ... name: ... description: ... version: ... ---
description ต้องขึ้นต้นด้วย trigger phrase ที่ self-contained (บอกว่า "ใช้เมื่อไร" ได้โดยไม่ต้องอ่านส่วนอื่น) และควรอยู่ในช่วง ~57 ตัวอักษรแรก

5 เพิ่ม linked_files (references / templates / scripts)

ถ้า skill ของคุณซับซ้อนพอที่จะมี routing table (เช่น step 4 ข้างบน) ให้แยกไฟล์เสริมออกจาก SKILL.md หลัก เพื่อไม่ให้ main file ยาวเกินไป:

mkdir -p ~/my-skill/references ~/my-skill/templates
# ตัวอย่าง: ย้าย pricing rules ยาวๆ ไปไว้ที่ reference แยก
nano ~/my-skill/references/pricing-rules.md
nano ~/my-skill/templates/proposal.md

หลักการ: SKILL.md ควรสั้น กระชับ พอที่จะโหลดเข้า context ได้เร็ว ส่วนรายละเอียดยาวๆ (เช่น ตาราง pricing เต็ม, ตัวอย่างเอกสารยาว) ให้แยกเป็นไฟล์ reference ที่โหลดเฉพาะเมื่อจำเป็นจริงๆ

Verify: find ~/my-skill -type f ควรเห็นอย่างน้อย SKILL.md + 1 ไฟล์ใน references/ หรือ templates/

6 เขียน "lesson" ไม่ใช่ "log"

กลับไปดู section Pitfalls ใน SKILL.md ที่เขียนไว้ใน Step 4 แล้วถามตัวเองว่า:

  • แต่ละบรรทัดเป็น imperative rule + เหตุผล หรือเปล่า? (เช่น "Never X — เพราะ Y")
  • หรือมันเป็นแค่ log เหตุการณ์ ที่ generalize ไม่ได้? (เช่น "วันที่ 3 มกรา เจอ bug ที่ proposal ของลูกค้า A")

ถ้าเจอ pitfall ที่เขียนเป็น log ให้แก้เป็น rule ทั่วไปที่ใช้ได้กับทุก use case ในอนาคต ไม่ใช่แค่เหตุการณ์เดียว

Verify: อ่าน pitfalls ทั้งหมดใน SKILL.md ของคุณ — ทุกบรรทัดต้องขึ้นต้นด้วยกริยาสั่ง (Never/Always/Use/Avoid) และมีเหตุผลต่อท้ายด้วย "—" หรือ "because"

7 จำลอง tool_search → tool_describe → tool_call

เข้าใจ pattern การเรียก deferred tools โดยลองไล่ scenario สมมุตินี้ (ไม่ต้องรันจริง เป็น mental exercise):

สถานการณ์: คุณต้องการส่งข้อความแจ้งเตือนไปที่ Discord channel หนึ่ง
แต่ tool ส่ง Discord message ไม่ได้อยู่ใน default tool list

Step 1: tool_search({queries: ["send discord message"]})
        → ได้ชื่อ tool กลับมา เช่น "discord_send" (ยังไม่รู้ parameter)

Step 2: tool_describe({names: ["discord_send"]})
        → ได้ full JSON schema พร้อม parameter ที่ต้องใส่

Step 3: tool_call({calls: [{name: "discord_send", arguments: {...}}]})
        → เรียกใช้งานจริง
Verify: อธิบายเป็นคำพูดของตัวเองได้ว่าทำไม pattern นี้ถึงลด context overhead เมื่อเทียบกับการโหลด schema ของทุก tool ไว้ตั้งแต่ต้น (คำตอบที่ถูก: schema ที่ไม่ถูกใช้ไม่ถูก inject เข้า context ทุก turn)
ข้อควรระวัง: อย่าสมมุติชื่อ parameter ของ tool เอง — เรียก tool_describe เพื่อดู schema จริงก่อนเรียก tool_call เสมอ ชื่อ parameter ที่เดาผิดจะทำให้ call fail
Troubleshooting: find ~/.hermes ไม่เจออะไรเลย / permission denied

สาเหตุที่เป็นไปได้:

  • คุณไม่มี shell access ตรงกับเครื่องที่รัน Hermes จริง (พบได้บ่อยถ้าคุยผ่าน connector อย่าง Discord ที่ terminal ทำงานบน sandbox/VM แยก) — ให้ข้ามไปทำ Step 4 (design a skill) แทน ซึ่งไม่ต้องพึ่ง path จริงของ Hermes
  • Hermes ถูกติดตั้งด้วย path หรือชื่อโฟลเดอร์อื่น ลองหา find / -maxdepth 4 -iname "*hermes*" -type d 2>/dev/null (อาจช้าและต้องรอสักครู่)
  • permission denied เป็นเรื่องปกติถ้า user ปัจจุบันไม่ใช่ owner ของ home directory ที่รัน Hermes — ไม่ต้องพยายาม sudo เข้าไปดู, ให้ทำ lab แบบ design skill แทน
Troubleshooting: SKILL.md frontmatter ไม่ valid

ปัญหาที่พบบ่อย:

  • ลืมใส่ --- ปิดท้าย frontmatter (ต้องมีทั้งเปิดและปิด)
  • description มีเครื่องหมาย : อยู่ในข้อความโดยไม่ quote — YAML จะตีความผิด ให้ครอบด้วย "..."
  • เว้นบรรทัดว่างระหว่าง key: value ผิดตำแหน่ง (YAML sensitive กับ indentation)

ตรวจสอบเร็วๆ ด้วย Python ถ้ามี:

python3 -c "
import re
content = open('$HOME/my-skill/SKILL.md').read()
fm = content.split('---')[1]
print(fm)
"

สรุป & ต่อยอด

ใน lab นี้คุณได้สำรวจ (หรือจำลอง) โครงสร้างจริงของ Hermes profile/skills directory, เข้าใจความแตกต่างระหว่าง memory กับ skills ในทางปฏิบัติ, และเขียน SKILL.md ของตัวเองที่มี frontmatter ถูกต้องตาม format ที่ใช้จริง พร้อมฝึกหลักการ "write lessons, not logs"

ต่อยอด:

  • ลองขยาย skill ที่เขียนไว้ด้วย scripts/ ที่ automate ขั้นตอนซ้ำๆ ของ use case นั้น
  • ลองใช้ delegate_task เพื่อให้ subagent ทดสอบใช้ skill ของคุณ แล้วดูว่า self-report ตรงกับสิ่งที่เกิดขึ้นจริงหรือไม่ (verify ด้วย evidence เสมอ ตามที่เรียนใน slides)
