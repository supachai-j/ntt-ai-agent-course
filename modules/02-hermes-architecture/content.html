Hermes Agent Platform — Architecture

สถาปัตยกรรมเต็มของ Hermes: Profiles, MCP Tools layer, Connectors, Skills system, และ Subagent orchestration — พื้นฐานก่อนเข้าสู่ Claude Code Fundamentals ใน Module 03

TL;DR: Hermes คือ platform ที่กำลังรันคอร์สนี้อยู่จริง ประกอบด้วย 5 layer หลัก — Profiles (แยก workspace), MCP Tools (ความสามารถของ agent), Connectors (ช่องทางสื่อสาร 20+ platforms), Skills system (procedural knowledge แบบ on-demand), และ Subagent orchestration (delegate_task) เข้าใจ layer เหล่านี้ช่วยให้ debug ไว เขียน skill ตรงจุด และออกแบบ automation ได้ปลอดภัย

ทำไมต้องเข้าใจสถาปัตยกรรมของ Hermes?

Hermes คือ platform ที่กำลังรันคอร์สนี้อยู่จริง — สิ่งที่คุณคุยกับ Claude Code ผ่าน Discord ตอนนี้คือ Hermes instance หนึ่ง ไม่ใช่ตัวอย่างสมมติหรือ diagram บนกระดาษ การเข้าใจ architecture ช่วยให้ debug ได้เร็วขึ้นเมื่อมีอะไรผิดปกติ เขียน skill ได้ตรงจุดเพราะรู้ว่าระบบ inject/โหลดเนื้อหาตอนไหน และออกแบบ automation ได้ปลอดภัยขึ้นเพราะเข้าใจขอบเขตของแต่ละ layer โมดูลนี้เป็นพื้นฐานสำคัญก่อนไป Module 03: Claude Code Fundamentals ซึ่งจะลงรายละเอียดของ Claude Code ในฐานะ subagent ที่ Hermes เรียกใช้

Integration Tools: 3 กลุ่มหลักจาก diagram

Diagram ข้างต้นแสดง integration จริงที่ deploy ใช้งาน แบ่งออกได้เป็น 3 กลุ่มใหญ่:

  1. Skills & Tools (MCP) — ความสามารถของ agent เอง: Search, Summarize, Analyze, Code, Operate, Manage, Integrate
  2. Knowledge Layer — แหล่งข้อมูลที่ agent อ่าน/เขียนได้: Google OKF, Local Files, Notion (optional)
  3. Channels & CI Pipeline — ทางเข้า-ออกของ agent กับโลกภายนอก: LINE, Discord (user-facing) + GitHub Actions (automated commit → validate → deploy)

1. Skills & Tools (MCP) — Capability Categories

Categoryตัวอย่าง MCP tool จริงใช้ทำอะไร
Searchweb_search, search_filesค้นเว็บ / ค้นไฟล์ในเครื่อง
Summarize / Analyzeweb_extract, read_fileดึงเนื้อหา อ่าน/สรุปเอกสาร
Codeterminal, patch, write_fileรันคำสั่ง แก้ไฟล์ เขียนโค้ด
Operatebrowser_*, cronjob_manageควบคุม browser, ตั้งเวลา automation
Manage / Integratetool_search + tool_call (deferred connectors)ต่อ third-party service ตามต้องการ ไม่ preload ทุกตัว
⚠️ ข้อควรระวัง: ไม่ใช่ทุก MCP tool ถูก preload ตลอดเวลา — บาง connector (เช่น Notion, Airtable, Google Workspace) เป็น "deferred tool" ต้องเรียกผ่าน tool_search ก่อนจึงจะ tool_describe/tool_call ได้

2. Knowledge Layer — แหล่งข้อมูลที่ agent เข้าถึงได้

Google OKF (Team Knowledge Base): structured knowledge และ team documentation, รองรับ search & retrieval แบบ semantic, และ version controlled — เห็น history การแก้ไข

Local Files (on Hermes host): configs, scripts, logs, reports เข้าถึงตรงผ่าน read_file/write_file/search_files เร็วที่สุดเพราะไม่มี network round-trip

Notion (Optional): team wiki / project docs, sync ผ่าน MCP connector, ใช้เก็บ knowledge ที่ non-technical stakeholder ต้องอ่านง่าย (เช่น presale proposal notes)

💡 หลักการเลือกแหล่งข้อมูล: Local Files สำหรับ code/config ที่ agent แก้บ่อย, Google OKF สำหรับ knowledge ที่ทีมต้อง search ย้อนหลัง, Notion สำหรับเอกสารที่ non-engineer ต้องอ่าน/แก้ร่วม

3. Channels & CI Pipeline

User-facing Channels: Discord ใช้สำหรับ team collaboration, multiple servers, bot commands (แบบที่ใช้คุยตอนนี้) ส่วน LINE เหมาะกับ non-technical user ในองค์กรไทย — chat กับ Hermes, ask/request, get notification

CI Pipeline (GitHub Actions) ทำงานเป็น 3 ขั้นตอน: (1) Commit changes — update docs/configs/prompts, (2) GitHub Actions — validate & test, build knowledge package, (3) Deploy/Sync — update Google OKF, sync ไป OneDrive/local, notify Hermes agent

ทำไม CI pipeline ถึงสำคัญสำหรับ knowledge base: knowledge base ที่ agent อ้างอิง (Google OKF) ควรผ่าน version control + validation เหมือน code — กัน "แก้ผิดแล้ว agent ตอบผิดตาม" ได้ audit trail และ rollback ได้ถ้า sync พัง (โยงกับหลักการ verify evidence จาก Module 08)

Profiles: แยก workspace ต่อบริบท

Profile คือ "ห้องทำงาน" แยกกันโดยสมบูรณ์ — คนละ memory, คนละ skills, คนละ cron jobs ตัวอย่างเช่น profile tumps สำหรับงานส่วนตัว แยกขาดจาก profile ของทีม KDX ไม่มี data leak ข้ามบริบท

Path convention

/home/ubuntu/.hermes/profiles/<name>/
  ├── skills/
  ├── memories/
  ├── cron/
  └── plugins/ (ถ้ามี)

# default profile (ไม่ระบุชื่อ):
/home/ubuntu/.hermes/skills/
/home/ubuntu/.hermes/memories/
/home/ubuntu/.hermes/cron/

Terminology: Profile vs Agent vs Bot vs Subagent

Official docs แยก 5 คำนี้ชัดเจน — สับสนกันบ่อยในทีม ควรใช้ให้ตรง:

คำความหมาย
Profilepersistent home directory สำหรับ config+data ของ assistant หนึ่งตัว
Agentrunning instance ที่ใช้ profile นั้นอยู่ ณ ขณะนั้น
Botprofile ที่ถูก present เป็น roster entry ใน Bot Mode พร้อม avatar — ไม่ใช่ทุก profile จะเป็น Bot
Platform accountaccount จริงบน Telegram/Discord/ฯลฯ ที่ผูกกับ gateway ผ่าน bot token
Subagentchild assistant จาก delegate_task — conversation แยก ไม่ใช่ profile แยก
⚠️ Official safety warning: "Never point two agent processes at the same profile" — สอง process ที่เขียน memory เข้า home เดียวกันจะโหลด write ของกันและกันเข้า system prompt ทุก session start จนสถานะพัง ควรใช้ external memory provider แทนถ้าต้องการ shared memory จริง

4 Open Standards เบื้องหลัง Agent ที่ Swap ได้: MCP, agents.md, Skills, ACP

นอกจาก MCP ที่คุยไปแล้ว วงการ AI coding agent ตอนนี้มีมาตรฐานเปิด (open standard) อีก 3 ตัวที่เกิดขึ้นมาเพื่อเหตุผลเดียวกัน: กันไม่ให้ทีมถูก lock-in กับ agent หรือ IDE ตัวใดตัวหนึ่ง เพราะ landscape ของ agent เปลี่ยนเร็วมาก (leaderboard สลับผู้นำแทบทุกเดือน) วิธีคิดง่ายๆ คือมองแต่ละมาตรฐานเป็นเส้นเชื่อมคนละเส้นระหว่าง agent กับสิ่งรอบๆ มัน:

มาตรฐานเชื่อม agent กับอะไร
MCP (Model Context Protocol)External tools / data sources — เครื่องมือและแหล่งข้อมูลภายนอก (คุยไปแล้วด้านบน)
agents.mdProject rules — ไฟล์ plain-text convention ที่เก็บกฎ/convention ของ project ให้ agent ตัวไหนก็อ่านได้
Agent SkillsRepeatable workflows — ชุด instruction + resource ที่ packaged ไว้ใช้ซ้ำ (เหมือน Skills system ของ Hermes ที่คุยไปก่อนหน้า)
ACP (Agent Client Protocol)Client/Editor — มาตรฐานเชื่อม agent เข้ากับ IDE/editor ที่ใช้งานมัน

ACP (Agent Client Protocol): มาตรฐานใหม่ล่าสุด

ACP standardize การเชื่อมต่อระหว่าง AI agent กับ client ของมัน (เช่น IDE หรือ text editor) แนวคิดเทียบได้ตรงๆ กับ LSP (Language Server Protocol) ที่ standardize การเชื่อม language server เข้ากับ editor มาก่อนหน้านี้ — LSP ทำให้ editor ตัวไหนก็ต่อ language server ตัวไหนก็ได้โดยไม่ต้องเขียน integration เฉพาะคู่ ACP ก็เล็งผลแบบเดียวกันแต่กับ agent: agent ที่ compatible กับ ACP เสียบเข้า editor/IDE ที่ compatible กับ ACP ได้ทันที โดยไม่ต้องมีใครเขียน custom integration ให้แต่ละคู่

ACP ไม่ได้ครอบคลุมแค่ chat interface — ยังรวมถึงฟีเจอร์ที่ IDE คาดหวังจาก agent สมัยใหม่ เช่น next-edit-suggestions (แนะนำการแก้ไขบรรทัดถัดไปในตัว editor) และ plan mode (โหมดให้ agent วางแผนก่อนลงมือแก้โค้ดจริง)

ACP Registry: เป็นแนวคิดของ directory ที่ IDE ใช้ discover, install และเชื่อมต่อกับ agent ที่ compatible กับ ACP ได้อัตโนมัติ ตัวอย่างที่ยกในวิดีโอ: AI chat panel ของ JetBrains WebStorm ให้ browse/install agent อย่าง "Open Code" จาก ACP registry ได้ด้วยคลิกเดียว — WebStorm จัดการทั้งการติดตั้ง binary ของ agent และการต่อสายเข้ากับ IDE ให้เองทั้งหมด ผู้ใช้ไม่ต้องไปหา config เองแยกต่างหาก

💡 ทำไม portability แบบนี้ถึงสำคัญ: เมื่อ tools (MCP), project rules (agents.md), workflows (Skills), และ editor integration (ACP) ถูก standardize แยกออกจากตัว agent เอง ทีมสามารถสลับ coding agent (เช่น Claude Code ↔ Codex ↔ ตัวอื่น) ได้โดยไม่ต้องรื้อ setup ทั้งหมดใหม่ — future-proof ต่อ leaderboard ที่เปลี่ยนผู้นำเร็วมาก

Nous Portal / Tool Gateway

ฟีเจอร์ที่ Hermes ไม่ได้บังคับให้ทุกคนหา API key เอง — paid subscriber ใช้ web search/image gen/TTS/browser ผ่าน Tool Gateway โดยไม่ต้องมี API key แยกต่างหาก

💡 เทียบกับสถานการณ์จริงของทีม: คล้ายกับ subscription ที่หลายคนมีอยู่แล้ว (เช่น ChatGPT Enterprise, Gemini Plus) — มี subscription ไม่ได้แปลว่ามี API access อัตโนมัติ ต้องแยกสมัคร API key ต่างหากเสมอ เว้นแต่ผู้ให้บริการมี "gateway" แบบเดียวกับ Nous Portal ที่ bridge ให้

Pattern: tool_search + tool_describe + tool_call

ปัญหา: มี MCP tools เยอะมาก ถ้าโหลด schema ทุกตัวทุก turn → context overhead สูง แนวทางแก้คือ pattern 3 ขั้นตอน:

// 1. ค้นหา tool ที่ต้องการ (ยังไม่รู้ schema)
tool_search({queries: ["send discord message", "read airtable record"]})

// 2. โหลด full schema เฉพาะ tool ที่จะใช้จริง
tool_describe({names: ["discord_send", "airtable_get"]})

// 3. เรียกใช้งานจริง
tool_call({calls: [{name: "discord_send", arguments: {...}}]})

แนวคิด: tool ที่ไม่ค่อยได้ใช้ถูก "deferred" — โหลดตามต้องการ ไม่ inject schema ทุกตัวตลอดเวลา ลด token cost ต่อ turn

Connectors: ช่องทางสื่อสารจริง

Hermes ไม่ได้ผูกกับ UI เดียว — official docs ของ Nous Research ระบุว่ารองรับ 20+ platforms จากตัว gateway เดียวกัน ไม่ใช่แค่ 2-3 ตัวที่คนทั่วไปคุ้นเคย

  • Multi-user thread — หลายคนคุยใน channel เดียวกันได้ Hermes ต้องแยกแยะว่าใครพูด
  • Sender prefix — ข้อความ inbound ถูก tag ด้วยชื่อผู้ส่ง เพื่อให้ agent ตอบถูกคน/บริบทถูก
  • Home channel — concept ของช่องทางหลักที่ agent "รายงานกลับ" หรือส่ง notification โดยดีฟอลต์
💡 ตัวอย่างในคอร์สนี้: คุณกำลังคุยกับ Claude Code ผ่าน Discord connector — ข้อความของคุณถูก route เข้า Hermes, ประมวลผลด้วย profile ที่กำหนด, แล้วตอบกลับผ่าน connector เดิม

Connectors: ลิสต์เต็มจาก official docs

Hermes Agent รองรับ platform ต่อไปนี้จาก gateway process เดียว (ที่มา: hermes-agent.nousresearch.com):

Chat/Messaging ที่คุ้นเคย: Telegram, Discord, Slack, WhatsApp, Signal, Matrix, Mattermost, Email, SMS

Enterprise/ภูมิภาคเฉพาะ: Microsoft Teams, Google Chat, DingTalk, Feishu, WeCom, Weixin, QQ Bot, Yuanbao, BlueBubbles, Home Assistant และอื่นๆ

⚠️ ข้อควรระวัง: อย่าอธิบาย Hermes ว่า "Discord bot ที่มี AI" กับลูกค้า/ทีม — มันคือ multi-platform gateway จริงจัง เหมาะกับองค์กรที่ทีมกระจายใช้หลาย platform (เช่น ทีมไทยใช้ LINE คู่กับ Teams ของฝั่ง global)

Skills System: โครงสร้าง SKILL.md

---
name: my-skill-name
description: Use when <trigger condition>. <one-line behavior>.
version: 1.0
---

# My Skill Name

## When to use
...

## Steps
1. ...
2. ...

## Pitfalls
- ...

Frontmatter (YAML) + markdown body — description คือ trigger หลัก: ต้องขึ้นต้นด้วยวลีที่ self-contained ภายใน ~60 ตัวอักษรแรก (house authoring standard ของ Hermes) เพื่อให้ระบบ keyword-match แล้วโหลด skill ได้ถูกต้อง

Skills: linked_files & keyword trigger

Keyword-based trigger: agent เห็นรายชื่อ skill + description ทั้งหมดก่อน แล้วเลือกโหลด (skill_view) เฉพาะตัวที่ relevant กับ task ปัจจุบัน — ไม่ inject เนื้อหาเต็มทุก skill ทุก turn

my-skill/
  SKILL.md
  references/   # เอกสารอ้างอิงยาว
  templates/    # ไฟล์ template ให้ copy
  scripts/      # helper scripts
⚠️ Write lessons, not logs: skill ควรบันทึก imperative rule + เหตุผล ("ทำแบบนี้เพราะ X") ไม่ใช่ log เหตุการณ์ ("วันที่ Y แก้ bug Z") — log ไม่ generalize ข้าม task ในอนาคต

ทางลัด: /learn และ Autonomous Curator

/learn — สอน skill โดยไม่ต้องเขียน SKILL.md เอง: บอก agent ว่า "อยากให้รู้เรื่องอะไร" หรือชี้ไปยังเอกสารอ้างอิง agent จะ gather material ด้วย tool ที่มีอยู่แล้ว แล้ว author skill ให้เองตาม house standard

/learn filing an expense: open the portal,
New > Expense, attach the receipt, submit

Autonomous Curator: hermes curator รีวิว skill ที่ agent สร้างเอง, consolidate ที่ซ้ำซ้อน, archive ที่ล้าสมัย — ส่วนหนึ่งของ "closed learning loop" ที่ทำให้ Hermes ต่างจาก agent framework ทั่วไป

Subagent Orchestration: delegate_task

  • Subagent แต่ละตัวมี isolated context — ไม่เห็น conversation หลักของ parent agent
  • Parent ต้องส่ง context ที่จำเป็น ทั้งหมด เข้าไปใน task description เอง (path, spec, constraints)
  • ผลลัพธ์ที่ subagent ส่งกลับคือ self-report — ข้อความบรรยายว่าทำอะไรสำเร็จ
⚠️ อย่าเชื่อ self-report เฉยๆ: ต้อง verify ด้วย evidence จริง เช่น เปิดไฟล์ดูเอง, เช็ค URL จริง, รัน command ตรวจสอบ — ไม่ใช่เชื่อคำอ้างของ subagent ว่า "ทำเสร็จแล้ว"

ตัวอย่าง delegate_task ในทางปฏิบัติ

delegate_task({
  task: "Build slides.html และ lab.html สำหรับ module 02 ...",
  context: "spec เต็ม + content brief + path ที่ต้องใช้ ...",
  // subagent ไม่เห็น conversation ก่อนหน้า ต้องใส่ context ครบ
})

// หลัง subagent รายงานว่า "สร้างไฟล์เสร็จแล้ว":
// → parent ต้อง read_file / ls -la ยืนยันเองเสมอ

Pattern นี้เหมาะกับงานที่แยก context ได้ชัดเจน (เช่น build 1 module ต่อ subagent) เพื่อไม่ให้ context หลักบวมจากรายละเอียดที่ไม่เกี่ยว

สรุป Module 02

  • Profiles แยก workspace สมบูรณ์ต่อบริบท — memory/skills/cron คนละชุด, ห้ามสอง process ชี้ profile เดียวกัน
  • Terminology: Profile ≠ Agent ≠ Bot ≠ Platform account ≠ Subagent
  • Memory = inject ทุก turn มี limit, Skills = โหลดตามต้องการ ไม่จำกัดจำนวน, description ≤60 ตัวอักษร
  • MCP tools ใช้ pattern tool_search → tool_describe → tool_call เพื่อลด context overhead
  • Connectors เชื่อม Hermes กับ 20+ platforms จริง (ไม่ใช่แค่ Discord/Telegram/Email)
  • Skills เขียนแบบ "lessons not logs" + /learn สอน skill เร็วๆ + Autonomous Curator ดูแลให้
  • delegate_task = isolated subagent — ต้อง verify ผลลัพธ์ด้วย evidence เสมอ
  • 4 open standards ทำให้ agent portable: MCP (tools), agents.md (project rules), Skills (workflows), ACP (editor/client) — สลับ coding agent ได้โดยไม่ต้องรื้อ setup
