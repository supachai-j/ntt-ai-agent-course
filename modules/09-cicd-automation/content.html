CI/CD & Automation Integration

รัน Claude Code แบบ headless ใน pipeline อัตโนมัติ, ใช้ gh CLI ทำ PR/deploy automation, deploy static site ขึ้น GitHub Pages แบบตรวจสอบได้จริง และวัดผลว่า pipeline ดีขึ้นจริงหรือแค่รู้สึกว่าดีขึ้นด้วย Evals

TL;DR: Headless mode (--bare -p) คือวิธีเดียวที่รัน Claude Code ใน CI ได้ — ต้อง lock tools, จำกัด turns/budget เสมอ. gh CLI + gh api ใช้ทำ PR automation และ deploy GitHub Pages ได้ทั้งหมด. แต่ไม่ว่า CI จะรายงานว่าสำเร็จแค่ไหน ต้อง verify ด้วยตัวเองเสมอ (curl HTTP code จริง, เปิด PR ดู comment จริง) — และหลักการเดียวกันนี้ขยายไปถึงการวัดผล prompt/config ด้วย Evals: อย่าเชื่อผลรันครั้งเดียว (n=1) ต้องมี Golden Task Set, เกณฑ์แบบ deterministic, และรันซ้ำหลายครั้งก่อนสรุปว่า "ดีขึ้นจริง"

ทำไม CI ต้องรัน Claude Code แบบ headless

Interactive REPL ที่เราคุ้นเคยตอนใช้งาน Claude Code แบบมือถือคีย์บอร์ด ใช้กับ pipeline อัตโนมัติไม่ได้ — เพราะไม่มีคนนั่งกด Enter ตอบ permission prompt กลางทาง CI runner รันแบบไม่มีคนเฝ้า ดังนั้นต้องใช้ headless mode ผ่านแฟล็ก --bare -p ซึ่งจะรับ input เข้ามาครั้งเดียว ประมวลผล แล้วส่ง output ออกมาแล้วจบการทำงานทันที ไม่ค้างรอ interaction ใดๆ เพิ่ม เหมาะสมพอดีกับธรรมชาติของ CI runner ที่ทำงานแบบ non-interactive job

Pattern นี้เปิดทางให้ทำงานอัตโนมัติได้หลายอย่างโดยไม่ต้องมี human อยู่ในลูปเลย เช่น automated PR review (สแกน diff หาบั๊ก/security issue อัตโนมัติทุกครั้งที่เปิด PR), changelog generation (สรุปการเปลี่ยนแปลงจาก commit history), และ test-failure triage (วิเคราะห์ทำไม test ถึงพังโดยไม่ต้องรอ engineer มานั่งอ่าน log เอง)

⚠️ ข้อควรระวังที่สำคัญที่สุด: headless หมายความว่าไม่มีใครยืนยัน permission กลางทางได้เลย ดังนั้นต้อง lock --allowedTools ให้แคบที่สุดเท่าที่งานจะทำได้ — ไม่ปล่อยให้ agent มีสิทธิ์กว้างเกินความจำเป็นในสภาพแวดล้อมที่ไม่มีคนคอยเบรก

Headless flags ที่ต้องรู้

มีแฟล็กหลักสี่ตัวที่ใช้ควบคุมพฤติกรรมของ Claude Code เมื่อรันแบบ headless:

Flagทำอะไร
--bareปิด UI แบบ interactive ทั้งหมด และข้าม OAuth login flow ที่ปกติต้องมีคนเปิด browser ยืนยันตัวตน
-p "..."ส่ง prompt ตรงเข้าไปให้รันครั้งเดียวจบ ไม่ใช่เปิด session สนทนาต่อเนื่อง
--allowedTools 'Read,Bash'จำกัดชุด tool ที่ agent เรียกใช้ได้ในรอบการรันนี้ — ยิ่งแคบยิ่งปลอดภัยในสภาพแวดล้อมที่ไม่มีคนคอยอนุมัติ
--max-turns Nจำกัดจำนวนรอบคิด/เรียก tool สูงสุด กันไม่ให้ agent วน loop ไม่จบและกินทรัพยากร/เวลาไม่จำกัด
💡 Auth ต้องมาจาก environment เสมอ — เพราะ bare mode ข้าม OAuth device flow ไปเลย จึงต้องมี ANTHROPIC_API_KEY อยู่ใน environment ของ runner ให้พร้อมก่อนรัน ปกติแล้ววิธีที่ปลอดภัยที่สุดคือ set ผ่าน GitHub Secrets แล้วดึงเข้ามาเป็น environment variable ในขั้นตอนของ job เท่านั้น ไม่ hardcode ค่าไว้ใน workflow file

ตัวอย่างคำสั่ง headless แบบเต็ม

ตัวอย่างการรัน headless review หนึ่งครั้งที่รวมทุกแฟล็กสำคัญเข้าด้วยกัน รวมถึงการควบคุมต้นทุนด้วย:

export ANTHROPIC_API_KEY="${{ secrets.ANTHROPIC_API_KEY }}"

claude --bare \
  -p "Review the diff in this PR for bugs, security issues, and style. Output findings as a markdown list." \
  --allowedTools 'Read,Bash' \
  --max-turns 8 \
  --max-budget-usd 0.50 \
  --fallback-model claude-3-5-haiku-20241022 \
  > review-output.md

ผลลัพธ์ที่ได้ออกมาเป็น plain text ธรรมดา ทำให้สามารถ pipe ต่อเข้า step อื่นๆ ใน pipeline ได้ง่าย เช่น เอาไปโพสต์กลับเข้า PR เป็น comment อัตโนมัติ หรือเอาไปประกอบเป็นส่วนหนึ่งของ report อื่น

GitHub Actions workflow แบบเต็ม: auto-review PR

ตัวอย่าง workflow YAML ที่ใช้งานได้จริงทั้งไฟล์ สำหรับตั้งค่าให้ทุกครั้งที่มีการเปิด PR ใหม่หรือ push commit เพิ่มเข้า branch นั้น Claude Code จะรัน review อัตโนมัติแล้วโพสต์ผลกลับเป็น comment:

name: claude-review
on:
  pull_request:
    types: [opened, synchronize]

jobs:
  review:
    runs-on: ubuntu-latest
    permissions:
      pull-requests: write
      contents: read
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Install Claude Code
        run: npm install -g @anthropic-ai/claude-code

      - name: Run headless review
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          git diff origin/${{ github.base_ref }}...HEAD > pr.diff
          claude --bare -p "Review pr.diff for bugs and risks. Be concise." \
            --allowedTools 'Read,Bash' --max-turns 6 > review.md

      - name: Post comment to PR
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: gh pr comment ${{ github.event.pull_request.number }} --body-file review.md

Trigger event: อ่านให้ถูกก่อนเขียน job

ก่อนเขียน job ต้องเข้าใจ trigger event ที่ใช้ให้ถูกต้อง เพราะการตั้งค่าผิดจะทำให้ workflow ไม่รัน หรือรันผิดจังหวะ:

pull_request
types: [opened, synchronize] — รันตอนเปิด PR ใหม่ และรันซ้ำทุกครั้งที่มีการ push commit เพิ่มเข้าไปใน branch นั้น (ไม่ใช่แค่ครั้งแรกที่เปิด PR เท่านั้น)
Context variable ที่ใช้บ่อย
github.event.pull_request.number, github.base_ref, github.head_ref — ใช้สำหรับระบุหมายเลข PR และกำหนด diff range ที่จะเทียบระหว่าง branch เป้าหมายกับ branch ที่กำลังจะ merge เข้า

สำคัญมาก: การประกาศ permissions: pull-requests: write ใน workflow เป็นสิ่งจำเป็น — หากไม่ประกาศไว้ คำสั่ง gh pr comment จะถูก GitHub API ปฏิเสธด้วย HTTP 403 ทันที เพราะ token ที่ GitHub Actions สร้างให้อัตโนมัติจะไม่มีสิทธิ์เขียนลง PR โดยดีฟอลต์

gh CLI automation patterns

นอกจากใช้ควบคุม workflow แล้ว gh CLI ยังเป็นเครื่องมือหลักสำหรับ automate การจัดการ PR และ repository settings จาก command line หรือจาก script ได้โดยตรง:

# สร้าง PR จาก branch ปัจจุบัน
gh pr create --title "fix: retry logic" --body "Fixes timeout on flaky tests" --base main

# เช็คสถานะ checks ของ PR ปัจจุบัน (ใช้ตัดสินใจ merge ใน script)
gh pr checks --watch

# เรียก endpoint ที่ porcelain command ไม่รองรับ ผ่าน REST โดยตรง
gh api repos/OWNER/REPO/pages -X POST \
  -f source[branch]=main -f source[path]=/

gh api คือทางออกที่สำคัญเมื่อ gh ไม่มี porcelain subcommand ให้ใช้ตรงๆ — เช่นการตั้งค่า GitHub Pages, การตั้งค่า branch protection rule, หรือการปรับ repo settings ปลีกย่อยอื่นๆ ที่ CLI ไม่ได้ทำ wrapper ไว้ให้ ในกรณีเหล่านี้เราสามารถเรียก REST API ของ GitHub ได้โดยตรงผ่าน gh api พร้อมส่ง field ที่ต้องการด้วย -f

Cost control: กันบิลบาน

เนื่องจาก pipeline ที่ตั้งไว้จะรันซ้ำทุกครั้งที่มี push หรือเปิด PR ใหม่ ถ้าไม่กำกับเรื่อง cost ไว้ตั้งแต่ต้น agent อาจวน loop นานแค่ไหนก็ได้โดยไม่มีการควบคุม ทำให้ค่าใช้จ่ายบานปลายอย่างไม่คาดคิด แฟล็กที่ใช้ควบคุมต้นทุนมีดังนี้:

  • --max-turns N — จำกัดจำนวนรอบ tool-call/think สูงสุดต่อการรันหนึ่งครั้ง
  • --max-budget-usd — ตัดการทำงานทันทีเมื่อค่าใช้จ่ายสะสมถึงเพดานที่ตั้งไว้
  • --fallback-model haiku — เปลี่ยนไปใช้โมเดลที่เล็กกว่าและถูกกว่าโดยอัตโนมัติ เมื่อโควตาของโมเดลหลักหมดหรือ budget ใกล้เต็ม
⚠️ กฎง่ายๆ ที่ไม่มีข้อยกเว้น: ทุก job ที่รัน Claude Code แบบอัตโนมัติซ้ำๆ (ทุก PR, ทุก commit) ต้องมีทั้งเพดานเทิร์นและเพดานเงินเสมอ ไม่ว่าจะดูเหมือนงานเล็กแค่ไหนก็ตาม

Deploy pattern: static site → GitHub Pages

การ deploy static site ขึ้น GitHub Pages แบบตรวจสอบได้จริง ใช้ pattern 3 ขั้นตอนดังนี้:

ขั้นที่ 1 — เปิดใช้งาน Pages ผ่าน API เพราะ porcelain gh ไม่มี subcommand ตรงสำหรับเปิด Pages ต้องเรียกผ่าน gh api โดยตรง:

gh api repos/OWNER/REPO/pages -X POST \
  -f "source[branch]=main" -f "source[path]=/"

ขั้นที่ 2 — Poll สถานะ build จนกว่าจะเป็น built เพราะการ build เป็นกระบวนการ async ไม่ใช่ผลลัพธ์ทันที:

gh api repos/OWNER/REPO/pages | jq -r '.status'

ขั้นที่ 3 — ยืนยันด้วย HTTP request จริง ไม่ใช่เชื่อ API response แต่เพียงอย่างเดียว ต้องยิง request จริงไปตรวจว่าเว็บ live แล้วจริงหรือไม่:

curl -s -o /dev/null -w '%{http_code}\n' https://OWNER.github.io/REPO/

ทำไมต้อง curl เอง — ห้ามเชื่อ API เฉยๆ

เหตุผลที่ต้องมีขั้นตอน verify ด้วย HTTP request จริงเสมอ มีสองส่วนสำคัญ:

API บอกว่าสำเร็จ ≠ เว็บ live แล้ว
การ POST เพื่อเปิดใช้งาน Pages มักตอบกลับด้วย status code 201 หรือ 204 ทันที แต่การ build จริงของหน้าเว็บนั้นเป็นกระบวนการ async ที่ใช้เวลาตั้งแต่หลักสิบวินาทีไปจนถึงหลายนาที การได้รับ response สำเร็จจาก API จึงบอกได้แค่ว่า "คำขอถูกรับแล้ว" ไม่ได้บอกว่า "หน้าเว็บพร้อมให้ดูแล้ว"
สถานะ 404 ในช่วงแรกคือเรื่องปกติ
เพราะ static asset ยังอยู่ระหว่าง build ไม่เสร็จ การเห็น 404 ทันทีหลังเปิด Pages ไม่ได้แปลว่ามีอะไรผิดพลาด แต่ต้อง poll ดู status ก่อนจนกว่าจะเป็น built แล้วจึงค่อย curl ตรวจดูว่าได้ HTTP 200 จริงหรือไม่

วินัยการ verify — กฎเดียวที่คุมทุกอย่าง

⚠️ Never report CI green without checking yourself — log ของ CI สามารถบอกว่า "success" ได้ทั้งที่ผลลัพธ์จริงผิดพลาด เช่น test ที่ flaky ผ่านโดยบังเอิญ, step ที่ถูก skip ไปเงียบๆ โดยไม่มีใครสังเกต, หรือ permission ที่ไม่พอแล้วเกิด silent-fail โดยไม่มี error ปรากฏชัดเจน

หลักการนี้ต้องนำไปใช้ในทุกจุดของ pipeline:

  • ก่อนบอกว่า deploy สำเร็จ → ต้อง curl ตรวจ HTTP code จริงด้วยตัวเองเสมอ ไม่เชื่อแค่ log ของ CI step
  • ก่อนบอกว่า PR review ทำงานถูกต้อง → ต้องเปิด PR ไปดู comment ที่โพสต์จริงบนหน้า GitHub ว่าเนื้อหาถูกต้องและโพสต์สำเร็จจริง
  • ก่อนบอกว่า workflow syntax ถูกต้อง → ต้อง validate ด้วย YAML parser จริง หรือใช้เครื่องมืออย่าง actionlint ไม่ใช่แค่อ่านด้วยตาเปล่าแล้วสรุปเอาเอง

วัดผลว่า pipeline "ดีขึ้นจริง" หรือแค่รู้สึกว่าดีขึ้น (Evals)

ก่อนที่จะแก้ prompt หรือ config ของ headless job ใน pipeline สิ่งที่ต้องเข้าใจก่อนคือ ความแปรปรวนระหว่างการรันสองครั้งของงานเดียวกัน มักใหญ่กว่าผลของการแก้ prompt ที่เพิ่งทำไป การรันงานเดิมซ้ำๆ กันสามารถให้ผลลัพธ์ diff คนละแบบได้ แม้จะไม่ได้แตะ prompt เลยแม้แต่นิดเดียว เพราะลำดับการเรียก tool, ผลลัพธ์ที่ tool คืนกลับมา, และบริบทที่สะสมไปเรื่อยๆ ไม่เหมือนเดิมทุกรอบการรัน

⚠️ กฎข้อ 1: n=1 คือเกร็ดเล่าสู่กันฟัง ไม่ใช่ผลการวัด — ก่อนจะเชื่อว่า "แก้แบบนี้แล้วดีขึ้น" ต้องรันซ้ำอย่างน้อย 5 ครั้งทั้งก่อนและหลังการแก้ไข แล้วดูช่วงของผลลัพธ์ทั้งหมด ไม่ใช่ดูแค่ค่าเดียวจากการรันครั้งเดียว

อ้างอิงเนื้อหาจาก ai-sdlc — M12 Evals (คอร์สแยกของผู้เขียน เจาะลึกเรื่องนี้เต็มโมดูล พร้อม eval harness รันได้จริง)

Golden Task Set — ชุดวัดของทีมตัวเอง

ชุดงานที่ใช้เป็นมาตรฐานวัดผล ต้องคงที่และเป็นตัวแทนงานจริง — การแต่งชุดงานขึ้นมาเองโดยไม่มีที่มา แล้ววัดผลด้วยชุดนั้นจะไม่ได้อะไร เพราะไม่สะท้อนงานจริงที่ทีมเจอ วิธีที่ถูกต้องคือดึงงานจาก backlog หรือ PR ย้อนหลังประมาณ 3 เดือนที่รู้คำตอบที่ถูกต้องอยู่แล้ว มาประกอบเป็นชุดวัด

แต่ละงานในชุดวัดควรประกอบด้วย 5 ส่วนหลัก:

ส่วนประกอบทำไมต้องมี
repo_shaตรึงสถานะ repo ไว้ ณ จุดหนึ่ง — ถ้า repo เคลื่อนไปเรื่อยๆ ผลที่วัดได้ระหว่างช่วงเวลาต่างกันจะเทียบกันไม่ได้
promptเขียนในรูปแบบที่คนจะพิมพ์จริงๆ ไม่ใช่ prompt ที่ขัดเกลาให้สวยงามเกินจริงแล้ว
criteriaต้องเป็นเกณฑ์ที่ตัดสินได้ด้วยสคริปต์อัตโนมัติ ไม่ใช่ต้องอาศัยคนมานั่งดูด้วยสายตาทุกครั้ง
envเวอร์ชันของ dependency และ seed ของฐานข้อมูล — เป็นตัวแปรที่คนมักลืมตรึงไว้บ่อยที่สุด จนทำให้ผลวัดไม่คงเส้นคงวา
tagsประเภทของงานและระดับความยาก เพื่อให้ดูภายหลังได้ว่าการเปลี่ยนแปลงทำให้พังเฉพาะในกลุ่มงานไหน
⚠️ ขนาดที่ใช้ได้จริง: ขั้นต่ำประมาณ 20 งานเริ่มมีประโยชน์ในการให้สัญญาณ ส่วน 40-60 งานคือระดับที่เริ่มเชื่อผลได้จริง โดยควรกระจายชุดงานตามลักษณะงานที่ทีมทำอยู่จริง ไม่ใช่ตามที่คิดเอาเองว่าน่าจะเป็นแบบไหน

งานที่ต้องคัดทิ้งออกจากชุดวัด

ไม่ใช่ทุกงานที่เหมาะเอามาอยู่ในชุดวัด มีสองประเภทที่ควรคัดทิ้งเพราะไม่ช่วยให้เห็นความแตกต่างของผลการทดลอง:

ประเภทที่ไม่ให้สัญญาณ
  • ง่ายเกินไป — ผ่านได้ 100% ทุกครั้งไม่ว่าจะแก้อะไร
  • ยากเกินไป — ตกทุกครั้งเหมือนกันหมดไม่ว่าจะแก้อะไร
ประเภทที่วัดไม่ได้จริง
  • ไม่ deterministic — ผลลัพธ์ขึ้นอยู่กับ network, เวลาปัจจุบัน หรือ service ภายนอกที่ควบคุมไม่ได้
  • อยู่ในข้อมูลฝึกของโมเดลอยู่แล้วแน่ๆ — เช่น bug ที่โด่งดังมากจนมีคำตอบเต็มอินเทอร์เน็ตอยู่แล้ว ทำให้โมเดลตอบถูกได้โดยไม่เกี่ยวกับความสามารถจริงของ pipeline ที่กำลังทดสอบ

สรุปแล้วให้เก็บไว้เฉพาะงานที่อยู่ตรงกลาง — งานที่ผลลัพธ์ไม่แน่นอน เพราะเป็นงานเดียวที่บอกได้จริงว่าการเปลี่ยนแปลงที่ทำมีผลจริงหรือไม่ (คะแนนเต็มตลอดเวลา กับคะแนนศูนย์ตลอดเวลา มีค่าเท่ากันในแง่ของการเป็นสัญญาณ นั่นคือไม่มีค่าเลย)

เกณฑ์ 4 แบบ: Deterministic มาก่อนเสมอ

ข้อผิดพลาดที่พบบ่อยที่สุดในการออกแบบ eval คือการกระโดดไปใช้ LLM-as-judge ทันที ทั้งที่เกณฑ์แบบสคริปต์ธรรมดาสามารถตอบคำถามได้อยู่แล้ว หลักการที่ถูกต้องคือใช้ judge เฉพาะเมื่อเกณฑ์ในระดับที่ถูกกว่าตอบไม่ได้จริงๆ เท่านั้น เกณฑ์ทั้ง 4 แบบเรียงจากถูกที่สุดไปแพงที่สุดดังนี้:

เกณฑ์ (เรียงถูก→แพง)ใช้เมื่อไหร่
cmdรัน typecheck/test จริง — ถูกที่สุดและเชื่อถือได้สมบูรณ์เพราะเป็นผลจากการรันจริง
before_afterตรวจว่าแดงก่อนแล้วเขียวหลังการแก้ไข — สัญญาณแรงที่สุดเมื่อเทียบกับต้นทุนที่จ่าย
diffใช้ allow/deny list และ max_lines — ตรวจสอบขอบเขต (scope) ของการเปลี่ยนแปลงที่เกิดขึ้น
budgetใช้ max_usd/max_wall_sec/max_turns — ยอมรับได้ก็ต่อเมื่อสามแบบข้างต้นไม่เพียงพอต่อการตัดสิน

ทำไมโมดูลนี้เชื่อมกับ Evals

Module 09 สอนวิธี "รัน Claude Code ใน pipeline อัตโนมัติ" แต่ไม่เคยตอบคำถามที่สำคัญกว่าคือ "pipeline นั้นทำงานดีขึ้นจริงไหมเมื่อเราแก้ prompt หรือ config" — Evals คือชิ้นส่วนที่ขาดหายไปตรงนี้พอดี

เชื่อมกับหลักการที่มีอยู่แล้วในโมดูลนี้
"Never report CI green without checking yourself" ใช้กับการทำ eval ได้เหมือนกันทุกประการ — ผลการรันครั้งเดียวที่ดูดีขึ้นอาจเป็นแค่ noise ธรรมดา ไม่ใช่ improvement ที่แท้จริง ต้อง verify ด้วยการรันซ้ำหลายครั้งก่อนสรุป เหมือนกับที่ต้อง curl ตรวจ HTTP code จริงก่อนที่จะบอกว่า deploy สำเร็จแล้ว

เรียนลึกเรื่อง eval harness ที่รันได้จริง (Bun runner, task template, deterministic-first grading) ต่อได้ที่ ai-sdlc M12 · Evals

สรุป Pattern การทำ CI/CD Automation

สรุปทุกขั้นตอนของโมดูลนี้เป็นตารางเดียว:

ขั้นตอนเครื่องมือ
1. รัน Claude Code แบบ headless--bare -p ... --allowedTools --max-turns
2. ควบคุมต้นทุน--max-budget-usd, --fallback-model
3. Trigger จาก event จริงon: pull_request
4. โพสต์ผลกลับgh pr comment
5. Deploy + verify จริงgh api + poll + curl
6. วัดว่า pipeline ดีขึ้นจริงGolden task set + deterministic criteria + รันซ้ำ 5 ครั้ง
