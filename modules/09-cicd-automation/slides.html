CI/CD & Automation Integration

รัน Claude Code แบบ headless ใน pipeline, gh CLI automation, deploy แบบตรวจสอบได้จริง

ทำไม CI ต้องรัน Claude Code แบบ headless

  • Interactive REPL ใช้กับ pipeline อัตโนมัติไม่ได้ — ไม่มีคนกด Enter ตอบ prompt
  • Headless mode (--bare -p) รันครั้งเดียว รับ input → output แล้วจบ เหมาะกับ CI runner
  • ใช้ทำ automated PR review, changelog generation, test-failure triage ได้โดยไม่ต้องมี human ในลูป
  • ข้อควรระวัง: headless = ไม่มีใครยืนยัน permission กลางทาง ต้อง lock --allowedTools ให้แคบ

Headless flags ที่ต้องรู้

Flagทำอะไร
--bareปิด UI แบบ interactive, ข้าม OAuth login flow
-p "..."ส่ง prompt ตรงเข้าไปรันครั้งเดียว
--allowedTools 'Read,Bash'จำกัด tool ที่ agent เรียกได้ในรอบนี้
--max-turns Nจำกัดจำนวนรอบคิด/เรียก tool กัน loop ไม่จบ

Auth ต้องมาจาก env

Bare mode ข้าม OAuth device flow ดังนั้นต้องมี ANTHROPIC_API_KEY อยู่ใน environment ของ runner — ปกติ set ผ่าน GitHub Secrets

ตัวอย่างคำสั่ง headless

export ANTHROPIC_API_KEY="${{ secrets.ANTHROPIC_API_KEY }}"

claude --bare \
  -p "Review the diff in this PR for bugs, security issues, and style. Output findings as a markdown list." \
  --allowedTools 'Read,Bash' \
  --max-turns 8 \
  --max-budget-usd 0.50 \
  --fallback-model claude-3-5-haiku-20241022 \
  > review-output.md

ผลลัพธ์ที่ได้เป็น text ธรรมดา → เอาไป pipe ต่อเข้า step อื่นได้ เช่น comment กลับเข้า PR

GitHub Actions workflow: auto-review PR

name: claude-review
on:
  pull_request:
    types: [opened, synchronize]

jobs:
  review:
    runs-on: ubuntu-latest
    permissions:
      pull-requests: write
      contents: read
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Install Claude Code
        run: npm install -g @anthropic-ai/claude-code

      - name: Run headless review
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          git diff origin/${{ github.base_ref }}...HEAD > pr.diff
          claude --bare -p "Review pr.diff for bugs and risks. Be concise." \
            --allowedTools 'Read,Bash' --max-turns 6 > review.md

      - name: Post comment to PR
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: gh pr comment ${{ github.event.pull_request.number }} --body-file review.md

Trigger event: อ่านให้ถูกก่อนเขียน job

pull_request

types: [opened, synchronize] — รันตอนเปิด PR ใหม่ และทุกครั้งที่ push commit เพิ่มเข้า branch นั้น

Context ที่ใช้บ่อย

github.event.pull_request.number, github.base_ref, github.head_ref — ใช้ระบุ PR และ diff range

permissions: pull-requests: write จำเป็น — ไม่งั้น gh pr comment จะถูก GitHub API ปฏิเสธด้วย 403

gh CLI automation patterns

# สร้าง PR จาก branch ปัจจุบัน
gh pr create --title "fix: retry logic" --body "Fixes timeout on flaky tests" --base main

# เช็คสถานะ checks ของ PR ปัจจุบัน (ใช้ตัดสินใจ merge ใน script)
gh pr checks --watch

# เรียก endpoint ที่ porcelain command ไม่รองรับ ผ่าน REST โดยตรง
gh api repos/OWNER/REPO/pages -X POST \
  -f source[branch]=main -f source[path]=/

gh api คือทางออกเมื่อ gh ไม่มี subcommand ให้ — เช่นการตั้งค่า GitHub Pages, branch protection, repo settings ปลีกย่อย

Cost control: กันบิลบาน

  • Pipeline รันซ้ำทุก push/PR — ถ้าไม่กำกับ cost, agent วน loop นานเท่าไหร่ก็ได้
  • --max-turns N — จำกัดจำนวนรอบ tool-call/think ต่อการรันหนึ่งครั้ง
  • --max-budget-usd — ตัดการทำงานทันทีเมื่อค่าใช้จ่ายถึงเพดานที่ตั้ง
  • --fallback-model haiku — เปลี่ยนไปใช้โมเดลเล็ก/ถูกกว่าอัตโนมัติเมื่อโควตาโมเดลหลักหมดหรือ budget ใกล้เต็ม

กฎง่ายๆ

ทุก job ที่รัน Claude Code แบบอัตโนมัติซ้ำๆ (ทุก PR, ทุก commit) ต้องมีทั้งเพดานเทิร์นและเพดานเงินเสมอ — ไม่มีข้อยกเว้น

Deploy pattern: static site → GitHub Pages

  1. เปิดใช้งาน Pages ผ่าน API เพราะ porcelain gh ไม่มี subcommand ตรง: 
    gh api repos/OWNER/REPO/pages -X POST \
  -f "source[branch]=main" -f "source[path]=/"
  2. Poll สถานะ build จนกว่าจะเป็น built: 
    gh api repos/OWNER/REPO/pages | jq -r '.status'
  3. ยืนยันด้วย HTTP request จริง — ไม่ใช่ เชื่อ API response อย่างเดียว: 
    curl -s -o /dev/null -w '%{http_code}\n' https://OWNER.github.io/REPO/

ทำไมต้อง curl เอง — ห้ามเชื่อ API เฉยๆ

API บอกว่าสำเร็จ ≠ เว็บ live แล้ว

POST เปิด Pages มักตอบ 201/204 ทันที แต่ build จริงเป็น async — ใช้เวลาหลักสิบวินาทีถึงหลายนาที

สถานะ 404 ช่วงแรกคือเรื่องปกติ

เพราะ static asset ยัง build ไม่เสร็จ ต้อง poll status ก่อน แล้วค่อย curl ตรวจ HTTP 200 จริง

วินัยการ verify — กฎเดียวที่คุมทุกอย่าง

Never report CI green without checking yourself

Log ของ CI บอกว่า "success" ได้ทั้งที่ผลลัพธ์จริงผิด (เช่น test flaky, step skip เงียบๆ, permission ไม่พอแล้ว silent-fail)

  • ก่อนบอกว่า deploy สำเร็จ → curl ตรวจ HTTP code จริงด้วยตัวเอง
  • ก่อนบอกว่า PR review ทำงานถูก → เปิด PR ไปดู comment ที่โพสต์จริง
  • ก่อนบอกว่า workflow syntax ถูก → validate ด้วย YAML parser หรือ actionlint จริงๆ ไม่ใช่อ่านตาเปล่า

วัดผลว่า pipeline "ดีขึ้นจริง" หรือแค่รู้สึกว่าดีขึ้น

ก่อนแก้ prompt/config ของ headless job ใน pipeline ต้องรู้ก่อนว่า ความแปรปรวนระหว่างการรันสองครั้งของงานเดียวกัน มักใหญ่กว่าผลของการแก้ prompt ที่เพิ่งทำ — รันงานเดิมซ้ำ ๆ ได้ diff คนละแบบได้ แม้ไม่แตะ prompt เลย เพราะลำดับ tool-call, ผลลัพธ์ tool, และบริบทที่สะสมไม่เหมือนเดิมทุกรอบ

กฎข้อ 1: n=1 คือเกร็ดเล่าสู่กันฟัง ไม่ใช่ผลการวัด — ก่อนเชื่อว่า "แก้แบบนี้แล้วดีขึ้น" ต้องรันซ้ำอย่างน้อย 5 ครั้งทั้งก่อน/หลัง แล้วดูช่วงของผล ไม่ใช่ค่าเดียว

อ้างอิงเนื้อหาจาก ai-sdlc — M12 Evals (คอร์สแยกของผู้เขียน เจาะลึกเรื่องนี้เต็มโมดูล พร้อม eval harness รันได้จริง)

Golden Task Set — ชุดวัดของทีมตัวเอง

ชุดงานต้องคงที่และเป็นตัวแทนงานจริง — แต่งขึ้นเองแล้ววัดไม่ได้อะไร ต้องดึงจาก backlog/PR ย้อนหลัง 3 เดือนที่รู้คำตอบแล้ว

ส่วนประกอบทำไมต้องมี
repo_shaตรึงสถานะ repo ไว้ — ถ้า repo เคลื่อน ผลเทียบข้ามเวลาไม่ได้
promptเขียนแบบที่จะพิมพ์จริง ไม่ใช่แบบขัดเกลาแล้ว
criteriaต้องตัดสินได้ด้วยสคริปต์ ไม่ใช่ด้วยสายตา
envเวอร์ชัน dependency, seed ของ DB — ตัวแปรที่คนลืมตรึงบ่อยที่สุด
tagsประเภทงาน + ระดับความยาก เพื่อดูว่าพังเฉพาะกลุ่มไหน
ขนาดที่ใช้ได้จริง: ขั้นต่ำ ~20 งานเริ่มมีประโยชน์, ~40-60 งานเริ่มเชื่อผลได้จริง — กระจายตามงานที่ทีมทำจริง ไม่ใช่ตามที่คิดว่าน่าจะเป็น

งานที่ต้องคัดทิ้งออกจากชุดวัด

ไม่ให้สัญญาณ

  • ง่ายเกิน — ผ่าน 100% ทุกครั้ง
  • ยากเกิน — ตกทุกครั้งเหมือนกันหมด

วัดไม่ได้จริง

  • ไม่ deterministic — พึ่ง network/เวลาปัจจุบัน/service ภายนอก
  • อยู่ในข้อมูลฝึกแน่ๆ — เช่น bug ดังที่มีคำตอบเต็มอินเทอร์เน็ต

เก็บเฉพาะงานตรงกลาง — ที่ผลไม่แน่นอน — เพราะเป็นงานเดียวที่บอกได้ว่า การเปลี่ยนแปลงมีผลจริงไหม (คะแนนเต็มตลอด กับศูนย์ตลอด มีค่าเท่ากันคือไม่มีค่า)

เกณฑ์ 4 แบบ: Deterministic มาก่อนเสมอ

ความผิดพลาดที่พบบ่อยที่สุด: กระโดดไปใช้ LLM-as-judge ทันที ทั้งที่เกณฑ์แบบสคริปต์ตอบได้อยู่แล้ว — ใช้ judge เฉพาะเมื่อเกณฑ์ชั้นล่างตอบไม่ได้จริงๆ

เกณฑ์ (เรียงถูก→แพง)ใช้เมื่อไหร่
cmdtypecheck/test รันจริง — ถูกที่สุด เชื่อได้สมบูรณ์
before_afterแดงก่อน เขียวหลัง — สัญญาณแรงที่สุดต่อบาทที่จ่าย
diffallow/deny/max_lines — ตรวจ scope ของการเปลี่ยนแปลง
budgetmax_usd/max_wall_sec/max_turns — ยอมรับได้ก็ต่อเมื่อ 3 แบบบนไม่พอ

ทำไมโมดูลนี้เชื่อมกับ Evals

Module 09 สอนวิธี "รัน Claude Code ใน pipeline อัตโนมัติ" แต่ไม่เคยตอบว่า "pipeline นั้นทำงานดีขึ้นจริงไหมเมื่อแก้ prompt/config" — Evals คือชิ้นส่วนที่ขาด

เชื่อมกับหลักการที่มีอยู่แล้วในโมดูลนี้

"Never report CI green without checking yourself" ใช้กับ eval เหมือนกัน — ผลรันครั้งเดียวที่ดูดีอาจเป็นแค่ noise ไม่ใช่ improvement จริง ต้อง verify ด้วยการรันซ้ำ เหมือนที่ต้อง curl ตรวจ HTTP code จริงก่อนบอกว่า deploy สำเร็จ

เรียนลึกเรื่อง eval harness ที่รันได้จริง (Bun runner, task template, deterministic-first grading) ต่อได้ที่ ai-sdlc M12 · Evals

สรุป Pattern การทำ CI/CD Automation

ขั้นตอนเครื่องมือ
1. รัน Claude Code แบบ headless--bare -p ... --allowedTools --max-turns
2. ควบคุมต้นทุน--max-budget-usd, --fallback-model
3. Trigger จาก event จริงon: pull_request
4. โพสต์ผลกลับgh pr comment
5. Deploy + verify จริงgh api + poll + curl
6. วัดว่า pipeline ดีขึ้นจริงGolden task set + deterministic criteria + รันซ้ำ 5 ครั้ง
