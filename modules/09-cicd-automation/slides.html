⚠️ Headless = ไม่มีใครยืนยัน permission กลางทาง → ต้อง lock --allowedTools ให้แคบ

Headless flags ที่ต้องรู้

Flagทำอะไร
--bareปิด UI interactive, ข้าม OAuth login flow
-p "..."ส่ง prompt ตรง รันครั้งเดียว
--allowedTools 'Read,Bash'จำกัด tool ที่เรียกได้
--max-turns Nกัน loop ไม่จบ

🔑 Auth ต้องมาจาก env

Bare mode ข้าม OAuth device flow → ต้องมี ANTHROPIC_API_KEY ใน environment (GitHub Secrets)

ตัวอย่างคำสั่ง headless

export ANTHROPIC_API_KEY="${{ secrets.ANTHROPIC_API_KEY }}"

claude --bare \
  -p "Review the diff in this PR for bugs, security issues, and style. Output findings as a markdown list." \
  --allowedTools 'Read,Bash' \
  --max-turns 8 \
  --max-budget-usd 0.50 \
  --fallback-model claude-3-5-haiku-20241022 \
  > review-output.md

📤 output = plain text → pipe ต่อเข้า step อื่นได้ทันที

GitHub Actions: auto-review PR

name: claude-review
on:
  pull_request:
    types: [opened, synchronize]

jobs:
  review:
    runs-on: ubuntu-latest
    permissions:
      pull-requests: write
      contents: read
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Install Claude Code
        run: npm install -g @anthropic-ai/claude-code

      - name: Run headless review
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          git diff origin/${{ github.base_ref }}...HEAD > pr.diff
          claude --bare -p "Review pr.diff for bugs and risks. Be concise." \
            --allowedTools 'Read,Bash' --max-turns 6 > review.md

      - name: Post comment to PR
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: gh pr comment ${{ github.event.pull_request.number }} --body-file review.md

gh CLI automation patterns

# สร้าง PR จาก branch ปัจจุบัน
gh pr create --title "fix: retry logic" --body "Fixes timeout on flaky tests" --base main

# เช็คสถานะ checks ของ PR ปัจจุบัน (ใช้ตัดสินใจ merge ใน script)
gh pr checks --watch

# เรียก endpoint ที่ porcelain command ไม่รองรับ ผ่าน REST โดยตรง
gh api repos/OWNER/REPO/pages -X POST \
  -f source[branch]=main -f source[path]=/

gh api = ทางออกเมื่อ gh ไม่มี subcommand ให้ (Pages, branch protection, repo settings ปลีกย่อย)

Deploy pattern: static site → GitHub Pages

1️⃣Enable Pages ผ่าน API
↓
2️⃣Poll status จนเป็น built
↓
3️⃣curl verify HTTP 200 จริง
# 1. Enable
gh api repos/OWNER/REPO/pages -X POST \
  -f "source[branch]=main" -f "source[path]=/"

# 2. Poll
gh api repos/OWNER/REPO/pages | jq -r '.status'

# 3. Verify
curl -s -o /dev/null -w '%{http_code}\n' https://OWNER.github.io/REPO/

ทำไมต้อง curl เอง — ห้ามเชื่อ API เฉยๆ

🟡 API ตอบ 201/204แค่ "รับคำขอแล้ว"
≠
🟢 เว็บ live จริงต้อง curl ตรวจ 200

Build เป็น async — 404 ช่วงแรกเป็นเรื่องปกติ ต้อง poll status ก่อนแล้วค่อย curl

วินัยการ verify — กฎเดียวที่คุมทุกอย่าง

Never report CI green without checking yourself. Log "success" ได้ทั้งที่ผลจริงผิด (test flaky, step skip เงียบๆ, permission ไม่พอแล้ว silent-fail)

วัดผลว่า pipeline "ดีขึ้นจริง" หรือแค่รู้สึกว่าดีขึ้น

ความแปรปรวนระหว่างการรัน 2 ครั้งของงานเดียวกัน มักใหญ่กว่าผลของการแก้ prompt

กฎข้อ 1: n=1 คือเกร็ดเล่าสู่กันฟัง ไม่ใช่ผลการวัด — รันซ้ำอย่างน้อย 5 ครั้งทั้งก่อน/หลัง แล้วดูช่วงของผล ไม่ใช่ค่าเดียว

อ้างอิงเนื้อหาจาก ai-sdlc — M12 Evals (คอร์สแยกของผู้เขียน เจาะลึกเรื่องนี้เต็มโมดูล พร้อม eval harness รันได้จริง)

Golden Task Set — ชุดวัดของทีมตัวเอง

ดึงจาก backlog/PR ย้อนหลัง 3 เดือนที่รู้คำตอบแล้ว — แต่งขึ้นเองวัดไม่ได้อะไร

ส่วนประกอบทำไมต้องมี
repo_shaตรึงสถานะ repo — ถ้า repo เคลื่อน เทียบข้ามเวลาไม่ได้
promptเขียนแบบที่จะพิมพ์จริง ไม่ใช่แบบขัดเกลาแล้ว
criteriaตัดสินได้ด้วยสคริปต์ ไม่ใช่ด้วยสายตา
envเวอร์ชัน dependency, seed ของ DB
tagsประเภทงาน + ระดับความยาก
ขนาดที่ใช้ได้จริง: ขั้นต่ำ ~20 งาน, ~40-60 งานเริ่มเชื่อผลได้จริง

งานที่ต้องคัดทิ้งออกจากชุดวัด

❌ ไม่ให้สัญญาณง่ายเกิน (ผ่าน 100%) / ยากเกิน (ตกตลอด)
VS
⚠️ วัดไม่ได้จริงไม่ deterministic / อยู่ใน training data

เก็บเฉพาะงานตรงกลาง — คะแนนเต็มตลอด กับศูนย์ตลอด มีค่าเท่ากันคือไม่มีค่า

เกณฑ์ 4 แบบ: Deterministic มาก่อนเสมอ

อย่ากระโดดไปใช้ LLM-as-judge ทันที — ใช้เฉพาะเมื่อเกณฑ์ชั้นล่างตอบไม่ได้จริงๆ

เกณฑ์ (ถูก→แพง)ใช้เมื่อไหร่
cmdtypecheck/test รันจริง — ถูกที่สุด เชื่อได้สมบูรณ์
before_afterแดงก่อน เขียวหลัง — สัญญาณแรงที่สุดต่อบาท
diffallow/deny/max_lines — ตรวจ scope
budgetmax_usd/max_wall_sec/max_turns — เมื่อ 3 แบบบนไม่พอ

สรุป Pattern การทำ CI/CD Automation

ขั้นตอนเครื่องมือ
1. รัน Claude Code แบบ headless--bare -p ... --allowedTools --max-turns
2. ควบคุมต้นทุน--max-budget-usd, --fallback-model
3. Trigger จาก event จริงon: pull_request
4. โพสต์ผลกลับgh pr comment
5. Deploy + verify จริงgh api + poll + curl
6. วัดว่า pipeline ดีขึ้นจริงGolden task set + deterministic criteria + รันซ้ำ 5 ครั้ง
