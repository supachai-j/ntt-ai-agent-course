CI/CD & Automation Integration

เขียน GitHub Actions workflow ที่รัน Claude Code แบบ headless review PR จริง แล้วฝึก deploy static site ขึ้น GitHub Pages ผ่าน gh api พร้อม verify HTTP 200 ด้วยตัวเอง — ไม่เชื่อ CI log อย่างเดียว

⏱ ~70-90 นาที 🖥 ต้องมี gh CLI + git + repo บน GitHub 🔑 ต้องมี ANTHROPIC_API_KEY 📦 Module 09 / 10

Prerequisite

  • ติดตั้ง gh CLI และรัน gh auth login แล้ว (เช็คด้วย gh auth status)
  • มี repository บน GitHub ที่ push ได้ (ใช้ repo ทดสอบใหม่ก็ได้ เพื่อไม่กระทบของจริง)
  • ตั้ง secret ANTHROPIC_API_KEY ใน repo settings → Secrets and variables → Actions
  • มี Python 3 หรือ pip install pyyaml สำหรับ validate YAML syntax (หรือใช้ actionlint ถ้ามี)
  • เข้าใจพื้นฐาน git branch/PR workflow จาก Module 03-04 มาแล้ว

Objectives

  • เขียนและ validate syntax ของ GitHub Actions workflow ที่รัน Claude Code แบบ headless
  • เข้าใจ flag คุมต้นทุนและ tool permission ของ headless mode
  • เปิดใช้งาน GitHub Pages ผ่าน gh api แทน porcelain command
  • Poll สถานะ build และ verify ด้วย curl จริงก่อนประกาศว่า deploy สำเร็จ
  • ฝึกวินัย "never trust green CI without checking yourself"
  • ฝึกความเข้าใจพื้นฐาน eval — ทำไมการเทียบ prompt ด้วยการรันครั้งเดียวถึงเชื่อไม่ได้

1เตรียม repo และ branch ทดสอบ

สร้างหรือใช้ repo ที่มีอยู่แล้ว สร้าง branch แยกไว้ทดลอง จะได้ไม่กระทบ main โดยตรง

cd /home/ubuntu
mkdir -p cicd-lab-demo && cd cicd-lab-demo
git init
git checkout -b setup-cicd
echo "# CI/CD Lab Demo" > README.md
git add README.md
git commit -m "init: cicd lab demo"

# สร้าง repo บน GitHub ผ่าน gh (private ไว้ก่อน)
gh repo create cicd-lab-demo --private --source=. --remote=origin --push
Verify: เช็คว่า repo ถูกสร้างจริงบน GitHub 
gh repo view --web=false --json url,visibility
ต้องเห็น url ชี้ไปที่ repo ของคุณ และ visibility: PRIVATE

2เขียน workflow file สำหรับ headless PR review

สร้างโฟลเดอร์ .github/workflows/ แล้วเขียนไฟล์ claude-review.yml ที่รัน Claude Code แบบ headless เมื่อมี PR event

mkdir -p .github/workflows
cat > .github/workflows/claude-review.yml << 'EOF'
name: claude-review
on:
  pull_request:
    types: [opened, synchronize]

jobs:
  review:
    runs-on: ubuntu-latest
    permissions:
      pull-requests: write
      contents: read
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Install Claude Code
        run: npm install -g @anthropic-ai/claude-code

      - name: Generate PR diff
        run: |
          git fetch origin ${{ github.base_ref }} --depth=1
          git diff origin/${{ github.base_ref }}...HEAD > pr.diff

      - name: Run headless review
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          claude --bare \
            -p "Review the changes in pr.diff for bugs, security issues, and style problems. Output a concise markdown list of findings." \
            --allowedTools 'Read,Bash' \
            --max-turns 8 \
            --max-budget-usd 0.50 \
            --fallback-model claude-3-5-haiku-20241022 \
            > review.md

      - name: Post comment to PR
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: gh pr comment ${{ github.event.pull_request.number }} --body-file review.md
EOF
Verify: ไฟล์ต้องมีอยู่จริงและมีเนื้อหาครบ 
cat .github/workflows/claude-review.yml | wc -l
# ควรได้ >= 30 บรรทัด

3Validate YAML syntax จริง — ห้ามอ่านตาเปล่าแล้วเชื่อ

Syntax error ใน workflow file จะทำให้ GitHub เงียบๆ ไม่รัน job เลย (บางกรณี fail แบบไม่มี log ชัดเจน) ต้อง parse จริงก่อน push

python3 - << 'EOF'
import yaml, sys
with open(".github/workflows/claude-review.yml") as f:
    doc = yaml.safe_load(f)
print("YAML parses OK")
print("Job keys:", list(doc["jobs"].keys()))
assert "review" in doc["jobs"], "missing review job"
assert doc["jobs"]["review"]["permissions"]["pull-requests"] == "write"
print("permissions check OK")
EOF
Verify: ต้องเห็น YAML parses OK และ permissions check OK พิมพ์ออกมาจริง ถ้า python บ่น traceback แปลว่า syntax ผิด ต้องแก้ก่อนไปต่อ
ถ้าไม่มี pyyaml: รัน pip install --user pyyaml หรือใช้ actionlint .github/workflows/claude-review.yml ถ้าติดตั้งไว้แล้ว — อย่าข้าม step นี้เด็ดขาด เพราะ indentation ผิดใน YAML คือสาเหตุ workflow พังอันดับหนึ่ง

6เปิดใช้งาน GitHub Pages ผ่าน gh api

gh porcelain ไม่มี subcommand สำหรับตั้งค่า Pages โดยตรง ต้องเรียก REST API ผ่าน gh api

OWNER=$(gh repo view --json owner -q .owner.login)
REPO=$(gh repo view --json name -q .name)

gh api repos/$OWNER/$REPO/pages -X POST \
  -f "source[branch]=main" -f "source[path]=/site" \
  || echo "อาจจะมี Pages เปิดอยู่แล้ว ลองใช้ PUT แทน POST"
Verify: เรียก GET ทันทีเพื่อดูสถานะที่ registered 
gh api repos/$OWNER/$REPO/pages
ต้องเห็น field html_url และ status ในผลลัพธ์ (status ตอนนี้อาจยังเป็น null หรือ building)

7Poll สถานะ build จนกว่าจะ built

การเปิด Pages เป็น async — API ตอบกลับ success ทันทีไม่ได้แปลว่าเว็บ build เสร็จแล้ว ต้อง poll

for i in $(seq 1 20); do
  STATUS=$(gh api repos/$OWNER/$REPO/pages -q .status 2>/dev/null)
  echo "attempt $i: status=$STATUS"
  if [ "$STATUS" = "built" ]; then
    echo "Pages build complete"
    break
  fi
  sleep 15
done
Verify: loop ต้องพิมพ์ status=built ก่อนจบ ถ้าวนครบ 20 รอบ (~5 นาที) แล้วยังไม่ built ให้เช็คว่า path /site ถูกต้องหรือ branch ที่ set ตรงกับที่ push จริงหรือไม่

8Verify ด้วย curl จริง — ห้ามเชื่อ API response อย่างเดียว

แม้ status จะเป็น built แล้ว ก็ต้องยิง HTTP request จริงเพื่อยืนยันว่าหน้าเว็บเปิดได้จริง

PAGES_URL=$(gh api repos/$OWNER/$REPO/pages -q .html_url)
echo "checking: $PAGES_URL"

HTTP_CODE=$(curl -s -o /dev/null -w '%{http_code}' "$PAGES_URL")
echo "HTTP status: $HTTP_CODE"

if [ "$HTTP_CODE" = "200" ]; then
  echo "LIVE: $PAGES_URL"
else
  echo "NOT LIVE YET (got $HTTP_CODE) — build อาจยังไม่เสร็จ propagate, ลองใหม่ใน 30-60 วินาที"
fi
ห้ามทำ: ห้ามประกาศว่า "deploy สำเร็จ" จาก gh api ตอบ 201/204 อย่างเดียว ต้องเห็น HTTP status: 200 จาก curl จริงก่อนถึงจะยืนยันได้ว่า live
Verify: รัน curl command ซ้ำจนกว่าจะได้ 200 จริง — เก็บ output เป็นหลักฐานว่า verify แล้ว ไม่ใช่แค่สันนิษฐาน

9Mini Eval: วัดว่า prompt เวอร์ชันไหน "ดีกว่า" จริง

สร้าง mini eval script ง่ายๆ เทียบ prompt 2 แบบสำหรับงาน headless review เดียวกัน — รันซ้ำหลายรอบแล้วดูช่วงของผล ไม่ใช่รันครั้งเดียวแล้วสรุป

mkdir -p ~/eval-mini && cd ~/eval-mini

cat > run_eval.sh << 'EOF'
#!/usr/bin/env bash
# Mini eval: รัน prompt เดิมซ้ำ N ครั้ง วัด num_turns เป็น deterministic proxy metric
PROMPT="$1"
LABEL="$2"
N="${3:-5}"

for i in $(seq 1 "$N"); do
  RESULT=$(claude --bare -p "$PROMPT" --max-turns 5 --output-format json 2>/dev/null)
  TURNS=$(echo "$RESULT" | python3 -c "import json,sys; print(json.load(sys.stdin).get('num_turns','NA'))")
  echo "$LABEL run $i: num_turns=$TURNS"
done
EOF
chmod +x run_eval.sh

./run_eval.sh "Explain what this repo does in one sentence" "prompt-A" 5
./run_eval.sh "In one sentence, explain the purpose of this repository" "prompt-B" 5
Verify: เก็บผลทั้ง 10 บรรทัด (5 รอบ x 2 prompt) — ดูว่าช่วงของ num_turns ระหว่าง prompt-A กับ prompt-B ทับกันไหม ถ้าทับกันเกือบทั้งหมด แปลว่าจากข้อมูลที่มี ยังสรุปไม่ได้ว่า prompt ไหนดีกว่าจริง — นี่คือกับดักที่พบบ่อยที่สุด (n=1 comparison)
ทำไมต้องรันซ้ำ 5 ครั้งไม่ใช่ 1 ครั้ง: agent loop ไม่เดินเส้นทางเดียวทุกครั้ง — ลำดับ tool-call, ผลลัพธ์ tool, และบริบทสะสมต่างกันได้แม้ prompt เหมือนเดิมทุกตัวอักษร รันครั้งเดียวแล้วสรุปว่า "prompt นี้ดีกว่า" คือการอ่าน noise แล้วเรียกว่า improvement

Mini exercise นี้สาธิตหลักการเท่านั้น ถ้าต้องการ eval harness เต็มรูปแบบ (golden task set, deterministic-first criteria, baseline tracking) ดูต่อได้ที่ ai-sdlc M12 · Evals

Troubleshoot: gh api ตอบสำเร็จแต่ curl ได้ 404

นี่คือพฤติกรรมปกติในช่วงแรกหลังเปิด Pages — POST/GET ต่อ /pages endpoint ยืนยันแค่ว่า "การตั้งค่า" ถูกบันทึกแล้ว แต่กระบวนการ build ไฟล์จริงเป็น asynchronous job ที่รันแยกต่างหาก มักใช้เวลา 30 วินาที ถึง 2-3 นาที

  • เช็ค status field จาก gh api repos/OWNER/REPO/pages ต้องเป็น built ก่อน ไม่ใช่ null หรือ building
  • ถ้า poll เกิน 5 นาทีแล้วยัง building ตลอด ให้เช็ค Actions tab ของ repo — Pages ใช้ internal workflow ชื่อ "pages build and deployment" ดู log ตรงนั้นว่า build fail หรือเปล่า
  • ถ้า path ที่ตั้งใน source[path] ไม่มี index.html อยู่จริง Pages จะ build "สำเร็จ" แต่ได้หน้า 404 ของ GitHub เอง — เช็ค path ให้ตรงกับที่ push จริง
  • บาง org/repo ต้องเปิด Pages ผ่าน Settings UI ครั้งแรกก่อน API ถึงจะยอมให้ POST ได้ (permission ของ token ไม่พอ) — เช็ค error message จาก gh api ให้ดี ไม่ใช่แค่ดู exit code
Troubleshoot: claude --bare รันแล้ว error "authentication failed"

Bare mode ข้าม OAuth device flow ไปเลย ดังนั้นถ้าไม่มี ANTHROPIC_API_KEY อยู่ใน environment มันจะ fail ทันที ไม่ fallback ไป login flow ให้

  • เช็คว่า secret ชื่อตรงกับที่ workflow อ้างถึง (ANTHROPIC_API_KEY) ใน repo Settings → Secrets and variables → Actions
  • ใน workflow ต้องมี env: ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }} อยู่ที่ step ที่เรียก claude จริงๆ ไม่ใช่แค่ประกาศไว้ที่ job level เฉยๆ แล้วลืม pass ต่อ
  • ทดสอบ local ก่อน push: export ANTHROPIC_API_KEY=sk-ant-... && claude --bare -p "hello" --max-turns 1

สรุป & ต่อยอด

ตอนนี้คุณมี pipeline ที่รัน Claude Code แบบ headless เพื่อ review PR อัตโนมัติ พร้อม cost guard (--max-turns, --max-budget-usd, --fallback-model) และรู้วิธี deploy static site ขึ้น GitHub Pages ผ่าน gh api แบบที่ verify ผลจริงทุกขั้นตอนแทนการเชื่อ response เฉยๆ

  • ลองเปิด PR จริงในโปรเจกต์ทดสอบ แล้วดู comment ที่ claude-review workflow โพสต์กลับมา
  • เพิ่ม job แยกสำหรับรัน test suite ก่อนค่อยเรียก Claude Code review เพื่อประหยัด budget เมื่อ test พังอยู่แล้ว
  • ลองตั้ง --fallback-model เป็นโมเดลอื่นแล้วเทียบคุณภาพ review กับต้นทุนที่ประหยัดได้
  • ขยาย mini eval script ของ step 9 ให้เก็บผลลง CSV แล้วลองเทียบ prompt 3-4 แบบพร้อมกัน
  • Module 10 (Capstone) จะรวม pattern จาก Module 01-09 ทั้งหมดเข้าเป็นโปรเจกต์เดียว รวมถึง pipeline นี้ด้วย
