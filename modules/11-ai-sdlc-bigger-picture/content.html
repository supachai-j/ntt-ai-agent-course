The Bigger Picture: AI Coding Agent SDLC

Module 01-10 สอนวิธีใช้ Hermes/Claude Code เป็นเครื่องมือ โมดูลนี้ชี้ไปยังคอร์สแยกที่ลึกกว่า (ai-sdlc) ซึ่งครอบคลุมวินัยทั้งวงจรชีวิตของการพัฒนาซอฟต์แวร์ด้วย agent — ตั้งแต่กลไกภายในของ agent ไปจนถึง governance ระดับทีม

TL;DR: คอร์สนี้ตอบคำถาม "ใช้เครื่องมือยังไง" ส่วนคอร์ส ai-sdlc (15 modules, 127 บท, พร้อม eval harness ที่รันได้จริง) ตอบคำถามที่ลึกกว่า — agent ทำงานข้างในยังไง, ต้นทุนคำนวณยังไง, จะรับมือ legacy code ยังไง, จะรู้ได้ยังไงว่า test ที่ agent เขียนจับบั๊กจริง, ภัยคุกคามจาก prompt injection มีหน้าตายังไง และจะดูแล agent ในทีมยังไง โมดูลนี้เป็นแผนที่สรุป ไม่ใช่สิ่งทดแทนการเรียนต้นทาง

ทำไมต้องมีโมดูลนี้

Module 01-10 ของคอร์สนี้ตอบคำถาม "ใช้ Hermes/Claude Code ยังไง" — วิธีตั้งค่า profile, เขียน prompt ที่ดี, ทำ feature loop แบบ TDD, ตั้งค่า tooling/MCP/multi-agent, CI/CD automation ฯลฯ แต่ยังไม่ได้ตอบคำถามที่ลึกกว่านั้น เช่น agent ทำงานข้างในยังไง, ต้นทุนคำนวณยังไง, จะรับมือ legacy code ยังไง, และ จะรู้ได้ยังไงว่า test ที่ agent เขียนจับบั๊กจริง

💡 คอร์สแยกที่ตอบคำถามเหล่านี้: คอร์ส AI Coding Agent SDLC — 15 modules, 127 บท, พร้อม eval harness ที่รันได้จริง ไม่ใช่ทฤษฎีเปล่า — ครอบคลุมตั้งแต่กลไกภายในของ agent ไปจนถึง governance ระดับทีม โมดูลนี้เป็น "แผนที่" สรุปหัวข้อสำคัญ 60-90 วินาทีต่อหัวข้อ แล้วชี้ไปเรียนลึกที่ต้นทาง

M01 · Agent ไม่ใช่กล่องดำ

Agent คือ loop ธรรมดา ที่ห่อด้วยวิศวกรรมหลายชั้น — ประกอบมาจาก 4-5 แนวคิดคนละทีม คนละปี ที่ค่อยๆ รวมกันในช่วง ~2 ปี ตารางลำดับเวลาด้านล่างแสดงว่าแต่ละแนวคิดเพิ่มอะไรเข้ามาในภาพรวม:

ปีแนวคิดสิ่งที่เพิ่มเข้ามา
2021-12WebGPTโมเดล + browser — เริ่มมีความคิดว่าให้หาข้อมูลเองได้
2022-01Chain-of-Thoughtให้คิดเป็นขั้นๆ ออกมาเป็นข้อความก่อนตอบ
2022-05MRKL Systemsแยกงานให้ module ภายนอกทำแทนที่จะให้โมเดลทำเอง
2022-10ReActต้นตำรับของลูป — "คิด" กับ "ลงมือ" สลับกันในลูปเดียว
💡 ทำไมสำคัญกับ debug: คนที่ debug agent ไม่เป็น ไม่ใช่เพราะไม่เก่ง แต่เพราะไม่มีแบบจำลองในหัวว่าข้างในมีอะไรบ้าง — เมื่อมีแล้ว ปัญหาที่ดูลึกลับจะกลายเป็นคำถามว่า "ชั้นไหนพัง"

M02 · Context Engineering

บริบทคืองบประมาณ ไม่ใช่ถัง — ทุก token ที่ใส่เข้าไปมีต้นทุนสองชั้น: เงินที่จ่าย และความสนใจของโมเดลที่ถูกดึงไปจากสิ่งที่สำคัญกว่า

⚠️ Lost in the Middle (2023): "ใส่ได้" กับ "ใช้ได้ดี" ไม่ใช่เรื่องเดียวกัน — context window ใหญ่ไม่ได้ยกเลิกวินัยข้อนี้ แค่ทำให้ค่าเสียหายมาช้าลง

เชื่อมกับ Module 05 (Prompt & Context) ของคอร์สนี้ที่สอนแค่ระดับ "ใช้ /compact ยังไง" — M02 ของ ai-sdlc สอนหลักคิดเบื้องหลังเต็มบทว่าทำไม trade-off นี้ถึงมีอยู่

M03 · เศรษฐศาสตร์ของ Token และโมเดล

คำถามที่ถูกไม่ใช่ "โมเดลไหนถูกกว่า" แต่คือ "ต้นทุนต่องานที่เสร็จเท่าไร" — โมเดลราคาต่อ token ถูกกว่าครึ่งแต่ต้องวน 3 รอบ แพงกว่าเสมอ M03 อธิบายผ่านสองแนวคิดคลาสสิกที่ย้อนไปก่อนยุค LLM มาก:

Cache (1960s CPU cache → prompt caching): อ่านซ้ำถูกกว่าอ่านครั้งแรกมาก — ตรรกะเดียวกันเป๊ะกับ prompt caching ยุค LLM

Cascade (Viola–Jones 2001 → model routing): กรองด้วยของถูกก่อน แล้วค่อยจ่ายแพงเฉพาะเคสที่จำเป็น

⚠️ แนวคิดทั้งสองขัดกันเองเมื่อใช้พร้อมกันกับ LLM — ต้องรู้จุดตัดสินใจว่าเมื่อไหร่ใช้อันไหน

M04 · Requirements ที่ "ตรวจได้"

บทที่ให้ผลตอบแทนสูงที่สุดในคอร์ส — วางแผน 10 นาที ประหยัดการสั่งซ้ำเป็นชั่วโมง ตารางด้านล่างเทียบความต่างระหว่าง "คำสั่ง" กับ "ข้อกำหนดที่ตรวจได้":

คำสั่งข้อกำหนด
ตัวอย่าง"แก้บั๊กตรงหน้า checkout ให้หน่อย""เมื่อตะกร้าว่าง ปุ่มชำระเงินต้อง disabled และเทสต์ checkout.empty ต้องเขียว"
รู้ว่าเสร็จเมื่อคนดูแล้วรู้สึกว่าใช่สคริปต์ตัดสินได้
เมื่อผิดต้องอธิบายใหม่ทั้งหมดชี้ได้ว่าข้อไหนไม่ผ่าน
💡 Prompt ที่ดีไม่ใช่คำสั่งที่เขียนเก่ง แต่คือ ข้อกำหนดที่ตรวจได้ — นี่คือหลักการเดียวกับที่ Module 04 (Engineering Workflows) ของคอร์สนี้ใช้ใน TDD RED phase (เขียน failing test = เขียนข้อกำหนดที่ตรวจได้)

M08 · Brownfield & Legacy Code

งานจริงไม่ได้เริ่มจากโฟลเดอร์ว่าง — เริ่มจาก repo อายุ 6 ปี ไม่มีเทสต์ ไม่มี type คนเขียนลาออกไปแล้ว กติกากลับด้านจาก greenfield:

GreenfieldBrownfield
ความเสี่ยงทำไม่เสร็จทำของที่เคยใช้ได้ให้พัง
กลยุทธ์ลุยได้เลยสร้างตาข่ายก่อน แล้วค่อยขยับ
💡 3 output ก่อนสั่งแก้อะไรเลย: 1) แผนที่ระดับบน (โมดูลหลัก, อะไรเรียกอะไร) 2) เส้นทางของฟีเจอร์ (request → DB ทีละไฟล์) 3) รายการของที่ดูแปลก (โค้ดตายแล้ว, ชื่อขัดกัน, ของซ้ำ) — ข้อ 3 มีค่าที่สุด เพราะ agent ไม่มีความคุ้นเคยมาบดบัง มันเห็นสิ่งที่คนในทีมชินตาจนมองไม่เห็นแล้ว

กรณีศึกษา "list-registration trap": ai-sdlc M08 ยกตัวอย่างเคสจริงที่ agent ถูกสั่งให้ "เพิ่มฟิลด์ registration ใหม่ในหน้า list" — โดยผิวเผินดูเป็นงานง่าย แต่โค้ดฐานมีระบบ registration สองชุดที่ตั้งชื่อคล้ายกันซ้อนกันอยู่ (legacy กับใหม่) ที่ไม่มีใครในทีมจำได้แล้วว่าทำไมถึงมีสองชุด agent ที่ไม่ได้ทำแผนที่ระดับบนก่อน แก้ผิดชุดและทำของที่ใช้งานได้อยู่แล้วพังแบบเงียบๆ — นี่คือเหตุผลที่ M08 ยืนกรานว่าต้องทำ 3 output ข้างต้นก่อนแตะโค้ดจริงเสมอในงาน brownfield

M11 · Testing: เทสต์ที่ Agent เขียนเอง

Agent เขียนเทสต์ได้เร็วมาก — ทั้งข้อดีและปัญหา เพราะเทสต์ที่ผ่านไม่ได้แปลว่าโค้ดถูก

⚠️ ความต่างสำคัญ: เมื่อคนเขียนโค้ดแล้วเขียนเทสต์ เทสต์สะท้อนความเข้าใจของคนนั้น — เมื่อ agent เขียนทั้งคู่ เทสต์สะท้อนสิ่งที่โค้ดทำ ไม่ใช่สิ่งที่โค้ดควรทำ

วิธีแก้ (TDD: red→green→refactor, Kent Beck 1999-2002) ถูกคิดมาก่อนมี LLM 20 ปี เพื่อกัน "เขียนโค้ดก่อนแล้วเขียนเทสต์ยืนยันสิ่งที่เพิ่งเขียน" — ตรงกับปัญหาของ agent วันนี้พอดี นี่คือเหตุผลที่ Module 04 ของคอร์สนี้ยืนกฎเหล็ก "ห้ามให้ agent แก้ไฟล์ test เอง" ในรอบ GREEN

M13 · Prompt Injection: ภัยคุกคามที่รู้วันเกิด

ข้อเท็จจริงหนึ่งข้อที่อธิบายภัยเกือบทั้งหมด: โมเดลแยกไม่ออกระหว่างคำสั่งจากคุณ กับข้อความที่หน้าตาเหมือนคำสั่งซึ่งอยู่ในข้อมูลที่มันอ่าน ลำดับเวลาด้านล่างแสดงว่าภัยนี้ถูกค้นพบและตั้งชื่อเมื่อไร:

วันที่เหตุการณ์
2022-09Riley Goodside สาธิต ข้อความในอินพุตทำให้โมเดลเลิกทำตามคำสั่งเดิม
2022-09-12Simon Willison ตั้งชื่อ "prompt injection" เทียบกับ SQL injection
2023-02Indirect prompt injection — พิษไม่ต้องมาจากผู้ใช้ มาจากของที่ agent ไปอ่านเอง
2023→OWASP จัดเป็นอันดับ 1 (LLM01)
⚠️ เชื่อมตรงกับกฎ untrusted-content ที่ระบบนี้เองก็บังคับใช้อยู่ — เนื้อหาจากเว็บ/ไฟล์ที่ agent อ่าน ต้องถูก treat เป็น data ไม่ใช่ instruction เสมอ

M12 · Evals

โมดูลที่คอร์สทั่วไปไม่มี — ความแปรปรวนระหว่างการรันสองครั้งของงานเดียวกัน มักใหญ่กว่าผลของการแก้ prompt ที่เพิ่งทำ

💡 เนื้อหานี้มีอยู่แล้วใน Module 09 ของคอร์สนี้ — ดู "วัดผลว่า pipeline ดีขึ้นจริงหรือแค่รู้สึกว่าดีขึ้น" ใน Module 09 (CI/CD Automation) — ดึงมาจาก M12 นี้โดยตรง พร้อม hands-on mini-eval lab

M15 · Governance: Runbook ที่ Agent ทำตามได้จริง

ปัญหาที่เหลืออยู่ไม่ใช่ปัญหาเทคนิค แต่เป็นความไว้ใจที่ปรับเทียบถูก — ไว้ใจน้อยเกินไม่ได้ประโยชน์ ไว้ใจมากเกินเจ็บ

💡 ทำไม runbook เดิมของทีมใช้กับ agent ไม่ได้: Runbook สำหรับคนเว้นช่องว่างไว้ให้คนเติมเอง เช่น "ตรวจดูว่าคิวปกติไหม" — คนอ่านรู้ว่าปกติแปลว่าอะไรเพราะเคยเห็นตอนไม่ปกติมาแล้ว agent ไม่มีความรู้ที่ค้างอยู่ในหัวคนเก่านั้น

เชื่อมกับ Module 08 (Enterprise Governance) ของคอร์สนี้ที่พูดเรื่อง account model/secrets — M15 ของ ai-sdlc ขยายไปถึงระดับ "ทีม 15 คนใช้ agent พร้อมกัน" ทั้งหมด

⚠️ กับดักที่พบบ่อย: session ที่ยังไม่มีคำศัพท์ใหม่หรือการตัดสินใจที่เข้าเกณฑ์ทั้ง 3 ข้อพร้อมกัน จะไม่มีอะไรถูกเขียนลงไฟล์เลย — นี่คือพฤติกรรมที่ถูกต้อง ไม่ใช่ bug แต่ต้องรู้ไว้ก่อน ไม่งั้นจะคิดว่า skill พัง

เชื่อมตรงกับหลักการ "artifact ต้องตรวจสอบได้" ที่ทั้ง Module 02 (AI-DLC Inception เป็น stage-gate) และ M04 ของ ai-sdlc (requirements ที่ตรวจได้) พูดถึง — เอกสารที่มีอยู่จริงในโค้ด ดีกว่าความเข้าใจที่ค้างอยู่ใน context window ของ session เดียว

สรุป: ทำไมควรเรียนต่อที่ ai-sdlc

  • M01-M03: กลไก agent + context + token economics — พื้นฐานที่คอร์สนี้ไม่ได้สอนลึกระดับนี้
  • M04, M08: requirements ที่ตรวจได้ + brownfield strategy — ขยาย engineering workflow ในระดับที่ลึกกว่า Module 04 ของคอร์สนี้
  • M11, M13: testing discipline + prompt injection threat model — เจาะลึกกว่า TDD/governance ที่มีในคอร์สนี้
  • M12: Evals — มีสรุปสั้นแล้วใน Module 09 ของคอร์สนี้ ไปอ่านเต็มที่ต้นทาง
  • M15: governance ระดับทีม — ต่อยอดจาก Module 08 ของคอร์สนี้
  • AI Hero Skills (aihero.dev) — ตัวอย่าง open-source ที่เอาหลักการ spec-first/TDD/code-review มาทำเป็น skill ติดตั้งใช้ได้จริงวันนี้ ไม่ต้องรอสร้างเอง
