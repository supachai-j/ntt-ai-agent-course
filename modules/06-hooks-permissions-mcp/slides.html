Module 06 · Engineering

Hooks, Permissions & MCP Integration

การควบคุม agent อย่างปลอดภัย และเชื่อมต่อกับระบบภายนอกจริง

ทำไมต้องคุม Claude Code

Agent ที่รัน tool ได้เองมีพลังมาก แต่ก็เสี่ยงมาก — รัน command ผิด, แก้ไฟล์ผิด, หรือ push โค้ดที่ยังไม่ผ่าน review ได้เหมือนกัน

สามชั้นการควบคุม

  • Permissions — กำหนดว่า tool ไหนใช้ได้/ห้ามใช้/ต้องถาม
  • Hooks — จุดแทรก script ที่ intercept และ block การกระทำได้จริง (deterministic, ไม่ใช่แค่ prompt)
  • MCP — มาตรฐานเชื่อม agent เข้ากับ tool/data source ภายนอกอย่างเป็นระบบ

Permission Modes

Modeพฤติกรรม
defaultถามยืนยันทุก tool call ที่มีผลกระทบ (write, bash, ฯลฯ)
acceptEditsยอมรับ file edit อัตโนมัติ แต่ยังถาม bash/tool อันตรายอื่น
planวางแผนอย่างเดียว ห้าม execute ใดๆ จนกว่าจะออกจากโหมด
bypassPermissionsข้ามการถามทั้งหมด (เทียบเท่า --dangerously-skip-permissions) — ใช้เฉพาะ sandbox/CI ที่ควบคุมแล้ว

เลือกโหมดผ่าน flag --permission-mode หรือกด Shift+Tab ใน interactive session

--allowedTools / --disallowedTools

# อนุญาตเฉพาะ Bash และ Read เท่านั้น ที่เหลือถามก่อนเสมอ
claude -p "run the test suite" --allowedTools "Bash,Read"

# ห้ามใช้ WebFetch และ Bash rm โดยเด็ดขาด
claude --disallowedTools "WebFetch" -p "review this PR"

# allow เจาะจงถึงระดับ command pattern
claude --allowedTools "Bash(git diff:*)" "Bash(git log:*)"

รูปแบบ Tool(pattern:*) ให้ควบคุมละเอียดกว่าการ allow ทั้ง tool

settings.json Hierarchy

ลำดับการอ่านค่า (สูง→ต่ำ)

  1. .claude/settings.local.json — ส่วนตัว ไม่ commit
  2. .claude/settings.json — project, commit เข้า repo
  3. ~/.claude/settings.json — user-level, ทุกโปรเจกต์
  4. Enterprise managed policy (บังคับ, override ไม่ได้)

ค่าที่ scope แคบกว่าจะ merge ทับ scope กว้างกว่า — เหมาะกับทีมที่ต้องการ baseline security ระดับ org แต่ยังให้ dev ปรับ local ได้บางส่วน

ตัวอย่าง permissions ใน settings.json

{
  "permissions": {
    "allow": [
      "Bash(git diff:*)",
      "Bash(git status)",
      "Read(*)"
    ],
    "ask": [
      "Bash(git push:*)",
      "Edit(*)"
    ],
    "deny": [
      "Read(.env)",
      "Read(**/*.pem)",
      "Bash(rm -rf *)"
    ]
  }
}

deny ชนะทุกกรณี — แม้ user จะ allow เองใน local ก็ override ไม่ได้ถ้า deny มาจาก scope สูงกว่า

Hooks คืออะไร

Hook คือ shell command ที่ Claude Code เรียกอัตโนมัติที่ event จุดต่างๆ ของ lifecycle — รับ JSON ทาง stdin, ตอบกลับผ่าน exit code / JSON ทาง stdout

8 ประเภท hook

UserPromptSubmitก่อน prompt ถูกส่งเข้า model
PreToolUseก่อน tool ถูกเรียก — block ได้จริง
PostToolUseหลัง tool รันเสร็จ
Notificationเมื่อ agent ต้องการแจ้ง user
Stopเมื่อ main agent หยุดตอบ
SubagentStopเมื่อ subagent หยุดตอบ
PreCompactก่อน context ถูก compact
SessionStartเมื่อ session เริ่มต้น/resume

PreToolUse: Security Gate ตัวจริง

ต่างจาก permission ask/deny (config ปกติ) — PreToolUse hook คือ code ที่รันจริง ตรวจ input แบบไหนก็ได้ (regex, call API, เช็ค policy server) ก่อนตัดสินใจ block

Contract

  • รับ JSON {tool_name, tool_input, ...} ทาง stdin
  • exit 0 → อนุญาตให้ tool รันต่อ
  • exit 2 → block tool call, stderr ถูกส่งกลับให้ agent เห็นเป็นเหตุผล
  • exit code อื่น → error, ถือว่า non-blocking แต่ log ไว้

ตัวอย่าง Hook: บล็อก rm -rf / force push

#!/usr/bin/env bash
# .claude/hooks/guard-bash.sh
input=$(cat)
tool_name=$(echo "$input" | jq -r '.tool_name')
command=$(echo "$input" | jq -r '.tool_input.command // empty')

[ "$tool_name" != "Bash" ] && exit 0

if echo "$command" | grep -Eiq 'rm[[:space:]]+-rf[[:space:]]+(/|\*|~)'; then
  echo "BLOCKED: destructive rm -rf detected: $command" >&2
  exit 2
fi

if echo "$command" | grep -Eiq 'git[[:space:]]+push[[:space:]].*--force'; then
  echo "BLOCKED: force push not allowed by policy" >&2
  exit 2
fi

exit 0

ผูก Hook เข้ากับ settings.json

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/guard-bash.sh"
          }
        ]
      }
    ]
  }
}

matcher กรองว่า hook นี้ทำงานกับ tool ไหน — ในที่นี้ทำงานเฉพาะตอนเรียก Bash เท่านั้น hook ตัวอื่นจะไม่ถูกเรียก

MCP คืออะไร

Model Context Protocol — มาตรฐานเปิดสำหรับเชื่อม AI agent เข้ากับ external tool และ data source (database, API, internal system) แบบไม่ต้องเขียน integration เฉพาะทุกครั้ง

Transport

  • stdio — subprocess local, สื่อสารผ่าน stdin/stdout
  • http — remote server ผ่าน HTTP request/response
  • sse — Server-Sent Events สำหรับ streaming จาก remote server

MCP server ประกาศ "tools", "resources", "prompts" ของตัวเอง — Claude Code discover แล้วนำมาต่อเข้ากับ tool list ที่ agent เรียกใช้ได้ เหมือนเป็น plugin มาตรฐาน

เพิ่ม MCP Server จริง

# stdio server (subprocess) — postgres MCP
claude mcp add postgres -s project -- npx -y @modelcontextprotocol/server-postgres \
  "postgresql://user:pass@localhost/db"

# HTTP/remote server — GitHub MCP
claude mcp add --transport http github https://api.githubcopilot.com/mcp \
  --header "Authorization: Bearer $GITHUB_TOKEN"

# ตรวจสอบว่าติดตั้งและเชื่อมต่อสำเร็จ
claude mcp list
claude mcp get postgres

Scope: -s user (ทุกโปรเจกต์ของ user), -s project (commit ใน .mcp.json แชร์ทีม), -s local (เฉพาะเครื่อง ไม่ commit)

# ใช้ MCP resource ตรงๆ ใน chat ด้วย URI scheme <server-name>:<resource-path>
คุณ: สรุป @github:issue://123 ให้หน่อย แล้วเสนอ fix

Resource reference (@server:type://id) ทำให้ agent ดึงข้อมูล live จาก external system เข้ามาเป็น context ได้ทันทีในบทสนทนา ไม่ต้อง copy-paste เอง

MCP ใน CI / Bare Mode

# รันแบบ headless ใน CI, ไม่มี interactive session, ใช้ MCP config ที่ pin ไว้
claude --bare -p "run migration check against staging db" \
  --mcp-config ./ci-mcp.json \
  --strict-mcp-config

# จำกัด output ของ MCP tool กัน context ถูก flood
export MAX_MCP_OUTPUT_TOKENS=8000

ทำไมต้องเข้มงวดใน CI

  • --strict-mcp-config — ใช้เฉพาะ server ใน config file ที่ระบุ ไม่ไป merge กับ user/project settings ที่อาจไม่ reproducible
  • MAX_MCP_OUTPUT_TOKENS — MCP tool บาง server (เช่น query DB) คืนข้อมูลก้อนใหญ่ได้ ต้องตัดเพื่อกัน context window ล้น

เชื่อมโยงกลับ Hermes (Module 02)

Concept เดียวกันทั้งคู่ — Hermes เองก็ไม่ได้ผูก tool ไว้ตายตัวใน code แต่ใช้ MCP เป็น "tool layer" มาตรฐานเหมือนกัน

ตัวอย่างใน Hermes

  • terminal, browser_*, web_search — ล้วนเป็น MCP tool ที่ profile ผูกเข้ามา
  • เพิ่ม/ตัด tool ให้ agent ได้โดยไม่ต้องแก้ core — เหมือนที่ Claude Code เพิ่ม MCP server ใหม่
  • permission model ของ Hermes (approval, allow/deny) ก็อิงหลักการเดียวกับ Claude Code permissions/hooks

สรุป

  • Permission modes + allow/ask/deny คุมว่า agent "ทำอะไรได้บ้าง" แบบ declarative
  • Hooks คุมแบบ "code จริง" — PreToolUse + exit code 2 คือ security gate ที่ bypass ไม่ได้ด้วย prompt
  • MCP คือมาตรฐานเชื่อมต่อ tool/data ภายนอก — เพิ่ม server ใหม่โดยไม่ต้องแก้ agent core
  • ใน CI ต้องใช้ --strict-mcp-config + จำกัด output token เพื่อความ reproducible และปลอดภัย
