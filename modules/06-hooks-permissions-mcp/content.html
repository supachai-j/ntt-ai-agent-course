Hooks, Permissions & MCP Integration

การควบคุม Claude Code อย่างปลอดภัยด้วย permission modes และ hooks ที่ block ได้จริง แล้วต่อด้วยการเชื่อมต่อ external tool/data source ผ่าน MCP

TL;DR: Claude Code คุม agent ด้วย 3 ชั้น — Permissions (declarative, allow/ask/deny), Hooks (code จริงที่ intercept และ block ได้), และ MCP (มาตรฐานต่อ tool/data ภายนอก) settings.json มี hierarchy 4 ระดับที่ scope แคบ merge ทับ scope กว้าง ส่วน PreToolUse hook คือ security gate ตัวจริงที่ prompt เอาชนะไม่ได้ เพราะเป็น exit code จาก script

ทำไมต้องคุม Claude Code

Agent ที่รัน tool ได้เองมีพลังมาก แต่ก็เสี่ยงมาก — รัน command ผิด, แก้ไฟล์ผิด, หรือ push โค้ดที่ยังไม่ผ่าน review ได้เหมือนกัน Claude Code จึงมีการควบคุมอยู่ 3 ชั้นที่ทำงานร่วมกัน:

  • Permissions — กำหนดว่า tool ไหนใช้ได้/ห้ามใช้/ต้องถาม เป็น configuration แบบ declarative
  • Hooks — จุดแทรก script ที่ intercept และ block การกระทำได้จริง (deterministic, ไม่ใช่แค่ prompt ที่ model อาจ "ลืม" หรือถูก jailbreak ได้)
  • MCP — มาตรฐานเชื่อม agent เข้ากับ tool/data source ภายนอกอย่างเป็นระบบ ไม่ต้องเขียน integration เฉพาะทุกครั้ง
💡 ทั้งสามชั้นนี้ไม่ได้แยกขาดจากกัน — permissions บอกว่า "อยากให้ถามไหม", hooks บอกว่า "ต้องบล็อกจริงไหมไม่ว่า user จะตอบยังไง", และ MCP คือช่องทางที่ tool เหล่านั้นเชื่อมออกไปหาโลกภายนอก

Permission Modes

Claude Code มี permission mode 4 แบบ ที่กำหนดพฤติกรรมการถามยืนยันก่อนรัน tool ที่มีผลกระทบ:

Modeพฤติกรรม
defaultถามยืนยันทุก tool call ที่มีผลกระทบ (write, bash, ฯลฯ)
acceptEditsยอมรับ file edit อัตโนมัติ แต่ยังถาม bash/tool อันตรายอื่น
planวางแผนอย่างเดียว ห้าม execute ใดๆ จนกว่าจะออกจากโหมด
bypassPermissionsข้ามการถามทั้งหมด (เทียบเท่า --dangerously-skip-permissions) — ใช้เฉพาะ sandbox/CI ที่ควบคุมแล้ว

เลือกโหมดผ่าน flag --permission-mode ตอน start session หรือกด Shift+Tab เพื่อสลับโหมดใน interactive session แบบ live โดยไม่ต้องรีสตาร์ท

⚠️ bypassPermissions อันตรายถ้าใช้ผิดที่ — ควรจำกัดไว้เฉพาะ environment ที่ sandbox/isolate แล้วเท่านั้น (เช่น CI container ที่ไม่มี network ออกนอก หรือ VM ทิ้งได้)

--allowedTools / --disallowedTools

นอกจาก permission mode แล้ว ยังสามารถระบุ allowlist/denylist ของ tool ได้ตรงๆ ผ่าน flag ตอนรัน:

# อนุญาตเฉพาะ Bash และ Read เท่านั้น ที่เหลือถามก่อนเสมอ
claude -p "run the test suite" --allowedTools "Bash,Read"

# ห้ามใช้ WebFetch และ Bash rm โดยเด็ดขาด
claude --disallowedTools "WebFetch" -p "review this PR"

# allow เจาะจงถึงระดับ command pattern
claude --allowedTools "Bash(git diff:*)" "Bash(git log:*)"

รูปแบบ Tool(pattern:*) ให้ควบคุมละเอียดกว่าการ allow ทั้ง tool ทั้งก้อน — เช่น allow เฉพาะ git diff/git log (read-only, ปลอดภัย) แต่ยังต้องถามก่อนถ้าเป็น git push หรือ bash command อื่น

settings.json Hierarchy

Claude Code อ่านค่า config จากหลายไฟล์ ตามลำดับความสำคัญจากสูงไปต่ำ:

  1. .claude/settings.local.json — ส่วนตัว ไม่ commit เข้า repo (ใส่ใน .gitignore)
  2. .claude/settings.json — project-level, commit เข้า repo เพื่อแชร์กับทีม
  3. ~/.claude/settings.json — user-level, มีผลกับทุกโปรเจกต์ของ user คนนั้น
  4. Enterprise managed policy — บังคับจาก org, override ไม่ได้แม้จะเป็นไฟล์ scope ที่สูงกว่าในลิสต์นี้

ค่าที่ scope แคบกว่า (เช่น local) จะ merge ทับค่าที่ scope กว้างกว่า (เช่น user-level) ยกเว้น Enterprise managed policy ที่ยึดสิทธิ์บังคับสูงสุดเสมอ การออกแบบนี้เหมาะกับทีมที่ต้องการ baseline security ระดับ org (เช่น deny การอ่านไฟล์ secret) แต่ยังให้ developer ปรับแต่ง config ส่วนตัวได้บางส่วน (เช่น allow tool เพิ่มสำหรับ workflow เฉพาะตัว)

ตัวอย่าง permissions ใน settings.json

ตัวอย่างการตั้งค่า permissions object ใน settings.json แบบเต็ม ที่มีทั้ง allow/ask/deny:

{
  "permissions": {
    "allow": [
      "Bash(git diff:*)",
      "Bash(git status)",
      "Read(*)"
    ],
    "ask": [
      "Bash(git push:*)",
      "Edit(*)"
    ],
    "deny": [
      "Read(.env)",
      "Read(**/*.pem)",
      "Bash(rm -rf *)"
    ]
  }
}

deny ชนะทุกกรณี — แม้ user จะ allow เองใน local scope ก็ override ไม่ได้ ถ้า deny rule นั้นมาจาก scope ที่สูงกว่า (เช่น project settings หรือ enterprise policy) นี่คือกลไกที่ทำให้ทีม security ตั้ง guardrail ระดับ org ได้อย่างมั่นใจว่า developer แต่ละคนจะ bypass ไม่ได้ผ่าน local config

Hooks คืออะไร

Hook คือ shell command ที่ Claude Code เรียกอัตโนมัติที่ event จุดต่างๆ ของ lifecycle การทำงานของ agent hook รับ JSON ทาง stdin (มีข้อมูลบริบท เช่น tool ที่กำลังจะถูกเรียก) และตอบกลับผ่าน exit code หรือ JSON ทาง stdout เพื่อสั่งให้ agent ดำเนินการต่อ, block, หรือแม้แต่ inject ข้อมูลเพิ่มเข้าไปใน context

Claude Code มี hook event ทั้งหมด 8 ประเภท ครอบคลุมทุกจุดสำคัญของ agent lifecycle:

Hookเมื่อไหร่
UserPromptSubmitก่อน prompt ถูกส่งเข้า model
PreToolUseก่อน tool ถูกเรียก — block ได้จริง
PostToolUseหลัง tool รันเสร็จ
Notificationเมื่อ agent ต้องการแจ้ง user
Stopเมื่อ main agent หยุดตอบ
SubagentStopเมื่อ subagent หยุดตอบ
PreCompactก่อน context ถูก compact
SessionStartเมื่อ session เริ่มต้น/resume

PreToolUse: Security Gate ตัวจริง

ต่างจาก permission ask/deny ซึ่งเป็น config ปกติ (agent อ่าน config แล้วตัดสินใจเอง) — PreToolUse hook คือ code ที่รันจริง นอก process ของ model สามารถตรวจ input แบบไหนก็ได้ ไม่จำกัดแค่ pattern matching ธรรมดา เช่น regex, เรียก external API, หรือเช็คกับ policy server ก่อนตัดสินใจ block

Contract ของ PreToolUse hook มีดังนี้:

  • รับ JSON {tool_name, tool_input, ...} ทาง stdin
  • exit 0 → อนุญาตให้ tool รันต่อตามปกติ
  • exit 2 → block tool call ทันที และข้อความที่เขียนไปยัง stderr จะถูกส่งกลับให้ agent เห็นเป็นเหตุผลของการถูก block (agent จะเอาเหตุผลนี้ไปปรับแผนต่อได้)
  • exit code อื่น (ไม่ใช่ 0 หรือ 2) → ถือเป็น error ของ hook เอง เป็น non-blocking (tool ยังรันต่อได้) แต่ระบบจะ log ไว้เพื่อ debug
💡 จุดสำคัญคือ hook ทำงานแบบ deterministic — ไม่ขึ้นกับว่า model จะ "เชื่อฟัง" instruction ในระบบหรือไม่ เพราะเป็น process แยกที่รันนอก inference loop ทำให้เหมาะกับ guardrail ที่ต้อง bypass ไม่ได้จริงๆ

ตัวอย่าง Hook: บล็อก rm -rf / force push

ตัวอย่าง bash hook script ที่ทำหน้าที่เป็น PreToolUse guard สำหรับ Bash tool โดยเฉพาะ — ตรวจจับ command อันตรายสองแบบคือ destructive rm -rf และ force push ด้วย git push --force:

#!/usr/bin/env bash
# .claude/hooks/guard-bash.sh
input=$(cat)
tool_name=$(echo "$input" | jq -r '.tool_name')
command=$(echo "$input" | jq -r '.tool_input.command // empty')

[ "$tool_name" != "Bash" ] && exit 0

if echo "$command" | grep -Eiq 'rm[[:space:]]+-rf[[:space:]]+(/|\*|~)'; then
  echo "BLOCKED: destructive rm -rf detected: $command" >&2
  exit 2
fi

if echo "$command" | grep -Eiq 'git[[:space:]]+push[[:space:]].*--force'; then
  echo "BLOCKED: force push not allowed by policy" >&2
  exit 2
fi

exit 0

Script นี้อ่าน JSON จาก stdin ด้วย jq, เช็คว่า tool ที่กำลังจะรันคือ Bash หรือไม่ (ถ้าไม่ใช่ก็ปล่อยผ่านทันทีด้วย exit 0) แล้วตรวจ pattern อันตรายสองแบบด้วย grep -Eiq ถ้าเจอ pattern อันตรายจะ echo ข้อความอธิบายไปที่ stderr แล้ว exit 2 เพื่อ block

ผูก Hook เข้ากับ settings.json

หลังจากเขียน hook script แล้ว ต้องลงทะเบียนมันใน settings.json ภายใต้ key hooks:

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/guard-bash.sh"
          }
        ]
      }
    ]
  }
}

matcher กรองว่า hook นี้ทำงานกับ tool ไหน — ในตัวอย่างนี้ทำงานเฉพาะตอนเรียก Bash เท่านั้น hook ตัวอื่นที่มี matcher อื่นจะไม่ถูกเรียกเมื่อ tool ที่ใช้ไม่ตรงกับ matcher ของมัน ตัวแปร $CLAUDE_PROJECT_DIR ทำให้ path ของ hook script อ้างอิงจาก root ของ project เสมอไม่ว่าจะรัน Claude Code จาก working directory ไหน

MCP คืออะไร

Model Context Protocol (MCP) คือมาตรฐานเปิดสำหรับเชื่อม AI agent เข้ากับ external tool และ data source (database, API, internal system ต่างๆ) โดยไม่ต้องเขียน integration เฉพาะทุกครั้งที่ต้องการต่อกับระบบใหม่ MCP server ประกาศ "tools", "resources", และ "prompts" ของตัวเองผ่าน protocol มาตรฐาน แล้ว Claude Code จะ discover สิ่งเหล่านี้อัตโนมัติและนำมาต่อเข้ากับ tool list ที่ agent เรียกใช้ได้ เหมือนเป็นระบบ plugin มาตรฐาน

MCP รองรับ transport 3 แบบ:

  • stdio — subprocess ที่รัน local บนเครื่อง สื่อสารผ่าน stdin/stdout เหมาะกับ tool ที่ทำงานบนเครื่องเดียวกัน เช่น เข้าถึง filesystem หรือ database local
  • http — remote server ที่สื่อสารผ่าน HTTP request/response แบบมาตรฐาน เหมาะกับบริการ SaaS ที่มี API endpoint ของตัวเอง
  • sse — Server-Sent Events สำหรับ streaming ข้อมูลจาก remote server แบบต่อเนื่อง

เพิ่ม MCP Server จริง

ใช้คำสั่ง claude mcp add เพื่อเพิ่ม MCP server ทั้งแบบ stdio (subprocess) และ http (remote):

# stdio server (subprocess) — postgres MCP
claude mcp add postgres -s project -- npx -y @modelcontextprotocol/server-postgres \
  "postgresql://user:***@localhost/db"

# HTTP/remote server — GitHub MCP
claude mcp add --transport http github https://api.githubcopilot.com/mcp \
  --header "Authorization: Bearer ***"

# ตรวจสอบว่าติดตั้งและเชื่อมต่อสำเร็จ
claude mcp list
claude mcp get postgres

Scope ของ MCP server config มี 3 ระดับ:

  • -s user — มีผลกับทุกโปรเจกต์ของ user คนนั้น
  • -s project — commit ใน .mcp.json เพื่อแชร์กับทั้งทีมในโปรเจกต์นี้
  • -s local — เฉพาะเครื่องนี้เท่านั้น ไม่ commit เข้า repo

นอกจากเรียก tool จาก MCP server แล้ว ยังสามารถ reference resource ของ MCP server ตรงๆ ในบทสนทนาได้ผ่าน URI scheme @server-name:resource-path:

# ใช้ MCP resource ตรงๆ ใน chat ด้วย URI scheme <server-name>:<resource-path>
คุณ: สรุป @github:issue://123 ให้หน่อย แล้วเสนอ fix

Resource reference รูปแบบ @server:type://id ทำให้ agent ดึงข้อมูล live จาก external system เข้ามาเป็น context ได้ทันทีในบทสนทนา โดยไม่ต้อง copy-paste ข้อมูลเข้ามาเอง — ในตัวอย่างนี้ agent จะดึง issue #123 จาก GitHub MCP server มาอ่านโดยตรง

MCP ใน CI / Bare Mode

เมื่อรัน Claude Code แบบ headless ใน CI pipeline ที่ไม่มี interactive session ควร pin MCP config ให้ reproducible และจำกัด output เพื่อความปลอดภัย:

# รันแบบ headless ใน CI, ไม่มี interactive session, ใช้ MCP config ที่ pin ไว้
claude --bare -p "run migration check against staging db" \
  --mcp-config ./ci-mcp.json \
  --strict-mcp-config

# จำกัด output ของ MCP tool กัน context ถูก flood
export MAX_MCP_OUTPUT_TOKENS=8000

เหตุผลที่ต้องเข้มงวดใน CI มากกว่า interactive session ปกติ:

  • --strict-mcp-config — บังคับให้ใช้เฉพาะ server ที่ระบุใน config file นั้นเท่านั้น ไม่ไป merge กับ user-level หรือ project-level settings ที่อาจไม่ reproducible ข้าม CI run หรือข้าม environment
  • MAX_MCP_OUTPUT_TOKENS — MCP tool บาง server (เช่น query database ขนาดใหญ่) สามารถคืนข้อมูลก้อนใหญ่มากได้ ต้องตั้ง limit เพื่อป้องกัน context window ล้นจนทำให้ agent ทำงานผิดพลาดหรือ cost พุ่ง
⚠️ ใน CI ห้ามพึ่งพา MCP config ที่ merge มาจาก user-level settings เด็ดขาด เพราะแต่ละ CI runner อาจมี environment ต่างกัน ทำให้ behavior ไม่ reproducible — ต้อง pin ด้วย --strict-mcp-config เสมอ

Case Study: Context7 และเทรนด์ MCP-to-CLI/Skills

MCP server ยังคงเป็นวิธีที่นิยมและมีประโยชน์มากสำหรับหลายงาน (ตามที่อธิบายไว้ทั้ง module นี้) แต่มีเทรนด์ใหม่กำลังเกิดขึ้นในวงการ agentic coding: สำหรับหลาย use case, การใช้ Skill ที่เรียก CLI tool แบบเบาๆ ก็ทำงานได้ผลลัพธ์เดียวกันกับการรัน MCP server เต็มรูปแบบ แต่ setup น้อยกว่าและกิน context window น้อยกว่าในระยะยาว

เหตุผลหลักคือความแตกต่างของ "วงจรชีวิต" การทำงาน — MCP server เป็นแบบ always-on: พอ connect เข้ามาแล้ว มันจะอยู่ใน session ตลอดเวลา ประกาศ tools/resources ของตัวเองเข้าไปใน tool list ของ agent ซึ่งกิน context และ tool-slot อย่างต่อเนื่องไม่ว่าจะได้ใช้งานจริงหรือไม่ ในทางกลับกัน Skill + CLI จะถูกเรียกเฉพาะตอนที่ agent ตัดสินใจว่าต้องใช้งานจริงๆ เท่านั้น — ไม่ต้องมี process ค้างอยู่ ไม่ต้องประกาศ tool schema ล่วงหน้าตลอดเวลา ทำให้ context budget ที่จำกัดของ agent เหลือไว้ใช้กับงานอื่นได้มากขึ้น

ตัวอย่างจริง: Context7

Context7 เป็นเครื่องมือยอดนิยมที่แก้ปัญหาคลาสสิกของ LLM: training data ของ model มักจะเก่ากว่า library/package เวอร์ชันล่าสุดที่ project จริงใช้อยู่เสมอ เช่น model อาจแนะนำ API ของ React 18 ทั้งที่ project กำลังใช้ React 19.2 อยู่จริง ซึ่งทำให้โค้ดที่ agent เขียนอาจใช้ API ที่ deprecated หรือไม่มีอยู่แล้วในเวอร์ชันปัจจุบัน Context7 แก้ปัญหานี้ด้วยการดึง documentation ที่ ตรงกับเวอร์ชันปัจจุบัน ของ library ที่ project ใช้อยู่จริง เข้ามาเป็น context ให้ agent อ้างอิงตอนเขียนโค้ด แทนที่จะพึ่งความรู้ที่ฝังอยู่ใน training data ซึ่งอาจล้าสมัยไปแล้ว

จุดที่น่าสนใจคือวิวัฒนาการของ Context7 เอง: เดิมทีมันเปิดตัวมาในรูปแบบ MCP server ล้วนๆ แต่ปัจจุบันเมื่อ install Context7 สำหรับ Claude Code ระบบจะให้เลือกระหว่างสองแบบ — MCP server (แบบเดิม) หรือ CLI + Skill (แบบใหม่) และทางเลือก CLI + Skill ถูกแนะนำเป็นแนวทางที่ทันสมัยและมีประสิทธิภาพกว่าในตอนนี้

💡 นี่คือภาพสะท้อนของเทรนด์ใหญ่ในวงการ agentic coding: เมื่อ ecosystem เติบโตขึ้น การ integrate เครื่องมือบางตัวกำลังขยับจาก "MCP server ที่ on อยู่ตลอด" ไปเป็น "Skill ที่ shell out ไปเรียก CLI เมื่อจำเป็น" เพราะประหยัด context budget ที่จำกัดของ agent และไม่ต้องมี infrastructure ค้างอยู่ตลอดเวลา

เลือกยังไง: MCP Server หรือ Skill + CLI

ทั้งสองแนวทางไม่ได้แข่งกันตายตัว — แต่ละแบบเหมาะกับสถานการณ์ต่างกัน:

  • เลือก MCP server เมื่อต้องใช้ tool นั้นบ่อยและต่อเนื่องตลอด session, ต้องการ resource reference แบบ @server:type://id ที่ integrate ลึกกับ chat, หรือ tool นั้นต้องรักษา state ระหว่างการเรียกหลายครั้ง
  • เลือก Skill + CLI เมื่อใช้งานเป็นครั้งคราว, อยากประหยัด context window, ไม่อยากมี process/server ค้างอยู่ตลอดเวลา หรือ setup ที่เบากว่าตอบโจทย์มากกว่า

เนื้อหานี้ดัดแปลงและอ้างอิงจากวิดีโอคอร์สของ DeepLearning.AI ร่วมกับ JetBrains: youtu.be/hy8UstR2NEg

เชื่อมโยงกลับ Hermes (Module 02)

Concept เดียวกันนี้ปรากฏใน Hermes ด้วย — Hermes เองก็ไม่ได้ผูก tool ไว้ตายตัวใน code แต่ใช้ MCP เป็น "tool layer" มาตรฐานเช่นเดียวกับ Claude Code ตัวอย่างที่เห็นได้ชัดใน Hermes:

  • terminal, browser_*, web_search — ทั้งหมดนี้ล้วนเป็น MCP tool ที่ profile ผูกเข้ามา ไม่ใช่ built-in ตายตัวในตัว agent core
  • สามารถเพิ่ม/ตัด tool ให้ agent ได้โดยไม่ต้องแก้ core code — เหมือนกับที่ Claude Code เพิ่ม MCP server ใหม่ได้ผ่านคำสั่งเดียว
  • permission model ของ Hermes (approval workflow, allow/deny) ก็อิงหลักการเดียวกับ Claude Code permissions/hooks — คุม "agent ทำอะไรได้บ้าง" ผ่าน config layer ที่แยกจาก reasoning ของ model
💡 การเข้าใจ MCP ใน Module นี้จึงไม่ใช่แค่ความรู้เฉพาะของ Claude Code — เป็น mental model ที่ใช้ได้กับทุก agent platform ที่ยึดมาตรฐาน MCP รวมถึง Hermes ที่ใช้งานอยู่ตอนนี้

สรุป

  • Permission modes + allow/ask/deny คุมว่า agent "ทำอะไรได้บ้าง" แบบ declarative ผ่าน config
  • Hooks คุมแบบ "code จริง" — PreToolUse + exit code 2 คือ security gate ที่ bypass ไม่ได้ด้วย prompt เพราะรันนอก inference loop
  • settings.json มี hierarchy 4 ระดับ (local → project → user → enterprise) ที่ scope แคบ merge ทับ scope กว้าง ยกเว้น enterprise policy ที่บังคับสูงสุดเสมอ
  • MCP คือมาตรฐานเชื่อมต่อ tool/data ภายนอก รองรับ 3 transport (stdio/http/sse) — เพิ่ม server ใหม่โดยไม่ต้องแก้ agent core
  • ใน CI ต้องใช้ --strict-mcp-config + จำกัด MAX_MCP_OUTPUT_TOKENS เพื่อความ reproducible และปลอดภัย
  • Hermes เองก็ยึดหลักการเดียวกัน — MCP เป็น tool layer มาตรฐาน ไม่ผูก tool ตายตัวใน core
