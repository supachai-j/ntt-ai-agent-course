Hooks, Permissions & MCP Integration

เขียน PreToolUse hook จริงเพื่อบล็อก dangerous command, ตั้งค่าใน .claude/settings.json, ทดสอบว่า block ทำงานจริงด้วย claude -p, แล้วต่อด้วยการเพิ่ม MCP server และตรวจสอบด้วย claude mcp list

⏱ 45–60 นาที 🖥 ต้องมี Claude Code CLI + bash + jq 🌐 ต้องมี network สำหรับ npx (MCP filesystem server) 📁 ใช้โฟลเดอร์ทดลองแยกจาก repo งานจริง

Prerequisites

  • ผ่าน Module 03 (Claude Code Fundamentals) มาแล้ว — รู้จัก claude -p, --allowedTools
  • ติดตั้ง claude CLI แล้ว (claude --version ใช้งานได้)
  • มี jq ในเครื่อง (jq --version) — ใช้ parse JSON ใน hook script
  • มี node/npx ใช้งานได้ สำหรับรัน MCP server ตัวอย่างผ่าน stdio

Objectives

  • เข้าใจโครงสร้าง PreToolUse hook: input JSON ทาง stdin, exit code เป็นสัญญาณ block/allow
  • เขียน hook script จริงที่บล็อก rm -rf และ git push --force
  • ผูก hook เข้ากับ .claude/settings.json แล้วพิสูจน์ว่า block ทำงานจริง (ไม่ใช่แค่ในทฤษฎี)
  • เพิ่ม MCP server (filesystem) ด้วย claude mcp add แล้ว verify ด้วย claude mcp list
  • เข้าใจความเสี่ยงของ --dangerously-skip-permissions เมื่อไม่มี hook คุม

1เตรียมโฟลเดอร์ทดลอง

สร้างโฟลเดอร์แยกต่างหาก (ห้ามใช้ repo งานจริง เพราะ step ถัดไปจะทดสอบ command ที่ตั้งใจ ให้ agent "พยายาม" รันสิ่งที่อันตราย แม้ hook จะบล็อกไว้ก็ตาม)

mkdir -p ~/lab06-hooks-mcp/.claude/hooks
cd ~/lab06-hooks-mcp
mkdir -p scratch   # โฟลเดอร์เป้าหมายที่จะให้ agent "ลอง" ลบ (ไม่ควรถูกลบจริง)
git init -q        # เผื่อทดสอบ git push --force ด้วย
Verify: รัน ls -la .claude/hooks scratch ต้องเห็นทั้งสองโฟลเดอร์ถูกสร้างแล้ว

2เขียน PreToolUse Hook Script

Hook รับ JSON ทาง stdin (มี field tool_name, tool_input) แล้วตัดสินใจ ด้วย exit code: 0 = อนุญาต, 2 = block (stderr จะถูกส่งกลับให้ agent เห็นเป็นเหตุผลที่ถูกปฏิเสธ)

cat > .claude/hooks/guard-bash.sh <<'EOF'
#!/usr/bin/env bash
input=$(cat)
tool_name=$(echo "$input" | jq -r '.tool_name')
command=$(echo "$input" | jq -r '.tool_input.command // empty')

# hook นี้สนใจเฉพาะ Bash tool เท่านั้น
[ "$tool_name" != "Bash" ] && exit 0

if echo "$command" | grep -Eiq 'rm[[:space:]]+-rf[[:space:]]+(/|\*|~)'; then
  echo "BLOCKED: destructive rm -rf detected in command: $command" >&2
  exit 2
fi

if echo "$command" | grep -Eiq 'git[[:space:]]+push[[:space:]].*--force'; then
  echo "BLOCKED: force push is not allowed by policy. Use --force-with-lease and get review approval." >&2
  exit 2
fi

exit 0
EOF
chmod +x .claude/hooks/guard-bash.sh
Verify: ทดสอบ hook เปล่าๆ (ไม่ผ่าน Claude Code) เพื่อดู exit code โดยตรงก่อน: 
echo '{"tool_name":"Bash","tool_input":{"command":"rm -rf /tmp/foo"}}' | .claude/hooks/guard-bash.sh
echo "exit code: $?"
# ต้องเห็น: BLOCKED: destructive rm -rf detected...
# ต้องเห็น: exit code: 2

echo '{"tool_name":"Bash","tool_input":{"command":"ls -la"}}' | .claude/hooks/guard-bash.sh
echo "exit code: $?"
# ต้องเห็น: exit code: 0 (ไม่มี message ใดๆ)

3ผูก Hook เข้ากับ settings.json

สร้าง .claude/settings.json ระดับ project แล้วประกาศ hook ใน event PreToolUse พร้อม matcher ที่กรองเฉพาะ Bash tool

cat > .claude/settings.json <<'EOF'
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/guard-bash.sh"
          }
        ]
      }
    ]
  }
}
EOF
cat .claude/settings.json | jq .
Verify: jq . ต้อง parse ผ่านโดยไม่มี error (พิสูจน์ว่า JSON valid) — ถ้า JSON ผิด format Claude Code จะเมิน hook เงียบๆ โดยไม่แจ้งเตือนชัดเจน

4ทดสอบ Block จริงผ่าน claude -p

สั่งให้ agent พยายามรัน command อันตรายตรงๆ ผ่าน print mode แล้วดูว่า hook สกัดไว้ได้จริง (ไม่ใช่แค่ agent "ปฏิเสธเอง" ด้วยเหตุผลด้าน safety — เราต้องการพิสูจน์ hook ทำงาน)

cd ~/lab06-hooks-mcp
claude -p "You must call the Bash tool directly with the exact command: rm -rf ./scratch — do not check if it exists first, do not ask, just run it." \
  --allowedTools "Bash"
Verify: Output ควรมีข้อความทำนอง "A hook in this project blocks destructive rm -rf commands... guard-bash.sh rejected it before execution" และรัน ls scratch ต่อ — โฟลเดอร์ต้อง ยังอยู่ (ไม่ถูกลบ) ซึ่งพิสูจน์ว่า hook block คำสั่งไว้จริงก่อน tool จะ execute
ถ้าไม่ถูก block: ตรวจว่า .claude/settings.json อยู่ใน working directory ที่ถูกต้อง (ต้องรัน claude จาก project root เดียวกับ .claude/) และ hook script มี permission execute (chmod +x) แล้วหรือยัง

5เพิ่ม MCP Server จริง (filesystem)

ใช้ @modelcontextprotocol/server-filesystem เป็นตัวอย่าง MCP server ที่รันผ่าน stdio transport (subprocess ผ่าน npx) — จำกัด scope การเข้าถึงไว้ที่โฟลเดอร์เดียว

mkdir -p ~/lab06-hooks-mcp/mcp-workspace

claude mcp add filesystem -s local -- \
  npx -y @modelcontextprotocol/server-filesystem ~/lab06-hooks-mcp/mcp-workspace

Scope -s local = เฉพาะเครื่องนี้ ไม่ commit เข้า repo (เทียบกับ -s project ที่บันทึกใน .mcp.json ให้ทั้งทีมใช้ร่วมกัน หรือ -s user ที่ใช้ได้ทุกโปรเจกต์)

Verify: 
claude mcp list
# ต้องเห็นบรรทัด: filesystem: npx -y @modelcontextprotocol/server-filesystem ... - ✔ Connected

claude mcp get filesystem
# ต้องเห็น Type: stdio, Status: ✔ Connected, และ path ของ workspace ที่ระบุไว้

6ทดสอบใช้งาน MCP Server ผ่าน Chat

ลองสั่งให้ agent เขียนไฟล์ผ่าน MCP filesystem server เพื่อยืนยันว่า tool ต่อเข้ามาใช้งานได้จริง ไม่ใช่แค่ "list แล้วเชื่อมได้" เฉยๆ

claude -p "using the filesystem MCP server, write a file named hello.txt containing the text 'MCP works' inside the allowed workspace" \
  --allowedTools "mcp__filesystem__write_file,mcp__filesystem__list_directory"
Verify: cat ~/lab06-hooks-mcp/mcp-workspace/hello.txt ต้องแสดง ข้อความ MCP works — พิสูจน์ว่า MCP server ไม่ใช่แค่ config เฉยๆ แต่ agent เรียกใช้งานได้จริง
หมายเหตุ: ชื่อ tool ที่ MCP server ประกาศออกมาจะขึ้นต้นด้วย mcp__<server-name>__<tool> เสมอ — ใช้ claude mcp get filesystem หรือถามใน interactive session ว่ามี tool อะไรบ้างถ้าจำชื่อ tool ไม่ได้

7MCP ใน CI / Bare Mode (ภาพรวม)

ในงานจริงที่รันใน pipeline (headless, ไม่มี interactive session) ต้อง pin MCP config ให้ชัดเจนและไม่ให้ merge กับ config อื่นที่ไม่ reproducible

cat > ci-mcp.json <<'EOF'
{
  "mcpServers": {
    "filesystem": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/workspace/allowed-dir"]
    }
  }
}
EOF

export MAX_MCP_OUTPUT_TOKENS=8000

claude --bare -p "list files in the allowed workspace" \
  --mcp-config ./ci-mcp.json \
  --strict-mcp-config
Verify: cat ci-mcp.json | jq . ต้อง parse ผ่าน และ flag --strict-mcp-config ต้องอยู่ในคำสั่งเสมอเมื่อรันใน CI — เพื่อบังคับให้ใช้เฉพาะ server ใน config file นี้เท่านั้น ไม่ดึง MCP server จาก user/project settings ที่อาจต่างกันระหว่างเครื่อง

8ทำความสะอาด

ลบ MCP server ทดลองออกเมื่อทำ lab เสร็จ เพื่อไม่ให้ config ค้างอยู่ในเครื่อง

claude mcp remove filesystem -s local
Verify: claude mcp list ต้องไม่มีบรรทัด filesystem อีกต่อไป
อย่าใช้ --dangerously-skip-permissions ใน production workflow โดยไม่มี hook คุม: flag นี้ข้ามการถามยืนยันทั้งหมด (เทียบเท่า permission mode bypassPermissions) — ถ้าไม่มี PreToolUse hook เป็น deterministic gate คอยดักไว้ agent จะรัน command อันตรายได้ทันทีโดยไม่มี ด่านใดหยุดเลย ใช้เฉพาะใน sandbox ที่ isolate แล้วเท่านั้น และควรคู่กับ hook เสมอแม้ใน sandbox
Troubleshoot: Hook ไม่ทำงานเลย (agent ไม่ถูก block)
  • เช็คว่ารัน claude จาก directory เดียวกับที่มี .claude/settings.json — hook เป็น project-scoped
  • เช็ค permission ของ script: ls -la .claude/hooks/guard-bash.sh ต้องมี x bit
  • ตรวจ path ใน command field — ถ้าใช้ $CLAUDE_PROJECT_DIR ต้องแน่ใจว่า Claude Code รุ่นที่ใช้รองรับตัวแปรนี้ (เช็คด้วย claude --version) ถ้าไม่รองรับให้ใช้ absolute path แทน
  • รัน hook script ตรงๆ ด้วย stdin จำลอง (ตามขั้นตอนที่ 2) เพื่อแยกปัญหาว่าเป็นที่ script เองหรือที่การ integrate กับ settings.json
  • เช็ค JSON syntax ด้วย jq . .claude/settings.json — ถ้า invalid, Claude Code จะไม่ error แต่จะเมิน hook เงียบๆ
Troubleshoot: claude mcp add แล้ว list ไม่เจอ / Status ไม่ Connected
  • เช็คว่า npx/node ใช้งานได้จริงในเครื่อง (node --version) — MCP server แบบ stdio ต้องมี runtime ให้รัน subprocess
  • รันคำสั่ง MCP server ตรงๆ ก่อน (เช่น npx -y @modelcontextprotocol/server-filesystem /path) เพื่อดูว่า error อะไรก่อนที่จะผ่าน Claude Code
  • เช็คว่า path ที่ระบุใน args มีอยู่จริงและ accessible (permission อ่าน/เขียน)
  • ถ้าใช้ -s project เช็คว่ามีไฟล์ .mcp.json ถูกสร้างที่ root ของ repo

สรุป & ต่อยอด

Lab นี้พิสูจน์ครบสองด้าน: (1) PreToolUse hook เป็น deterministic security gate ที่บล็อกคำสั่งอันตรายได้จริงด้วย exit code 2 — ไม่ใช่แค่ prompt ที่ agent อาจ "เลือกเชื่อฟังหรือไม่" และ (2) MCP server ต่อเข้ากับ external tool/data ได้แบบ standard โดยไม่ต้องแก้ agent core

  • ต่อยอด: เขียน hook เพิ่มสำหรับ block pattern อื่น เช่น curl | bash, การเขียนทับไฟล์ .env, หรือ deploy command ที่ยังไม่ผ่าน approval
  • ต่อยอด: ลองเพิ่ม MCP server จริงที่ทีมใช้งาน (postgres, GitHub) แล้วลอง reference resource ด้วย @server:type://id ใน chat
  • ต่อยอด: ตั้งค่า deny list ใน settings.json ระดับ organization ให้ครอบคลุม secret file patterns (.env, *.pem, id_rsa) เป็น baseline สำหรับทุกโปรเจกต์
  • ต่อไปที่ Module 07 จะดูว่าเมื่อมี subagent หลายตัวทำงานพร้อมกัน permission/hook ต้องคุมยังไงให้ยังปลอดภัยเหมือนเดิม
