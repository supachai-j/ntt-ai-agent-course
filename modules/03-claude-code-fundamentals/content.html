Claude Code CLI — Fundamentals

ติดตั้ง Claude Code, ยืนยัน authentication, เข้าใจสอง orchestration mode, ตั้งค่า CLAUDE.md เป็นความจำโปรเจกต์ และใช้ tmux เพื่อรัน session ให้รอดจาก SSH disconnect

TL;DR: Claude Code เป็น official CLI coding agent จาก Anthropic ติดตั้งผ่าน npm และ auth ได้หลายวิธี รันได้ทั้งแบบ interactive (คุยโต้ตอบ) และ print mode (automation/CI) CLAUDE.md คือไฟล์ความจำโปรเจกต์ที่ agent auto-load ทุก session ส่วน tmux คือเครื่องมือสำคัญที่ทำให้ session บน remote server ไม่หายเมื่อ SSH หลุด — เปิดค้างไว้ แล้วกลับมา attach ดูงานที่ทำต่อได้เหมือนไม่เคยหลุดเลย

Claude Code คืออะไร

Claude Code คือ official CLI coding agent จาก Anthropic ติดตั้งผ่าน npm package ชื่อ @anthropic-ai/claude-code มันรันอยู่ในเทอร์มินัลของคุณโดยตรง อ่านและแก้ไฟล์ในโปรเจกต์ รัน command จริง (build, test, lint) และใช้ git ได้เหมือน engineer คนหนึ่งที่นั่งทำงานอยู่หน้าเครื่อง ไม่ใช่แค่ chatbot ที่ตอบคำถามอย่างเดียว

Claude Code ใช้งานได้ทั้งสองแบบ: แบบ interactive ที่คุณคุยโต้ตอบกับ agent ทีละขั้นตอน และแบบ automation/CI (one-shot, headless) ที่เหมาะกับการรันใน pipeline โดยไม่มีคนนั่งดู ที่น่าสนใจคือ Claude Code เป็น agent ตัวเดียวกับที่กำลังรันงานอยู่เบื้องหลังในหลายโมดูลของคอร์สนี้ — คุณกำลังเรียนรู้เครื่องมือที่ใช้สร้างคอร์สนี้ขึ้นมาเอง

ติดตั้งและ Authentication

การติดตั้งทำผ่าน npm แบบ global package แล้วตรวจสอบด้วย version flag:

npm install -g @anthropic-ai/claude-code
claude --version

หลังติดตั้งเสร็จ ควรรัน claude doctor เพื่อตรวจสุขภาพการติดตั้งทันที:

claude doctor

สำหรับ authentication มีให้เลือก 3 วิธี ขึ้นกับว่าคุณมี subscription หรือใช้ API billing:

# Browser OAuth — Claude Pro/Max subscription
claude
# หรือ login แบบ console สำหรับ API billing
claude auth login --console
# หรือใช้ API key ตรงๆ
export ANTHROPIC_API_KEY="sk-ant-..."
💡 วิธีแรก (claude เฉยๆ) จะเปิด browser ให้ล็อกอินผ่าน OAuth เหมาะกับคนที่มี Claude Pro/Max subscription อยู่แล้ว ส่วนวิธีที่สองและสามเหมาะกับทีมที่ต้องการ billing ผ่าน API key โดยตรง

ตรวจสอบสถานะการติดตั้ง

คำสั่งพื้นฐานสามคำสั่งนี้ควรรันทุกครั้งหลังติดตั้งหรือเมื่อพบปัญหาการใช้งาน:

คำสั่งใช้ทำอะไร
claude --versionเช็ค version ของ CLI ที่ติดตั้งอยู่
claude doctorตรวจสุขภาพการติดตั้ง (path, config, auto-update, multiple installs)
claude auth statusเช็คว่า login อยู่หรือยัง ใช้ auth method ไหน

ตัวอย่าง output จริงจากคำสั่ง claude auth status เมื่อ login สำเร็จ:

{
  "loggedIn": true,
  "authMethod": "claude.ai",
  "apiProvider": "firstParty",
  "email": "user@example.com"
}
💡 ถ้า loggedIn เป็น false หรือคำสั่งขึ้น error ให้กลับไปรัน auth flow ใหม่ตามวิธีที่เลือกไว้ในขั้นตอนก่อนหน้า

สอง Orchestration Mode: Interactive vs Print Mode

Claude Code รันได้ 2 แบบหลัก ขึ้นกับว่าคุณต้องการ dialog กับ agent หรือแค่ผลลัพธ์เดียวจบ:

โหมดคำสั่งเหมาะกับ
Interactive REPLclaudeทำงานร่วมกับ agent แบบโต้ตอบ, สำรวจโค้ด, debug ทีละขั้น
Print modeclaude -p "task"Automation, CI/CD, script — รันครั้งเดียวแล้วจบ ไม่มี dialog

กฎง่ายๆ ในการเลือกโหมด: ถ้าต้องการควบคุมทีละ step และตรวจงานระหว่างทาง ให้ใช้ Interactive แต่ถ้าต้องรันใน pipeline/script โดยไม่มีคนนั่งดู ให้ใช้ Print mode (-p)

Print Mode ในทางปฏิบัติ

# รันงานเดียวแล้วจบ ไม่มี interactive dialog
claude -p "explain what this repo does" --max-turns 3

# เอาผลลัพธ์เป็น JSON เพื่อ parse ต่อใน script
claude -p "list files" --output-format json | jq -r '.result'

Print mode ข้าม trust dialog โดยอัตโนมัติ — เหมาะกับ non-interactive context (CI runner, cron, script)

⚠️ เนื่องจาก print mode ข้าม trust dialog อัตโนมัติ ต้องรันเฉพาะใน directory ที่เชื่อถือได้เท่านั้น เพราะไม่มีขั้นตอนถามยืนยันก่อนอ่าน/รันไฟล์ในโฟลเดอร์นั้น

CLAUDE.md — Project Memory

CLAUDE.md คือไฟล์ที่ Claude Code auto-load ทุกครั้งที่เริ่ม session ใน directory นั้น ไฟล์นี้เก็บบริบทโปรเจกต์ เช่น architecture, key commands (test/lint/dev), และ code standards ที่ทีมใช้ มันไม่ใช่ prompt แต่คือ "ความจำถาวร" ที่ agent อ่านก่อนเริ่มงานทุกครั้ง ยิ่งเขียนดี agent ยิ่งเดาโครงสร้างโปรเจกต์ถูกโดยไม่ต้องถามซ้ำในทุก session

ตัวอย่าง CLAUDE.md ของโปรเจกต์จริง:

# Project: internal-billing-api

## Architecture
Node.js + Express REST API, PostgreSQL via Prisma ORM.
Entry point: src/server.js. Routes in src/routes/.

## Key commands
- Run dev server: npm run dev
- Run tests: npm test
- Lint: npm run lint
- Build: npm run build

## Code standards
- Use TypeScript strict mode, no `any`
- All routes need input validation via zod
- Write a test for every new endpoint
- Follow existing error-handling pattern in src/lib/errors.js

CLAUDE.md — Hierarchy (3 ระดับ)

CLAUDE.md มีลำดับชั้น 3 ระดับ ซึ่ง Claude Code จะรวมทั้งหมดเข้าด้วยกันตอนโหลด context — ระดับที่เฉพาะเจาะจงกว่าจะ override ระดับที่กว้างกว่า:

ระดับPathขอบเขต
Global~/.claude/CLAUDE.mdใช้กับทุกโปรเจกต์ของ user คนนั้น
Project./CLAUDE.mdเฉพาะโปรเจกต์นี้ — commit เข้า git แชร์กับทีม
Local.claude/CLAUDE.local.mdเฉพาะเครื่อง — gitignored ใช้เก็บ config ส่วนตัว
💡 ใช้ Global สำหรับ preference ส่วนตัวที่ใช้ทุกโปรเจกต์ (เช่น สไตล์การเขียนโค้ดที่ชอบ), Project สำหรับความรู้ที่ทั้งทีมต้องรู้ (commit เข้า git), และ Local สำหรับ config เฉพาะเครื่องที่ไม่อยากแชร์ (เช่น path เฉพาะเครื่องของคุณ)

Flags สำคัญที่ใช้บ่อย

Flags เหล่านี้ช่วยควบคุมพฤติกรรมและความเสี่ยงของ Claude Code โดยเฉพาะเมื่อรันแบบ automation:

Flagใช้ทำอะไร
--allowedToolsจำกัด tool ที่ agent ใช้ได้ เช่น "Bash(git *) Edit"
--max-turnsจำกัดจำนวนรอบการคุย/tool call ป้องกัน runaway loop
--output-format jsonoutput เป็น JSON เพื่อ parse ต่อด้วย script/jq
--modelเลือกโมเดล เช่น sonnet, opus, หรือชื่อเต็ม
-c, --continueสานต่อ conversation ล่าสุดใน directory ปัจจุบัน
-r, --resumeresume session เดิมด้วย session ID หรือเปิด picker
💡 การรวม --allowedTools กับ --max-turns เข้าด้วยกันเป็น pattern ที่ปลอดภัยที่สุดเวลารัน Claude Code แบบ automation ใน CI — จำกัดทั้งชนิด action ที่ทำได้ และจำนวนรอบสูงสุด

Trust Dialog & Workspace Safety

ครั้งแรกที่เปิด directory ใหม่ในโหมด interactive Claude Code จะถามว่า "Do you trust the files in this folder?" ก่อนอ่านหรือรันอะไรในโฟลเดอร์นั้น เพื่อป้องกันการรันโค้ดที่ไม่รู้จักที่มาโดยไม่ตั้งใจ

  • Trust dialog ถูกข้ามอัตโนมัติใน print mode (-p) — เพราะออกแบบมาให้รันแบบ non-interactive
  • ข้อแนะนำ: รัน print mode เฉพาะใน directory ที่ควบคุม/เชื่อถือได้เท่านั้น
  • Permission mode ควบคุมเพิ่มเติมได้ผ่าน --permission-mode (เช่น acceptEdits, plan, bypassPermissions)
⚠️ อย่ารัน print mode ใน directory ที่ไม่รู้จักที่มา เพราะไม่มี trust dialog มาป้องกันเหมือนโหมด interactive

Quick Win Demo

ตัวอย่างคำสั่งเดียวที่พิสูจน์ว่า Claude Code ใช้งานได้จริงบนเครื่อง รันได้ใน directory ของโปรเจกต์ใดก็ได้:

cd /path/to/your-project
claude -p "explain what this repo does" --max-turns 3

ภายใน 3 turns agent จะสำรวจไฟล์สำคัญ (README, package.json, entry point) แล้วสรุปโครงสร้างโปรเจกต์กลับมาเป็นข้อความ

ปัญหา: Interactive session หลุดเมื่อ SSH disconnect

Claude Code interactive mode (claude เฉยๆ) เป็น process ที่ผูกกับ terminal session — ปิด SSH หรือปิดแล็ปท็อป ทำให้ process ตายทันที พร้อมงานที่ยังไม่เสร็จ นี่เป็นปัญหาโดยเฉพาะเมื่อ:

  • งานที่ใช้เวลานาน (refactor ใหญ่, multi-step pipeline) ต้องรอดูจนจบ ไม่สามารถ "เดินไปทำอย่างอื่นแล้วกลับมาดู" ได้
  • เปิดหลาย SSH session พร้อมกันเพื่อรันหลายงาน → จัดการยาก สลับหน้าต่างไม่สะดวก
💡 ทางออก: tmux (terminal multiplexer) — รัน process ไว้ "ข้างใน" tmux session ที่อยู่บน server เอง ไม่ผูกกับ SSH connection ของคุณ ปิด SSH ได้ session ยังรันต่อ กลับมา SSH ใหม่แล้ว attach กลับเข้าไปดูงานที่ทำค้างไว้ได้เหมือนไม่เคยหลุด

tmux พื้นฐานที่ต้องรู้

คำสั่งใช้ทำอะไร
tmux new -s workสร้าง session ใหม่ชื่อ work
Ctrl-b แล้วกด dDetach — ออกจาก session โดยไม่ปิด process ข้างใน
tmux lsดูรายชื่อ session ที่กำลังรันอยู่ทั้งหมด
tmux attach -t workAttach กลับเข้า session ที่ detach ไว้
tmux kill-session -t workปิด session ทิ้งถาวร (process ข้างในตายด้วย)
⚠️ ข้อควรระวัง: Ctrl-b d คือ detach (ปลอดภัย งานยังรันต่อ) ส่วน exit หรือ Ctrl-d ภายใน shell ของ tmux pane คือปิด pane นั้นทิ้งจริง — อย่าสับสนสองอย่างนี้ ถ้าพิมพ์ exit ตอน Claude Code กำลังทำงานอยู่ งานจะถูก kill ทันที

Workflow จริง: Claude Code ผ่าน tmux บน remote server

ขั้นตอนเต็มของการรัน Claude Code แบบยาวๆ บน remote server โดยไม่กลัว SSH หลุด:

# 1. SSH เข้า server ตามปกติ
ssh user@remote-server

# 2. สร้าง tmux session แล้วรัน Claude Code ข้างใน
tmux new -s claude-work
claude
# ... คุยงานกับ Claude Code ตามปกติ อาจใช้เวลานาน ...

# 3. อยากออกไปทำอย่างอื่นแต่ไม่อยากให้งานหยุด
#    กด Ctrl-b แล้วกด d (detach) — กลับสู่ shell ปกติ
#    session ยังรันอยู่เบื้องหลัง แม้ปิด SSH ไปแล้ว

# 4. กลับมาดูทีหลัง (แม้ SSH connection เดิมหลุดไปแล้วก็ตาม)
ssh user@remote-server
tmux attach -t claude-work
# กลับเข้าไปเห็น Claude Code ตรงจุดที่ค้างไว้เป๊ะ

Pattern นี้เหมาะกับงานยาว (refactor ข้ามคืน, migration หลายขั้นตอน) หรือเมื่อทำงานจาก network ที่ไม่เสถียร (WiFi หลุดบ่อย, VPN ตัด)

รันหลายงานพร้อมกันด้วยหลาย tmux session

tmux ยังทำให้รันหลายงานคู่ขนานได้ง่าย โดยแยก session ตามโปรเจกต์หรือ task:

# ตั้งชื่อ session ให้สื่อความหมาย แยกงานตามโปรเจกต์/task
tmux new -s frontend-fix -d    # -d = สร้างแบบ detached ทันที ไม่ต้องเข้าไปก่อน
tmux new -s backend-refactor -d
tmux new -s db-migration -d

# ดูว่ามีอะไรรันอยู่บ้าง
tmux ls
# frontend-fix: 1 windows ...
# backend-refactor: 1 windows ...
# db-migration: 1 windows ...

# ส่งคำสั่งเข้า session โดยไม่ต้อง attach ก่อน (ใช้บ่อยเวลา automate/monitor จากภายนอก)
tmux send-keys -t frontend-fix 'claude -p "fix the failing test in Button.test.tsx"' Enter

# ตรวจความคืบหน้าแบบไม่ต้อง attach เข้าไปเต็มๆ
tmux capture-pane -t frontend-fix -p -S -30
💡 เกี่ยวข้องกับ Module 07: Pattern tmux send-keys + capture-pane นี้เป็นรากฐานเดียวกับที่ Module 07 (Multi-Agent Orchestration) ใช้ตอน spawn หลาย Claude Code instance พร้อมกัน — ต่างกันแค่ที่นี่คุณเป็นคนสั่งเอง ส่วน Module 07 ให้ agent อื่นเป็นคนสั่งแทน
