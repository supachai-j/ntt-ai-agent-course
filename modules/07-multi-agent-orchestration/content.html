Multi-Agent Orchestration

เมื่อไหร่ควรแตกงานเป็นหลาย agent, วิธีสร้าง/เรียกใช้ Claude Code subagents, การรัน parallel instances อย่างปลอดภัย, และหลักการ verify ก่อนเชื่อผลลัพธ์จาก subagent เสมอ

TL;DR: ใช้ multi-agent เมื่อ context ล้น, งาน independent รันขนานได้, หรือต้องการ specialist role — สร้าง subagent ผ่าน .claude/agents/*.md (static) หรือ --agents flag (dynamic), รัน parallel งานผ่าน tmux session แยกกัน แต่ห้ามขนานงานที่มี dependency ระหว่างกัน และไม่ว่า pattern ไหนก็ต้อง verify evidence จริงก่อนเชื่อว่า subagent ทำสำเร็จ — ไม่ใช่แค่เชื่อ self-report

เมื่อไหร่ต้องใช้ Multi-Agent

ไม่ใช่ทุกงานที่ต้องแตกเป็นหลาย agent — การเพิ่ม agent เพิ่ม complexity, overhead ในการ coordinate, และความเสี่ยงเรื่อง context ที่ไม่ sync กัน ควรประเมินก่อนว่างานตรงกับเงื่อนไขไหน

Single agent พอแล้ว เมื่องานเป็น sequential เดียวที่ context เล็ก, งานที่ต้อง maintain state ต่อเนื่องตลอดการทำงาน (เช่น debug ที่ต้องจำ hypothesis ก่อนหน้า), หรือ debug/fix เฉพาะจุดในไฟล์เดียวที่ไม่ต้องการมุมมองจากหลาย role

ต้องแตกเป็น Multi-Agent เมื่อ context ใหญ่เกินจะยัดใน context window เดียวได้อย่างมีประสิทธิภาพ, งานเป็น independent ที่รันขนานกันได้จริง (parallelizable), หรือต้องการ specialist role ที่แยกจากกัน เช่น security reviewer, test writer, docs writer ที่แต่ละตัวมี system prompt/focus แคบของตัวเอง

3 สัญญาณหลักที่บอกว่าถึงเวลาแตก Agent

1. Context overflow — งานมีไฟล์หรือสเปกเยอะจนโมเดลลืม instruction ตอนต้น หรือ performance ตกลงเมื่อ context ยาวเกินไป นี่คือสัญญาณว่าควรแตกงานให้แต่ละ agent รับผิดชอบ context ส่วนที่เล็กลง

2. Parallelizable independent tasks — งาน A ไม่ต้องรอผลของงาน B เลย เช่น เขียน README.md กับเขียน unit test ให้อีกไฟล์หนึ่ง เป็นงานที่ไม่ share state หรือ interface ระหว่างกัน สามารถรันพร้อมกันได้อย่างปลอดภัย

3. Role specialization — อยากได้ persona หรือ system prompt ที่ focus แคบเฉพาะเรื่อง เช่น "review เฉพาะ security" แทนที่จะให้ agent ตัวเดียวสวมหลายหมวก (เขียนโค้ด + review + เขียน docs ในตัวเดียว) ซึ่งทำให้ quality ของแต่ละบทบาทลดลง

Claude Code Custom Subagents

Claude Code รองรับการสร้าง subagent แบบ static โดยเก็บเป็นไฟล์ Markdown ที่มี YAML frontmatter ไว้ในโฟลเดอร์ .claude/agents/*.md ของ repo แต่ละไฟล์นิยาม 1 subagent ที่มี system prompt, model, และ tool access ของตัวเอง แยกจาก context ของ main conversation โดยสมบูรณ์

---
name: reviewer
description: Reviews code for security issues, bad practices, and style violations. Use proactively after writing or editing code.
model: sonnet
tools: Read, Grep, Glob
---

You are a senior security-focused code reviewer.
Review the diff or files given for:
- Injection risks (SQL, command, template)
- Secrets/credentials committed in plaintext
- Missing input validation
- Unsafe deserialization

Report findings as a list with severity (critical/high/medium/low),
file:line reference, and a concrete fix suggestion. Do not modify files.
💡 สังเกตว่า tools ถูกจำกัดเหลือแค่ Read, Grep, Glob — subagent นี้ไม่มี write access เลย เพราะหน้าที่ของมันคือ "review" ไม่ใช่ "fix" การจำกัด tools แบบนี้ช่วยลดความเสี่ยงที่ subagent จะแก้ไฟล์โดยไม่ได้ตั้งใจ

เรียกใช้ Subagent: Static @name vs Dynamic --agents

มีสองวิธีหลักในการเรียกใช้ subagent ใน Claude Code

Static agent (ไฟล์ .md) — เรียกด้วย @name ตรงในบทสนทนา Claude Code จะโหลด system prompt และ tools ที่ระบุไว้ใน frontmatter ของไฟล์นั้น แล้วรันเป็น subagent ที่แยก context ออกจาก conversation หลัก

› @reviewer check this diff for security issues

Dynamic agent (CLI flag) — กำหนด agent ชั่วคราวตอนรัน CLI ผ่าน flag --agents โดยส่ง JSON ที่นิยาม description, prompt, tools แบบ inline โดยไม่ต้องสร้างไฟล์ในระบบเลย เหมาะกับ automation/CI ที่ agent definition อาจ generate แบบ dynamic ตาม pipeline

claude -p "review auth.py" \
  --agents '{"reviewer":{"description":"security reviewer","prompt":"You are a security reviewer...","tools":["Read","Grep"]}}'

Subagent Frontmatter Fields

YAML frontmatter ของไฟล์ subagent มี field หลักดังนี้:

Fieldความหมาย
nameชื่อที่ใช้เรียกด้วย @name
descriptionบอก Claude Code ว่า agent นี้ทำอะไร ใช้ตอนไหน — ใช้สำหรับ auto-delegation ที่ Claude Code จะเลือก subagent ที่เหมาะสมให้อัตโนมัติ
modelโมเดลที่ subagent นี้ใช้ (เช่น sonnet, opus) — เลือกให้เหมาะกับความซับซ้อนของงานและ cost ที่ยอมรับได้
toolsจำกัด tool ที่ subagent เข้าถึงได้ — ตัด write access ถ้า subagent ไม่จำเป็นต้องแก้ไฟล์ ลด blast radius หากมี error

Parallel Claude Instances ผ่าน tmux

เมื่อมีหลาย independent task ที่อยากรันพร้อมกันจริงๆ (ไม่ใช่ subagent ภายใน conversation เดียว แต่เป็น process Claude Code แยกกันเลย) วิธีหนึ่งที่ใช้ได้จริงคือรันแต่ละ task ใน tmux session ของตัวเอง แล้ว monitor ผลลัพธ์แบบ async

# สร้าง session แยกสำหรับแต่ละงาน
tmux new-session -d -s task-readme "claude -p 'write README.md for this repo' > out-readme.log"
tmux new-session -d -s task-tests  "claude -p 'write unit tests for utils.py' > out-tests.log"

# monitor ผลแบบ loop
for s in task-readme task-tests; do
  echo "=== $s ==="
  tmux capture-pane -t "$s" -p | tail -20
done

# เช็คว่า session จบหรือยัง แล้ว kill session ที่ค้าง
tmux list-sessions
tmux kill-session -t task-readme
💡 การ capture-pane และ tail แบบนี้ให้ผลลัพธ์ล่าสุดของแต่ละ session โดยไม่ต้อง attach เข้าไปดูตรงๆ ทำให้ script อัตโนมัติสามารถ poll สถานะของหลาย task พร้อมกันได้

⚠️ Anti-pattern: Dependency Race Condition

ข้อผิดพลาดที่พบบ่อยที่สุดเมื่อเริ่มใช้ parallel agent คือการขนานงานที่มี dependency ระหว่างกันโดยไม่รู้ตัว

❌ อย่าทำ: รัน "เขียน API endpoint" กับ "เขียน integration test ที่เรียก endpoint นั้น" แบบขนานกัน — เพราะ task B (เขียน test) อาจ generate เสร็จก่อนที่ task A จะสร้าง endpoint จริงเสียอีก ผลที่ได้คือ test อ้าง function signature ที่ยังไม่มีอยู่จริง หรือ mock ที่ผิดเพี้ยนไปจาก implementation จริงที่ task A สร้างขึ้นมาทีหลัง
✅ ทำแบบนี้: งานที่มี dependency ต้องรัน sequential เท่านั้น (A เสร็จสมบูรณ์ก่อนจึงเริ่ม B) หรือให้ agent เดียวทำทั้งคู่ต่อกันเพื่อรักษา context ต่อเนื่องระหว่าง endpoint และ test เฉพาะงานที่ independent จริงๆ — ไม่ share state และไม่ share interface ระหว่างกัน — ถึงจะปลอดภัยพอที่จะรันขนานได้

Hermes delegate_task Pattern

หลักการเดียวกันกับ Claude Code custom subagents นำมาใช้กับ Hermes ผ่าน delegate_task ได้เช่นกัน — เทียบเคียงกับสิ่งที่เคยพูดถึงใน Module 02 (Hermes Architecture):

Isolated context — subagent ที่ถูก delegate ไปไม่เห็น conversation history ของ parent agent เลย มันเริ่มต้นจาก context ที่ว่างเปล่า (หรือเกือบว่างเปล่า) ทุกครั้ง

ต้องส่ง context ที่จำเป็นทั้งหมด — เพราะ subagent ไม่ได้ "จำ" อะไรมาก่อนจาก parent agent เลย ดังนั้น path ของไฟล์ที่เกี่ยวข้อง, spec ของงาน, และ constraint ทุกอย่างต้องถูกระบุไว้อย่างชัดเจนใน task prompt ที่ส่งไป การละเลยส่วนนี้เป็นสาเหตุอันดับหนึ่งที่ subagent ทำงานผิดพลาดหรือทำงานที่ไม่ตรงกับที่ต้องการ

ผลลัพธ์เป็น self-report — เมื่อ subagent จบงาน มันจะสรุปกลับมาว่า "ทำสำเร็จแล้ว" แต่นั่นเป็นเพียงคำบอกเล่าของ subagent เอง ไม่ใช่หลักฐานที่ยืนยันได้ subagent อาจ hallucinate ว่าทำสำเร็จทั้งที่จริงมี error เกิดขึ้น หรือไฟล์ที่ควรถูกสร้างไม่ถูกสร้างขึ้นจริง

💡 หลักการร่วม: Verify ก่อนเชื่อ — ไม่ว่าจะเป็น Claude Code subagent หรือ Hermes subagent parent agent ต้องตรวจสอบ evidence จริงเสมอ เช่น ไฟล์ที่มีอยู่จริงในระบบไฟล์, test ที่รันผ่านจริง, หรือ output ที่สามารถ diff ได้ ก่อนที่จะถือว่างานนั้นเสร็จสมบูรณ์

ทำไมต้อง Verify เสมอ

พฤติกรรมบางอย่างที่ดูสะดวกแต่มีความเสี่ยงสูงเมื่อทำงานกับ subagent:

พฤติกรรมเสี่ยงทำไมอันตราย
เชื่อ log "Done" จาก subagent ทันทีSubagent อาจ hallucinate ว่าทำสำเร็จ ทั้งที่ error หรือไฟล์ไม่ถูกสร้างขึ้นจริง
ไม่เปิดไฟล์ output จริงมาตรวจเนื้อหาอาจไม่ตรงสเปกที่ต้องการ หรือมี syntax ผิดที่ log ไม่ได้บอกไว้เลย
ไม่รัน test/lint หลัง subagent เสร็จงานCode อาจ compile ไม่ผ่าน แต่ subagent รายงานกลับมาว่าเขียนเสร็จเรียบร้อยแล้ว

🔍 Second Look: Spawn Sub-Agents ให้ Deep Review ก่อน Commit

อีกวิธีใช้ subagent ที่ต่างจากการเรียก @reviewer ตัวเดียวรีวิวไฟล์เดียว คือการสั่ง main agent ให้ spawn sub-agents หลายตัวเพื่อรีวิวทั้งโปรเจกต์ที่ถูกกระทบแบบอิสระ ไม่ใช่มองแค่ diff ในไอโซเลชัน แต่ให้มองพื้นที่ของโค้ดทั้งหมดที่เกี่ยวข้องกับ feature นั้นว่ามี bug, ความไม่สอดคล้องกัน, หรือ requirement ที่ตกหล่นไปหรือไม่

Workflow คร่าวๆ: implement feature เสร็จ → สั่ง main agent "spawn several sub-agents to do a deep review of the entire project with this feature change" → sub-agents รายงานกลับมาเป็น consolidated list → triage findings → แก้ไฟล์จริงถ้าเจอปัญหา → รัน test อีกครั้ง → แล้วค่อย commit/merge

สองเหตุผลที่เทคนิคนี้ต่างจากการให้ agent ตัวเดิม self-review งานตัวเอง:

1. Thinking space — sub-agent ที่ spawn มาใหม่ได้ context window สะอาด ใช้เฉพาะสำหรับงานรีวิวเท่านั้น ในขณะที่ agent หลักที่เพิ่ง implement เสร็จ context เต็มไปด้วย history ของการเขียนโค้ด ทำให้ self-review มักหลวมกว่า

2. รักษา context window ของ main agent — sub-agents ทำ review pass แบบยาวๆในพื้นที่ของตัวเอง แล้วส่งกลับมาแค่สรุปสั้นๆ (consolidated findings) เข้า context หลัก ไม่ใช่เอา full review ทั้งหมดไปยัดใส่จนแน่น

💡 เก็บเทคนิคนี้ไว้เป็น "second look" สำหรับ feature ที่สำคัญพอจะกังวลว่าอาจมีจุดที่มองข้ามไป ไม่จำเป็นต้องใช้เฉพาะงานใหญ่เท่านั้น — ที่มา: youtu.be/hy8UstR2NEg (DeepLearning.AI × JetBrains)

Agent Teams (Advanced)

นอกเหนือจาก subagent เดี่ยวๆ และ parallel tmux แล้ว Claude Code ยังรองรับโหมด multi-agent แบบ collaborative ที่ agent หลายตัวทำงานร่วมกันเป็นทีมและแชร์สถานะระหว่างกันได้ ผ่าน flag ระดับ advanced

claude --teammate-mode --brief "coordinate with other agents on this refactor"

--teammate-mode เปิดโหมดให้ agent ทำงานร่วมกันเป็นทีม แชร์สถานะระหว่างกันได้ ในขณะที่ --brief เป็นข้อความสั้นสำหรับ SendUserMessage ที่ agent อื่นในทีมสามารถเห็นได้ ทำให้เกิดการประสานงานระหว่าง agent หลายตัวแบบใกล้เคียง real-time

💡 Agent Teams เป็น feature ขั้นสูงที่เหมาะกับ workflow ที่ต้องประสานงาน agent หลายตัวอย่างจริงจัง — แนะนำให้เริ่มจากการใช้ subagent เดี่ยวและ parallel ผ่าน tmux ให้คล่องตัวก่อนที่จะขยับไปใช้ Agent Teams
