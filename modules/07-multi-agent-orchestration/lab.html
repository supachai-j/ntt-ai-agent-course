Lab · Module 07

Multi-Agent Orchestration

สร้าง custom subagent จริงสำหรับ code review, เรียกใช้ผ่าน @reviewer, แล้วรัน 2 งาน Claude Code print-mode แบบขนานจริงด้วย background terminal — จบด้วยการ verify ผลลัพธ์ทั้งสองงานด้วยหลักฐานจริง ไม่ใช่แค่เชื่อ log

⏱ ~50 นาที 🖥 ต้องมี Claude Code CLI ติดตั้งแล้ว 📦 ต้องมี tmux ติดตั้งแล้ว 🔧 ระดับ: Intermediate

Prerequisites

  • Claude Code CLI ติดตั้งและ authenticate แล้ว (ดู Module 03)
  • tmux ติดตั้งในเครื่อง — เช็คด้วย tmux -V
  • มี git repo ทดสอบ (จะสร้าง scratch repo ใหม่ในแล็บนี้ก็ได้)
  • เข้าใจพื้นฐาน subagent/context isolation จาก slides ของ module นี้

Objectives

  • สร้าง custom subagent .claude/agents/reviewer.md พร้อม frontmatter ที่ถูกต้อง
  • เรียกใช้ subagent ด้วย @reviewer ใน interactive session จริง
  • รัน 2 Claude Code print-mode task แบบขนานผ่าน background terminal process (tmux)
  • Verify ผลลัพธ์ทั้งสองงานด้วยการเปิดไฟล์ output จริง ไม่เชื่อ log อย่างเดียว
  • รู้จัก failure mode: tmux session ค้าง/ลืม kill และวิธีแก้

1เตรียม scratch project

สร้างโฟลเดอร์ทดสอบแยกจากงานจริง เพื่อไม่ให้ subagent แก้ไฟล์ที่สำคัญโดยไม่ตั้งใจ

mkdir -p ~/lab07-multiagent && cd ~/lab07-multiagent
git init -q
mkdir -p .claude/agents
echo "def add(a, b):
    return a + b

def divide(a, b):
    return a / b
" > utils.py
git add -A && git commit -q -m "init scratch repo for lab 07"
Verify: รัน ls -la .claude/agents utils.py — ต้องเห็นโฟลเดอร์ .claude/agents ว่างเปล่า และไฟล์ utils.py มีเนื้อหาตามด้านบน

2สร้าง custom subagent: reviewer

เขียนไฟล์ Markdown พร้อม YAML frontmatter — name/description/model/tools ตามสเปกของ Claude Code custom agents

cat > .claude/agents/reviewer.md << 'EOF'
---
name: reviewer
description: Reviews code for correctness, edge cases (e.g. division by zero), and security issues. Use proactively after code changes.
model: sonnet
tools: Read, Grep, Glob
---

You are a senior code reviewer. When given a file or diff to review:

1. Check for unhandled edge cases (null/zero/empty input, off-by-one, etc.)
2. Check for security issues (injection, unsafe eval, secrets in code)
3. Check for missing input validation and error handling

Report findings as a bullet list with severity (critical/high/medium/low),
exact file:line reference, and a concrete one-line fix suggestion.
Do NOT edit files — you only have read-only tools. Report only.
EOF
Verify: cat .claude/agents/reviewer.md — ต้องเห็น frontmatter ที่ parse เป็น YAML ได้ (มี --- เปิด-ปิด, name:, description:, model:, tools: ครบ)

3เรียกใช้ @reviewer ใน interactive session

เปิด Claude Code แบบ interactive ในโฟลเดอร์นี้ แล้วเรียก subagent ด้วย @reviewer ตรงในพรอมต์

cd ~/lab07-multiagent
claude

ในพรอมต์ interactive พิมพ์:

› @reviewer review utils.py for edge cases and issues

Claude Code จะ spawn subagent reviewer ด้วย system prompt และ tools ตามที่กำหนดไว้ ผลที่ควรได้: subagent ชี้ว่า divide(a, b) ไม่ได้เช็ค b == 0 ซึ่งจะ raise ZeroDivisionError

Verify: อ่าน output จาก subagent จริง — ต้องมีการชี้ severity + file:line ของ divide ที่ระบุปัญหา division-by-zero ชัดเจน ถ้า subagent ตอบทั่วๆไปไม่ชี้ปัญหานี้ แสดงว่า tools/frontmatter ตั้งผิด ให้กลับไปเช็ค step 2
ข้อสังเกต: subagent มี tools: Read, Grep, Glob เท่านั้น — ไม่มี Write/Edit เพราะฉะนั้นมันจะ "รายงานปัญหา" ไม่ใช่ "แก้ไฟล์" ถ้าอยากให้แก้ต้องเปลี่ยน tools list เอง

4เตรียม 2 งาน independent สำหรับรันขนาน

เลือกงานที่ ไม่มี dependency ระหว่างกัน — งานที่ 1 เขียน README, งานที่ 2 เขียน unit test ทั้งสองอ่าน utils.py เหมือนกันแต่ไม่แก้ไฟล์เดียวกัน ไม่ต้องรอผลกัน จึงปลอดภัยที่จะขนาน 

mkdir -p out
# ทดสอบว่า claude print mode ใช้ได้
claude --version
Verify: claude --version ต้องคืนเลขเวอร์ชันโดยไม่ error ก่อนไปขั้นถัดไป

5รัน 2 tmux session ขนานกันจริง

แต่ละงานแยก tmux session ของตัวเอง รันเป็น background process จริง ไม่ block terminal หลัก

cd ~/lab07-multiagent

tmux new-session -d -s task-readme \
  "claude -p 'Read utils.py and write a README.md documenting the add() and divide() functions, including their signatures and any known edge cases. Save it as README.md in the current directory.' --allowedTools Read,Write > out/readme.log 2>&1"

tmux new-session -d -s task-tests \
  "claude -p 'Read utils.py and write pytest unit tests for add() and divide(), including a test for division by zero raising ZeroDivisionError. Save as test_utils.py in the current directory.' --allowedTools Read,Write > out/tests.log 2>&1"

tmux list-sessions

ต้องเห็น session ชื่อ task-readme และ task-tests ทั้งคู่ในลิสต์

Verify: tmux list-sessions แสดงทั้งสอง session — ถ้าเห็นแค่ session เดียวหรือ error แปลว่า tmux ตัวก่อนไม่ได้ detach (-d) ถูกต้อง หรือชื่อ session ชนกัน

6Monitor ด้วย loop tmux capture-pane

เช็คความคืบหน้าของทั้งสอง session โดยไม่ต้อง attach เข้าไปแบบ interactive

for s in task-readme task-tests; do
  if tmux has-session -t "$s" 2>/dev/null; then
    echo "=== $s: still running ==="
    tmux capture-pane -t "$s" -p | tail -15
  else
    echo "=== $s: session ended (task finished or crashed) ==="
  fi
  echo
done

รันคำสั่งนี้ซ้ำทุก 10-15 วินาที (หรือใส่ใน watch) จนทั้งสอง session หาย (แปลว่า process จบแล้ว)

watch -n 10 'tmux list-sessions 2>/dev/null || echo "no sessions left — both tasks finished"'
Verify: รอจน tmux list-sessions คืน error/ว่าง (no server running) — แปลว่า ทั้งสอง process จบแล้วจริง ไม่ใช่แค่ terminal เงียบ

7Verify ผลลัพธ์ทั้งสองงานด้วยหลักฐานจริง

อย่าเชื่อ log ว่า "เสร็จแล้ว" อย่างเดียว — ต้องเปิดไฟล์ output จริงและตรวจเนื้อหา 

# 1. ไฟล์ README.md ต้องมีอยู่จริงและพูดถึงฟังก์ชันทั้งสอง
test -f README.md && echo "README.md exists" || echo "MISSING: README.md"
grep -E "add|divide" README.md

# 2. ไฟล์ test_utils.py ต้องมีอยู่จริงและมี test สำหรับ zero-division
test -f test_utils.py && echo "test_utils.py exists" || echo "MISSING: test_utils.py"
grep -i "zero" test_utils.py

# 3. รัน test จริง — นี่คือหลักฐานที่แน่นอนที่สุด ไม่ใช่แค่อ่าน log
python3 -m pytest test_utils.py -v
Verify: ทั้งสามคำสั่งต้องผ่าน — ไฟล์ต้องมีอยู่จริง เนื้อหาต้องตรงกับงานที่สั่ง และ pytest ต้องรันผ่านจริง (รวม test ที่เช็ค ZeroDivisionError) ถ้าขั้นไหนล้มเหลว = งานยังไม่เสร็จจริง ต่อให้ log บอกว่า "Done" ก็ตาม
อย่าข้ามขั้นนี้: การเชื่อ self-report ของ subagent โดยไม่ verify คือสาเหตุอันดับหนึ่งที่ทำให้ multi-agent workflow ล้มเหลวแบบเงียบๆ — subagent อาจรายงานว่า "สร้างไฟล์แล้ว" ทั้งที่ path ผิด หรือ tool call ถูก permission ปฏิเสธไปเฉยๆ

8Cleanup — kill session ที่เหลือ

ถ้ามี session ใดยังไม่จบ (hang) หรือรันจบแล้วแต่ session ยังไม่ถูกลบ ให้ kill ทิ้งเสมอ

# เช็คว่ามี session หลงเหลือไหม
tmux list-sessions 2>/dev/null

# kill รายตัว ถ้ายังเหลือ
tmux kill-session -t task-readme 2>/dev/null
tmux kill-session -t task-tests 2>/dev/null

# หรือ kill server tmux ทั้งหมดถ้าแน่ใจว่าไม่มีงานอื่นค้างอยู่
# tmux kill-server
Verify: tmux list-sessions ต้องคืน "no server running" หรือว่างเปล่า ก่อนปิดแล็บนี้ — ห้ามทิ้ง session ค้างไว้
Troubleshoot: tmux session ค้าง / ลืม kill

อาการ: รัน tmux list-sessions แล้วเห็น session เก่าจากแล็บก่อนหน้าที่ไม่มีใครไป kill — กิน memory เปล่าๆ หรือแย่กว่านั้นคือ process ข้างในยัง "ทำงาน" อยู่โดยที่คุณไม่รู้ตัว (เช่น เขียนไฟล์ทับของเดิมโดยไม่ได้ตั้งใจ)

วิธีเช็คและแก้:

# ดู session ทั้งหมดที่รันอยู่ในเครื่อง (ไม่ใช่แค่ของแล็บนี้)
tmux list-sessions

# เข้าไปดูว่า session ไหนยัง active อยู่จริง ทำอะไรอยู่
tmux capture-pane -t <session-name> -p | tail -30

# kill รายตัวที่ไม่ต้องการแล้ว
tmux kill-session -t <session-name>

# ถ้าจำชื่อไม่ได้เลยและมั่นใจว่าไม่มีงานสำคัญค้างอยู่ — ปิดทุก session รวดเดียว
tmux kill-server

ป้องกันไว้ก่อน: ตั้งชื่อ session ให้สื่อความหมายและมี timestamp/task-id เสมอ (เช่น task-readme-20240115) และปิดท้าย workflow ทุกครั้งด้วยขั้นตอน cleanup (step 8) อย่าปล่อยให้เป็น "manual step ที่ลืมได้" — ถ้าทำเป็น script ให้ใส่ trap 'tmux kill-session -t $SESSION' EXIT ใน wrapper script เพื่อ kill อัตโนมัติแม้ script fail กลางทาง

สรุป & ต่อยอด

ในแล็บนี้คุณสร้าง custom subagent จริงที่จำกัด tools เฉพาะ read-only สำหรับงาน review, เรียกใช้มันผ่าน @reviewer ในเซสชัน interactive, และรันสองงานที่ independent จริง (README กับ test) แบบขนานผ่าน tmux background process — จุดสำคัญที่สุดคือขั้น verify: การเปิดไฟล์จริงและรัน pytest จริง คือสิ่งที่แยก "งานเสร็จจริง" จาก "log บอกว่าเสร็จ"

ต่อยอด: ลองสร้าง subagent เพิ่มอีกตัว (เช่น docs-writer) แล้วให้ทั้งสามตัวทำงานร่วมกันในโฟลว์เดียว — แต่ระวัง anti-pattern จาก slides: ถ้างานสองอันมี dependency กัน (เช่น subagent เขียน endpoint ใหม่ กับ subagent เขียน integration test เรียก endpoint นั้น) ต้องรัน sequential ไม่ใช่ขนาน ลองทดลองสร้างสถานการณ์ dependency แบบนี้ดูว่า race condition เกิดขึ้นจริงยังไงเมื่อรันขนานผิดๆ
