AI Agents 101

พื้นฐาน agentic loop, tool use, ความต่างจาก chatbot ธรรมดา และเหตุผลที่องค์กรต้องลงทุนเรื่อง AI agents

TL;DR: Agent ไม่ใช่ LLM ที่ฉลาดกว่า แต่คือ LLM ที่ทำงานผ่าน agentic loop (observe → plan → act → observe) ร่วมกับ system prompt, tools, memory และ loop controller — ทำให้ทำงานหลายขั้นตอนอัตโนมัติได้จริงแทนที่จะตอบครั้งเดียวจบแบบ chatbot ธรรมดา มีประโยชน์ชัดเจนทั้งฝั่ง presale และ engineering แต่ต้องระวัง hallucination, สิทธิ์ tool ที่กว้างเกินไป และต้องมี human-in-the-loop สำหรับ action ที่ irreversible เสมอ

LLM call ธรรมดา คืออะไร

ก่อนจะเข้าใจว่า agent คืออะไร ต้องเข้าใจก่อนว่า LLM call แบบธรรมดา (single-turn inference) ทำงานยังไง: เราส่ง prompt เข้าไป โมเดลประมวลผลแล้วตอบกลับมาครั้งเดียว แล้วจบการทำงานตรงนั้น ไม่มีการวนซ้ำ ไม่มีการเรียกอะไรต่อ 

User: "สรุป email นี้ให้หน่อย"
LLM:  [สรุปข้อความ] → จบการทำงาน

จุดสำคัญคือ โมเดลในโหมดนี้ ไม่รู้จักโลกภายนอก — มันไม่สามารถไปอ่านไฟล์จริงในเครื่อง เรียก API ภายนอก หรือรันคำสั่ง terminal เองได้ ทุกอย่างที่มันตอบมาจากสิ่งที่อยู่ใน prompt/context กับความรู้ที่ถูก train มาเท่านั้น นี่คือสิ่งที่ chatbot ทั่วไปหลายตัวทำงานอยู่

💡 ถ้าคุณเคยใช้ ChatGPT/Claude แบบถาม-ตอบธรรมดาไม่เปิด tool ใดๆ นั่นคือ single-turn inference — ไม่ใช่ agent

สิ่งที่ทำให้เป็น "Agent"

สิ่งที่แยก agent ออกจาก LLM call ธรรมดา ไม่ใช่โมเดลที่ฉลาดกว่า แต่คือสถาปัตยกรรมที่ห่อหุ้ม โมเดลไว้ เรียกว่า agentic loop ซึ่งประกอบด้วย 4 ขั้นตอนที่วนซ้ำไปเรื่อยๆ:

  1. Observe — ดู state ปัจจุบัน หรือรับ user request เข้ามา
  2. Plan — ตัดสินใจว่าต้องทำอะไรต่อไป เพื่อเข้าใกล้เป้าหมาย
  3. Act — เรียก tool หรือ function call จริง เพื่อลงมือทำ
  4. Observe result — ดูผลลัพธ์ที่ได้กลับมาจาก tool นั้น

จากนั้นวนกลับไปที่ข้อ 1 ใหม่อีกครั้ง โดยใช้ผลลัพธ์ล่าสุดเป็นข้อมูลในการ plan รอบถัดไป กระบวนการนี้จะวนต่อไปเรื่อยๆ จนกว่างานจะเสร็จสมบูรณ์ หรือจนกว่าจะถึง limit ที่กำหนดไว้ (เช่น จำนวนรอบสูงสุด หรือ timeout) เพื่อป้องกันไม่ให้ agent วน loop ไม่จบ

💡 กุญแจสำคัญ: agent = LLM + loop ที่ให้มันสังเกต-วางแผน-ลงมือทำ-สังเกตผลซ้ำๆ ไม่ใช่แค่โมเดลรุ่นใหม่กว่าเดิม

Agentic Loop ในทางปฏิบัติ: ตัวอย่าง restart service

ลองดูตัวอย่างการทำงานจริงของ agentic loop เมื่อ user สั่งงานที่ต้องใช้หลาย tool call ต่อเนื่องกัน และ agent ต้องตัดสินใจเองว่าจะเรียกอะไรต่อจากผลลัพธ์ที่ได้ในแต่ละรอบ: 

User: "เช็คว่า service X down อยู่ไหม แล้ว restart ถ้า down"

Loop:
  observe → user request
  plan    → ต้องเรียก tool "check_status" ก่อน
  act     → check_status("service-x")
  observe → result: "down"
  plan    → ต้องเรียก tool "restart_service"
  act     → restart_service("service-x")
  observe → result: "restarted, status: up"
  plan    → งานเสร็จแล้ว ไม่ต้องเรียก tool เพิ่ม
  → ตอบ user: "restart สำเร็จ service กลับมา up แล้ว"

สังเกตว่า agent ไม่ได้ถูกบอกล่วงหน้าว่าต้องเรียก tool ไหนบ้างตามลำดับตายตัว มันตัดสินใจเองใน แต่ละรอบของ loop โดยอิงจากผลลัพธ์ (observation) ล่าสุด — ถ้า check_status คืนค่า "up" อยู่แล้ว agent ก็จะ plan ต่างออกไป (ไม่เรียก restart_service) และตอบ user ไปเลยว่าไม่ต้องทำอะไร นี่คือความยืดหยุ่นที่ chatbot ธรรมดาทำไม่ได้

องค์ประกอบหลักของ agent

Agent ที่ใช้งานได้จริงประกอบด้วย 4 ส่วนหลัก ซึ่งทำงานร่วมกันเพื่อขับเคลื่อน agentic loop:

องค์ประกอบหน้าที่
System prompt / instructionsกำหนดบทบาท ขอบเขต และกติกาการทำงานของ agent ตั้งแต่ต้น — เช่น agent นี้ทำอะไรได้/ไม่ได้ ควรตอบสไตล์ไหน
Available toolsความสามารถในการ function calling — อ่าน/เขียนไฟล์, เรียก API ภายนอก, รันคำสั่ง terminal และอื่นๆ ที่ทำให้ agent แตะโลกภายนอกได้จริง
Memory / contextเก็บ conversation history, เอกสารที่ retrieve มา, และ state ระหว่างการวน loop เพื่อให้ agent จำได้ว่าทำอะไรไปแล้วบ้าง
Loop controllerกลไกที่ตัดสินใจว่ารอบถัดไปควรเรียก tool ไหน หรือควรหยุด loop แล้วตอบ user ไปเลย
💡 ถ้าขาดองค์ประกอบไหนไป agent จะทำงานได้ไม่ครบ เช่น มี tools แต่ไม่มี memory จะลืมว่าทำอะไรไปแล้วในรอบก่อนหน้า

Chatbot ธรรมดา vs Agent

เพื่อให้เห็นความต่างชัดเจนขึ้น เทียบคุณสมบัติหลักของทั้งสองแบบ:

Chatbot ธรรมดาAgent
Single-turn — ตอบครั้งเดียวจบMulti-turn tool use — วน loop จนงานเสร็จ
ไม่มี tool / ไม่แตะโลกภายนอกเรียก tool จริง: ไฟล์, API, terminal, DB
ผู้ใช้ต้องทำ step ต่อไปเองทำงานหลายขั้นตอนอัตโนมัติ
ไม่มี state ระหว่าง turnเก็บ context/observe result เพื่อวางแผนต่อ
เหมาะกับ Q&A, สรุปข้อความเหมาะกับงานที่ต้องลงมือทำจริง

ทำไมองค์กรต้องสนใจเรื่องนี้

Agent มีประโยชน์ในหลายบทบาทขององค์กร โดยเฉพาะสองฝั่งหลักที่คอร์สนี้เน้น:

Presale: ช่วย research ข้อมูลคู่แข่ง/ลูกค้า, drafting proposal เบื้องต้น, สรุป requirement จาก meeting notes ให้เร็วขึ้น — งานที่เดิมต้องใช้เวลาหลายชั่วโมงในการอ่านและสรุปเอกสาร สามารถให้ agent ช่วยร่นเวลาได้มาก

Engineering: เขียนโค้ด, debug, review PR, deploy อัตโนมัติ, ลด manual toil ในงาน routine เช่น log analysis, config check — งานที่ทำซ้ำๆ ตามรูปแบบเดิมแต่ต้องใช้เวลา เหมาะกับการให้ agent รับช่วงทำแทน

ตัวอย่างงานจริงที่ agent ช่วยได้ในแต่ละบทบาท:

  • Engineer: "หา bug ที่ทำให้ test นี้ fail แล้ว fix ให้" — agent อ่านโค้ด, รัน test, แก้, รันซ้ำ
  • Presale: "สรุป pain point ลูกค้าจาก transcript นี้ แล้วร่าง outline proposal" — agent ค้น, สรุป, ร่าง draft
  • Ops: "ตรวจ log 24 ชม.ที่ผ่านมา หา anomaly แล้วสรุปเป็น report" — agent วน query + สรุปอัตโนมัติ

จุดร่วมของทั้ง 3 ตัวอย่าง: เป็นงานที่มีหลายขั้นตอน ทำซ้ำได้ แต่ยังต้องใช้ "การตัดสินใจ" ระหว่างทาง — นี่คือจุดที่ agent ทำได้ดีกว่า automation script แบบตายตัว เพราะ agent ปรับ plan ตาม observation ที่ได้ในแต่ละรอบ

ความเสี่ยง/ข้อจำกัดที่ต้องรู้ตั้งแต่ต้น

ก่อนนำ agent ไปใช้งานจริง มีข้อควรระวังสำคัญที่ต้องเข้าใจตั้งแต่แรก:

⚠️ Hallucination — agent อาจสร้างข้อมูล/ผลลัพธ์ที่ดูสมเหตุสมผลแต่ผิดจริง เพราะโมเดลพยายามตอบให้ครบถ้วนแม้ไม่มีข้อมูลจริงรองรับ ต้อง verify ผลลัพธ์สำคัญเสมอ
⚠️ สิทธิ์ tool กว้างเกินไป — การให้ agent เข้าถึง production database หรือ deploy key โดยไม่จำเป็น เพิ่มความเสี่ยงมหาศาลถ้า agent ตัดสินใจผิดพลาดหรือถูก prompt injection หลอกให้ทำสิ่งที่ไม่ควรทำ
⚠️ ต้องมี human-in-the-loop สำหรับ action ที่ irreversible เช่น deploy production, delete ข้อมูล, ส่งอีเมลออกไปหาลูกค้าจริง — action เหล่านี้ต้องมีจุดหยุดรอ human อนุมัติก่อนเสมอ ไม่ควรให้ agent ทำอัตโนมัติ 100%

Landscape เครื่องมือที่คอร์สนี้สอน: Hermes vs Claude Code

คอร์สนี้จะสอนสองเครื่องมือหลักที่ใช้สร้างและ orchestrate agent ในบริบทที่ต่างกัน:

Hermes — agent orchestration platform ที่จัดการ profile, skills, memory, MCP tool layer และ connector (Discord/Telegram/Email) ให้ agent ทำงานแบบ persistent ข้าม session และรองรับหลาย channel พร้อมกัน เหมาะกับงานที่ต้องการ agent ที่ทำงานต่อเนื่อง อยู่เบื้องหลัง หรือต้องคุยผ่านหลายช่องทาง

Claude Code — coding agent CLI ที่รันในเครื่องหรือ CI โดยตรง เข้าถึง filesystem และ terminal ได้ตรงๆ เหมาะกับงาน engineering เช่นเขียนโค้ด, review, refactor, automation ที่ต้องการความเร็วและการเข้าถึงเครื่องแบบตรงไปตรงมา

ทั้งสองเครื่องมือใช้คนละบริบท: Hermes เป็น platform ที่ orchestrate agent หลายตัว/หลาย channel ส่วน Claude Code เป็น agent เดี่ยวที่โฟกัสงานโค้ดในเครื่อง — Module 02 และ Module 03 จะลงลึกในแต่ละตัวตามลำดับ

สรุป

  • Agent = LLM + agentic loop (observe → plan → act → observe) + tools + memory
  • ต่างจาก chatbot ตรงที่ทำงานหลายขั้นตอนอัตโนมัติผ่าน tool call จริง
  • มีประโยชน์ชัดเจนทั้งฝั่ง presale และ engineering แต่ต้องระวัง hallucination และสิทธิ์ tool
  • Action ที่ irreversible ต้องมี human-in-the-loop เสมอ
