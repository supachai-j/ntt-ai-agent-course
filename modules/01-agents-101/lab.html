Lab · Module 01

Lab: ออกแบบ Agentic Loop ของงานจริง

Lab นี้ไม่มี CLI ให้ติดตั้ง (ยังไม่ถึง Claude Code) — เป็น reasoning exercise เชิงปฏิบัติ ให้คุณเลือก use case จริงจากงานตัวเอง (presale หรือ engineering) แล้วแตกออกเป็น agentic loop ลงในไฟล์ markdown จริงบนเครื่อง เพื่อฝึกคิดแบบ agent designer ก่อนเริ่มลงมือ build จริงใน module ถัดไป

⏱ 30-45 นาที ระดับ: เริ่มต้น ต้องมี: terminal, text editor (nano/vim/VS Code) 🎯 Hands-on

สิ่งที่ต้องมีก่อนเริ่ม

  • เครื่องที่มี terminal ใช้งานได้ (macOS/Linux/WSL)
  • Text editor ที่ถนัด — ตัวอย่างในนี้ใช้ nano แต่จะใช้ vim, code หรืออื่นก็ได้
  • Use case งานจริง 1 อย่างในใจ จาก presale หรือ engineering ที่คุณอยากให้ agent ช่วยทำ
  • ไม่ต้องมี API key, ไม่ต้องมี Claude Code — module นี้เป็นการฝึกคิด/ออกแบบล้วนๆ

Learning Objectives

  • อธิบายความต่างระหว่าง chatbot ธรรมดากับ agent ด้วยตัวอย่างของตัวเองได้
  • แตก use case จริง 1 อย่างออกเป็น agentic loop (observe → plan → act → observe) ได้ครบทุกขั้น
  • ระบุ tools ที่ agent ต้องใช้จริง พร้อมเหตุผลว่าทำไมต้องมี tool นั้น
  • กำหนด stopping condition ที่ชัดเจน ไม่ใช่ "ทำจนกว่าจะพอ"
  • ระบุจุดที่ต้องมี human approval ก่อน agent ลงมือทำจริง (โดยเฉพาะ action ที่ irreversible)

1 เตรียม working directory

สร้างโฟลเดอร์สำหรับเก็บงาน lab ของ module นี้ — ใช้ terminal จริง ไม่ใช่แค่คิดในหัว

mkdir -p ~/agent-course-lab01
cd ~/agent-course-lab01
pwd
✅ ตรวจสอบผล: คำสั่ง pwd ต้อง print path ที่ลงท้ายด้วย /agent-course-lab01

2 เลือก use case จริงของตัวเอง

เลือก 1 use case จากงานจริงของคุณ — เกณฑ์คือต้องเป็นงานที่ "มีหลายขั้นตอน" และ "ต้องตัดสินใจระหว่างทาง" ไม่ใช่แค่ single-shot Q&A

ตัวอย่างที่ใช้ได้จริง:

  • Presale: "อ่าน RFP ของลูกค้า สรุป requirement หลัก แล้วร่าง outline proposal เบื้องต้น"
  • Engineering: "หา root cause ของ test ที่ fail ใน CI แล้วเสนอ fix"
  • Ops: "ตรวจ error log 24 ชม.ล่าสุด สรุป anomaly เป็นรายงาน"
✅ ตรวจสอบผล: คุณเขียน use case ของตัวเองเป็นประโยคเดียวได้ (goal ชัดเจน ไม่กำกวม)

3 สร้างไฟล์ markdown สำหรับออกแบบ agent

สร้างไฟล์ .md จริงด้วย editor ในเครื่อง เพื่อเก็บ agent design ของคุณ

nano ~/agent-course-lab01/my-agent-design.md
# (หรือใช้ vim / code แทน nano ก็ได้)
✅ ตรวจสอบผล: ไฟล์ ~/agent-course-lab01/my-agent-design.md ถูกสร้างขึ้น — เช็คด้วย ls -la ~/agent-course-lab01/

4 Copy template ลงไฟล์แล้วกรอกให้ครบ

Copy template ด้านล่างนี้ลงในไฟล์ my-agent-design.md แล้วแก้ทุกส่วนให้ตรงกับ use case ของคุณจริงๆ (ห้ามเว้นว่าง)

# Agent Design: [ชื่อ use case ของคุณ]

## 1. Goal
[Agent นี้มีเป้าหมายอะไร เขียนเป็นประโยคเดียว ชัดเจน วัดผลได้]

## 2. Tools ที่ agent ต้องใช้
- Tool 1: [ชื่อ tool] — [ทำไมต้องมี tool นี้ / ใช้ทำอะไร]
- Tool 2: [ชื่อ tool] — [ทำไมต้องมี tool นี้ / ใช้ทำอะไร]
- Tool 3: [ชื่อ tool] — [ทำไมต้องมี tool นี้ / ใช้ทำอะไร]

## 3. Agentic Loop (observe → plan → act → observe)
1. Observe: [agent เห็น/รับ input อะไรตอนเริ่ม]
2. Plan: [agent ตัดสินใจอะไรต่อ]
3. Act: [agent เรียก tool ไหน ด้วย input อะไร]
4. Observe result: [ผลลัพธ์ที่ agent เห็นหลัง act]
5. (วนซ้ำ step 2-4 จนกว่าจะถึง stopping condition)

## 4. Stopping condition
[Agent จะหยุด/ตอบ user เมื่อไหร่ — ต้องเจาะจง ไม่ใช่ "ทำจนกว่าจะพอ"]

## 5. จุดที่ต้องมี human approval
[Step ไหนที่ agent ต้องหยุดรอ human อนุมัติก่อนทำต่อ โดยเฉพาะ action ที่ irreversible เช่น
deploy, ลบข้อมูล, ส่งอีเมลออกไปหาลูกค้าจริง]
⚠️ ข้อควรระวัง: อย่าเขียน tool กว้างเกินไปแบบ "เข้าถึงทุกอย่าง" — ระบุ tool ให้เจาะจงเท่าที่ agent ต้องใช้จริงเท่านั้น (least privilege) จะเป็นพื้นฐานสำคัญตอนเรียน Module 08 เรื่อง governance

5 ตรวจสอบว่า stopping condition ไม่คลุมเครือ

อ่านข้อ 4 ในไฟล์ของคุณอีกรอบ — ถ้าคำตอบเป็นอะไรทำนอง "จนกว่างานจะเสร็จ" หรือ "จนกว่าจะโอเค" แปลว่ายังไม่เจาะจงพอ ให้แก้ใหม่ให้เป็นเงื่อนไขที่ตรวจสอบได้จริง เช่น "หยุดเมื่อ test suite ผ่านทั้งหมด (exit code 0)" หรือ "หยุดเมื่อ draft proposal มีครบ 3 section: pain point, solution, timeline"

# เปิดไฟล์กลับมาแก้ไข section 4 ถ้ายังคลุมเครือ
nano ~/agent-course-lab01/my-agent-design.md
✅ ตรวจสอบผล: Stopping condition ในไฟล์เป็นประโยคที่ตรวจสอบได้จริง (measurable) ไม่ใช่ความรู้สึก

6 ระบุ human-in-the-loop point สำหรับ action ที่ irreversible

ทบทวนอีกครั้งว่าใน loop ของคุณ มี step ไหนที่ทำแล้วแก้คืนไม่ได้บ้าง (เช่น deploy production, ลบไฟล์/ข้อมูล, ส่ง email ออกไปหาลูกค้าจริง) — step เหล่านั้นต้องมี human approval คั่นก่อนเสมอ

🛑 ระวัง (Irreversible): ถ้า use case ของคุณมี action ที่ irreversible แต่ในไฟล์ section 5 ยังไม่มีจุด human approval คั่นไว้ — ให้กลับไปแก้ก่อน อย่าปล่อยให้ agent ทำ action แบบนี้แบบอัตโนมัติ 100% แม้แต่ในการออกแบบเชิงทฤษฎี

7 ตรวจสอบไฟล์ครบ 4 องค์ประกอบ

เปิดไฟล์อีกครั้งเพื่อ review ทั้งหมด แล้วเช็คด้วยตาว่าครบทุก section

cat ~/agent-course-lab01/my-agent-design.md
✅ ตรวจสอบผล: ไฟล์ต้องมีครบทั้ง 4 องค์ประกอบนี้ (ไม่มีช่องว่าง [ ] ที่ยังไม่ได้กรอก):
  • Goal ชัดเจน วัดผลได้
  • รายการ tools ที่ agent ต้องใช้ พร้อมเหตุผล
  • Agentic loop ครบ 4 ขั้น (observe → plan → act → observe)
  • Stopping condition + human approval point ระบุชัดเจน
ปัญหาที่พบบ่อย: เขียน stopping condition ไม่ออก / รู้สึกว่า loop วนไม่รู้จบ

อาการนี้มักเกิดเพราะ goal ในข้อ 1 กว้างเกินไป (เช่น "ช่วยงานลูกค้าให้ดีขึ้น") ลองย่อ use case ให้แคบลงเหลือ 1 task ที่จบได้จริงใน 1 ครั้ง เช่นแทนที่จะเป็น "จัดการ support ticket ทั้งหมด" ให้แคบเป็น "แก้ ticket เดียวที่ระบุ ID มา แล้วหยุดเมื่อ ticket ถูก mark เป็น resolved" ยิ่ง scope แคบ ยิ่งเขียน stopping condition ที่วัดผลได้ง่าย

สรุป & ต่อยอด

คุณเพิ่งฝึกคิดแบบ "agent designer" — แตก use case จริงออกเป็น goal, tools, loop, stopping condition และจุดที่ต้องมี human approval ก่อนลงมือ ทักษะนี้เป็นพื้นฐานที่ใช้ทุก module ต่อจากนี้ เมื่อเริ่มใช้ Claude Code และ Hermes จริงใน module ถัดไป คุณจะเอา design นี้ไปเทียบกับสิ่งที่เครื่องมือจริงทำได้

ลองต่อยอด:

  • ลองออกแบบ agent design อีก 1 use case จากทีมอื่น (เช่น ถ้าคุณเป็น engineer ลองออกแบบของฝั่ง presale ดูบ้าง)
  • ลอง identify ว่า tools ที่คุณระบุใน section 2 มีตัวไหนที่ "มีอยู่แล้ว" ใน Claude Code หรือ Hermes MCP tools บ้าง (จะเรียนใน Module 02-03)
  • เก็บไฟล์ my-agent-design.md นี้ไว้ — ใน Module 07 (Multi-Agent Orchestration) จะย้อนกลับมาใช้ design นี้ต่อยอดเป็น subagent จริง
