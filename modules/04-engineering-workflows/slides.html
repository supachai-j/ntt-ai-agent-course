Engineering Workflows
with Claude Code

Feature dev loop · PR review · Refactor · TDD · Session control · Cost discipline

Agenda

  • Feature development loop มาตรฐาน (branch → prompt → review → iterate → commit → PR)
  • PR review pattern ด้วย git diff | claude -p
  • Interactive refactor workflow ผ่าน tmux + PTY
  • Test-Driven Development กับ agent (RED-GREEN-REFACTOR)
  • Session continuation: -c, -r, --fork-session
  • Cost/performance discipline: --max-turns, --max-budget-usd, --effort

Feature Development Loop

Loop มาตรฐาน

  1. 1สร้าง branch ใหม่
  2. 2prompt Claude Code ให้ implement
  3. 3review diff ที่เกิดขึ้น
  4. 4iterate — ให้ feedback รอบต่อไป
  5. 5commit เมื่อพอใจ
  6. 6เปิด PR

หลักการสำคัญ

Agent เขียนโค้ดได้เร็ว แต่ engineer ยังต้อง review ทุก diff ก่อน commit เสมอ — ไม่ trust output แบบ blind. Loop นี้เหมือน pair-programming ที่คุณเป็นคนตัดสินใจสุดท้าย

Feature Loop: ตัวอย่างจริง

สร้าง branch แล้วสั่ง Claude Code ใน print mode ให้ทำงานที่ scope ชัดเจน จากนั้น review diff, iterate ถ้าจำเป็น แล้วค่อย commit:

git checkout -b feature/api-error-handling

claude -p 'Add error handling to all API calls in src/' \
  --allowedTools 'Read,Edit' \
  --max-turns 10

# ตรวจ diff ทุกครั้งก่อน commit
git diff

# ถ้าไม่โอเค ให้ prompt ต่อเพื่อ iterate (ใช้ -c เพื่อสาน context เดิม)
claude -p 'The retry logic in fetchUser() is missing a max-retry cap, fix it' \
  --continue --max-turns 5

# พอใจแล้วค่อย commit + เปิด PR
git add -p
git commit -m "Add error handling to API calls"
git push -u origin feature/api-error-handling
gh pr create --fill

PR Review Pattern

ใช้ Claude Code เป็น first-pass reviewer ก่อนส่งให้ human review — pipe diff เข้าไปตรง ๆ ด้วย print mode

git diff main...feature | claude -p \
  'Review this diff for bugs, security issues, style' \
  --max-turns 2

ทำไมต้องตั้ง --max-turns ต่ำ ๆ (แต่ไม่ใช่ 1)

Review งานนี้เป็น text-in / text-out เป็นหลัก ไม่ต้องแก้ไฟล์ จึงตั้ง turn limit ต่ำเพื่อควบคุมต้นทุน — แต่จากการทดสอบจริง --max-turns 1 มักไม่พอ เพราะ Claude มักขอใช้ tool หนึ่งครั้งก่อนตอบ (เช่น ตรวจสอบ context) ทำให้ error error_max_turns ตั้งแต่ turn แรก — ใช้ --max-turns 2 ขึ้นไปจึงจะสำเร็จจริง

PR Review: ใช้ใน CI จริง

#!/usr/bin/env bash
set -euo pipefail

git fetch origin main
git diff origin/main...HEAD | claude -p \
  'Review this diff for bugs, security issues, style. \
   Output a bullet list, flag any CRITICAL issue at the top.' \
  --output-format json \
  --max-turns 3 > review.json

python -c "import json,sys; r=json.load(open('review.json')); print(r['result'])"

--output-format json ให้ผลลัพธ์ที่ parse ได้ เหมาะกับ pipeline ที่ต้อง post comment กลับเข้า PR อัตโนมัติ

Interactive Refactor Workflow: tmux + PTY

Refactor ใหญ่ ๆ มักต้องมี human-in-the-loop หลายรอบ — print mode ไม่พอเพราะเราอยากเห็น progress และ steer ระหว่างทาง ต้องรัน Claude Code แบบ interactive ข้างใน tmux session แล้วควบคุมด้วย send-keys, ตรวจ progress ด้วย capture-pane

# เปิด session
tmux new-session -d -s refactor-auth -x 140 -y 40

# เข้าโปรเจกต์แล้วสั่ง claude
tmux send-keys -t refactor-auth \
  'cd ~/project && claude' Enter

# รอ startup + trust dialog แล้ว Enter รับ default
sleep 4 && tmux send-keys -t refactor-auth Enter

# ส่ง task แรก
sleep 2 && tmux send-keys -t refactor-auth \
  'Refactor the auth module to use JWT tokens' Enter

# ตรวจความคืบหน้า
sleep 15 && tmux capture-pane -t refactor-auth -p -S -50

tmux Pattern: iterate แล้วปิด session

# เห็น diff ที่ยังไม่ถูกใจ ส่ง feedback รอบสอง
tmux send-keys -t refactor-auth \
  'Also add unit tests for the new JWT verify function' Enter

sleep 20 && tmux capture-pane -t refactor-auth -p -S -60

# จบงาน — ออกจาก Claude แล้วเก็บ session
tmux send-keys -t refactor-auth '/exit' Enter
tmux kill-session -t refactor-auth
ข้อควรระวัง: อย่าลืม kill session เมื่อจบงาน — session ที่ค้างไว้ กิน resource และอาจสร้างความสับสนเมื่อรัน task ใหม่ในไดเรกทอรีเดิม

Test-Driven Development กับ Agent

วินัยสำคัญที่สุดของ engineering workflow กับ agent: ห้ามให้ agent เขียนโค้ด production โดยไม่มี test คุมทิศทาง

RED

Engineer เขียน failing test เองก่อน — กำหนด contract ที่ชัดเจน

GREEN

ให้ Claude Code implement จนกว่า test จะผ่าน ไม่มากไม่น้อยกว่านั้น

REFACTOR

เมื่อ test เขียวแล้ว ค่อยให้ agent (หรือ human) ปรับโครงสร้างโค้ดให้สะอาดขึ้น โดย test ต้องเขียวตลอดขั้นตอนนี้

TDD Loop: ตัวอย่างคำสั่ง

# RED: engineer เขียน failing test เอง (ไม่ให้ agent เขียน)
pytest tests/test_discount.py
# FAILED — apply_discount() not implemented

# GREEN: ให้ Claude Code implement จนผ่าน
claude -p 'Implement apply_discount() in src/pricing.py so that \
  tests/test_discount.py passes. Do not modify the test file.' \
  --allowedTools 'Read,Edit,Bash(pytest*)' \
  --max-turns 8

# verify
pytest tests/test_discount.py -q
กฎเหล็ก: ห้ามให้ --allowedTools รวม permission แก้ไฟล์ test ในรอบ GREEN — ถ้า agent แก้ test ให้ผ่านง่าย ๆ แทนที่จะแก้โค้ด นั่นคือ false green

Session Continuation

งานยาวข้ามหลาย session ต้องใช้ flag เหล่านี้แทนการเริ่ม context ใหม่ทุกครั้ง

Flagใช้เมื่อไหร่
-c, --continueสาน conversation ล่าสุดในไดเรกทอรีปัจจุบัน
-r, --resume <id>resume session เฉพาะเจาะจงด้วย session ID
--fork-sessionresume แต่แตก session ID ใหม่ (เก็บ history เดิมไว้)
# เริ่มงาน เก็บ session_id จาก JSON output
claude -p 'Start refactoring the database layer' \
  --output-format json --max-turns 10 > session1.json

SID=$(python -c "import json;print(json.load(open('session1.json'))['session_id'])")

# มาต่อวันถัดไปในไดเรกทอรีเดียวกัน
claude -p 'Continue and add connection pooling' \
  --continue --max-turns 5

# หรือ resume แบบเจาะจง id / fork เพื่อลองแนวทางอื่นโดยไม่ทับของเดิม
claude -p 'Continue' --resume "$SID" --max-turns 5
claude -p 'Try a different pooling strategy' \
  --resume "$SID" --fork-session --max-turns 10

Cost / Performance Discipline

Automation จริงต้อง set flag เหล่านี้เสมอ — อย่าปล่อย default

Flagทำไมต้อง set
--max-turnsกัน agentic loop ที่ไม่มีจุดจบ — งาน automation ต้องมี upper bound
--max-budget-usdcap ค่าใช้จ่าย API ต่อ run โดยตรง
--effort low/highงานง่ายใช้ low ลด latency/cost, งานซับซ้อนใช้ high เพื่อความแม่นยำ
--allowedToolsจำกัด blast radius — งาน review ไม่ควรมีสิทธิ์ Write/Bash
# งาน review เบา ๆ: effort ต่ำ, turn จำกัด, ไม่มีสิทธิ์แก้ไฟล์
git diff | claude -p 'Quick style review' \
  --effort low --max-turns 3 --allowedTools ''

# งาน implement ที่ซับซ้อน: effort สูง, budget cap ชัดเจน
claude -p 'Implement the rate limiter per docs/rate-limit-spec.md' \
  --effort high --max-turns 15 --max-budget-usd 2.00 \
  --allowedTools 'Read,Edit,Write,Bash(pytest*)'
อย่าลืม: ไม่ set flag พวกนี้ = agent มีสิทธิ์เต็ม + ไม่มี turn limit = เสี่ยง runaway cost และแก้ไฟล์เกิน scope ที่ตั้งใจ

สรุป

  • Feature loop: branch → prompt → review diff → iterate → commit → PR — review เสมอ ไม่ trust blind
  • PR review: pipe diff เข้า claude -p เป็น first-pass ก่อน human review
  • Refactor ใหญ่ที่ต้อง human-in-the-loop → interactive mode ผ่าน tmux
  • TDD: agent implement ได้เฉพาะเมื่อมี failing test คุมทิศทางเสมอ
  • งานยาวข้าม session ใช้ -c/-r/--fork-session
  • Automation จริงต้อง set --max-turns, --max-budget-usd, --effort, --allowedTools เสมอ
