Engineering Workflows with Claude Code

วิธี engineer มืออาชีพใช้ Claude Code เป็น pair-programmer จริง — ตั้งแต่ feature loop ระดับวัน, framework AI-DLC ระดับ sprint, ไปจนถึง PR review, refactor แบบ interactive, TDD, session control และ cost discipline

TL;DR: ทุก workflow ในโมดูลนี้ยึดหลักเดียวกัน — agent เขียนโค้ดเร็ว แต่ human ต้อง verify ทุกครั้งด้วยของจริง (diff review, test run, build) ไม่ใช่เชื่อรายงานของ agent เฉยๆ Feature loop จัดการงานระดับวัน, AI-DLC จัดการงานระดับ sprint, ส่วน TDD/session flags/cost flags คือวินัยเสริมที่ทำให้ automation ปลอดภัยและควบคุมต้นทุนได้

1. Feature Development Loop

Loop มาตรฐานสำหรับงานพัฒนาฟีเจอร์ระดับวันกับ Claude Code มี 6 ขั้นตอน:

  1. สร้าง branch ใหม่ — แยกงานออกจาก main เสมอ
  2. prompt Claude Code ให้ implement — บอก scope ให้ชัดเจน
  3. review diff ที่เกิดขึ้น — อ่านทุกบรรทัดที่เปลี่ยน
  4. iterate — ให้ feedback รอบต่อไปถ้ายังไม่โอเค
  5. commit เมื่อพอใจ
  6. เปิด PR

หลักการสำคัญ: Agent เขียนโค้ดได้เร็ว แต่ engineer ยังต้อง review ทุก diff ก่อน commit เสมอ — ไม่ trust output แบบ blind. Loop นี้เหมือน pair-programming ที่คุณเป็นคนตัดสินใจสุดท้าย

ตัวอย่างจริง

สร้าง branch แล้วสั่ง Claude Code ใน print mode ให้ทำงานที่ scope ชัดเจน จากนั้น review diff, iterate ถ้าจำเป็น แล้วค่อย commit:

git checkout -b feature/api-error-handling

claude -p 'Add error handling to all API calls in src/' \
  --allowedTools 'Read,Edit' \
  --max-turns 10

# ตรวจ diff ทุกครั้งก่อน commit
git diff

# ถ้าไม่โอเค ให้ prompt ต่อเพื่อ iterate (ใช้ -c เพื่อสาน context เดิม)
claude -p 'The retry logic in fetchUser() is missing a max-retry cap, fix it' \
  --continue --max-turns 5

# พอใจแล้วค่อย commit + เปิด PR
git add -p
git commit -m "Add error handling to API calls"
git push -u origin feature/api-error-handling
gh pr create --fill

2. Framework ระดับ Sprint: AI-DLC

AI-DLC (AI Development Life Cycle) เป็น framework จาก AWS AI-DLC ที่ครอบ feature loop ก่อนหน้านี้ทั้งหมดไว้ในระดับ sprint/module มี 4 phase: Ideation → Inception → Construction → Operation — และ 4 phase นี้ วนซ้ำทุก sprint/module ไม่ใช่วนครั้งเดียวตลอดทั้งโปรเจกต์

💡 ทำไมต้องมี framework นี้: Feature loop (branch→prompt→review→commit) ตอบคำถาม "ทำอย่างไร" แต่ AI-DLC ตอบคำถาม "ควรเริ่ม/หยุด/ส่งต่อเมื่อไหร่" ระดับ sprint — ป้องกัน scope กระจาย และให้จุด stage-gate ชัดเจนก่อนแตะโค้ดจริง

4 Phase โดยละเอียด

Phaseสิ่งที่ทำใครทำ
Ideationแปลง scope เป็น user story ที่ตรวจสอบได้ ยืนยันร่วมกับผู้ใช้/PO ก่อนเริ่มDev + PO/ผู้ใช้
Inceptionออกแบบ implementation plan ระดับไฟล์ ตั้ง acceptance criteria — เป็น stage-gate ก่อนแตะโค้ดจริงDev (planning-tier model)
ConstructionAgent implement ตาม scope ที่แบ่งไว้ (ไม่ให้ agent สองตัวแตะไฟล์เดียวกัน) มี review ระหว่างทางDev + agent(s)
Operationรัน automated test จริงก่อนเชื่อรายงานของ agent, merge, ส่งต่อ QA + เอกสารDev → QA + Docs
⚠️ หลักการยึดทุก sprint: ไม่เชื่อ agent report เฉยๆ — ต้อง verify ด้วย build/test จริงก่อนจะนับว่า Operation phase เสร็จ (พบจริงจากการใช้งาน)

ตัวอย่างจริงจาก Sprint

ตัวอย่าง sprint ทั่วไป — เพิ่ม feature "override ค่าบางอย่างตอนอนุมัติคำขอ" + "ทุกหน้า admin ต้องมี auth":

  • Ideation — user story: "admin ต้อง override ค่าที่จะให้จริงตอนอนุมัติได้ ไม่ใช่ตามที่ขอมาเป๊ะๆ" + "ทุกหน้า admin ต้องมี auth ก่อนเข้าถึง"
  • Inception — วางแผนแก้ validate-then-mutate flow, ออกแบบ shared admin shell/proxy ให้ใช้ซ้ำได้ทุกหน้าในอนาคต (กัน sprint ถัดไปต้อง refactor ซ้ำ)
  • Construction — แยกงาน backend (auth middleware) กับ frontend (shared shell) เป็นงานคู่ขนานที่ ไม่แตะไฟล์ร่วมกัน
  • Operation — รัน regression test เดิม, ทีม QA เช็ค edge case จริงก่อนปิด sprint

Inception เป็น Stage-Gate จริง — กรณีศึกษา

Sprint ถัดมา: เพิ่ม entity ใหม่ที่ผูกกับของเดิม — Inception เลือกแยก entity ใหม่ ออกจากของเดิม (ไม่เพิ่ม field ใหม่ลงตรงๆ) เพื่อไม่ให้ reader/logic เดิมพัง

💡 บทเรียนจากของจริง: "list-registration trap" — ทุกครั้งที่สร้าง entity ใหม่ ต้องเพิ่มเข้า order/index list ที่มีอยู่แล้วเสมอ ไม่งั้น entity จะ "มีอยู่จริงในระบบแต่ไม่โผล่ที่ไหนเลย" ใน UI. แก้ด้วยการเตือน agent ล่วงหน้า ในคำสั่งงานตั้งแต่ prompt แรก — เป็นความรู้เฉพาะ codebase ที่ agent เดาเองไม่ได้

Construction: แบ่งงาน Agent คู่ขนานให้ปลอดภัย

ตัวอย่างจริง sprint "Security Hardening" — ปิดช่องโหว่ที่พบจาก code review หลายรอบ ด้วย 5 agent คู่ขนาน แบ่งตาม layer:

Layer 1: backend auth        → Agent A
Layer 2: backend data store   → Agent B
Layer 3: authorization logic  → Agent C
Layer 4: frontend write-flow  → Agent D
Layer 5: frontend generator   → Agent E
⚠️ Inception ต้องจัดกลุ่ม finding ตามไฟล์ก่อนแบ่งงาน — พลาดจุดนี้แล้ว 2 agent จะแก้ไฟล์เดียวกันพร้อมกันและ merge conflict กันเอง แต่ละ agent ต้อง verify ด้วย test จริงก่อนส่งงานกลับ ก่อน Operation phase verify ซ้ำอีกรอบรวมทุก layer ด้วย full test suite

AI Agent Coding Discipline (ใน AGENTS.md)

วินัย 4 ข้อที่ควรใส่ใน AGENTS.md/CLAUDE.md ของทุกโปรเจกต์ — ใช้ เสริม ไม่ใช่แทนที่ PR review/security review:

  1. Think Before Coding — state assumption ชัดเจนก่อนลงมือ ถ้า request ตีความได้หลายแบบ บอกก่อนแล้วเลือก แทนที่จะเดาเงียบๆ หยุดถามเมื่อไม่แน่ใจจริงๆ
  2. Simplicity First (มี exception ได้) — เขียนโค้ดขั้นต่ำที่แก้ปัญหาที่ระบุ แต่ยอมรับ indirection ที่ดูเกินจำเป็นได้ ถ้ามีเหตุผลบันทึกไว้ชัดเจน (เช่น กัน breaking change ในอนาคต)
  3. Surgical Changes — แตะเฉพาะสิ่งที่ task ต้องการ ห้าม refactor/clean-up โค้ดข้างเคียงที่ไม่เกี่ยวเป็นผลพลอยได้ — เข้ากับหลักการแบ่ง agent คู่ขนานแบบไม่แตะไฟล์ร่วมกัน
  4. Goal-Driven Execution — แปลง request คลุมเครือเป็น goal ที่ verify ได้ (failing test/repro/acceptance criteria) ก่อนเขียนโค้ด แล้ว verify จริงตอนจบ — ไม่เชื่อ รายงานความสำเร็จเฉยๆ

3. PR Review Pattern

ใช้ Claude Code เป็น first-pass reviewer ก่อนส่งให้ human review — pipe diff เข้าไปตรงๆ ด้วย print mode:

git diff main...feature | claude -p \
  'Review this diff for bugs, security issues, style' \
  --max-turns 2
💡 ทำไมต้องตั้ง --max-turns ต่ำๆ (แต่ไม่ใช่ 1): Review งานนี้เป็น text-in / text-out เป็นหลัก ไม่ต้องแก้ไฟล์ จึงตั้ง turn limit ต่ำเพื่อควบคุม ต้นทุน — แต่จากการทดสอบจริง --max-turns 1 มักไม่พอ เพราะ Claude มักขอใช้ tool หนึ่งครั้งก่อนตอบ (เช่น ตรวจสอบ context) ทำให้ error error_max_turns ตั้งแต่ turn แรก — ใช้ --max-turns 2 ขึ้นไปจึงจะสำเร็จจริง

ใช้ใน CI จริง

#!/usr/bin/env bash
set -euo pipefail

git fetch origin main
git diff origin/main...HEAD | claude -p \
  'Review this diff for bugs, security issues, style. \
   Output a bullet list, flag any CRITICAL issue at the top.' \
  --output-format json \
  --max-turns 3 > review.json

python -c "import json,sys; r=json.load(open('review.json')); print(r['result'])"

--output-format json ให้ผลลัพธ์ที่ parse ได้ เหมาะกับ pipeline ที่ต้อง post comment กลับเข้า PR อัตโนมัติ

4. Interactive Refactor Workflow: tmux + PTY

Refactor ใหญ่ๆ มักต้องมี human-in-the-loop หลายรอบ — print mode ไม่พอเพราะเราอยากเห็น progress และ steer ระหว่างทาง ต้องรัน Claude Code แบบ interactive ข้างใน tmux session แล้วควบคุมด้วย send-keys, ตรวจ progress ด้วย capture-pane:

# เปิด session
tmux new-session -d -s refactor-auth -x 140 -y 40

# เข้าโปรเจกต์แล้วสั่ง claude
tmux send-keys -t refactor-auth \
  'cd ~/project && claude' Enter

# รอ startup + trust dialog แล้ว Enter รับ default
sleep 4 && tmux send-keys -t refactor-auth Enter

# ส่ง task แรก
sleep 2 && tmux send-keys -t refactor-auth \
  'Refactor the auth module to use JWT tokens' Enter

# ตรวจความคืบหน้า
sleep 15 && tmux capture-pane -t refactor-auth -p -S -50

Pattern: iterate แล้วปิด session

# เห็น diff ที่ยังไม่ถูกใจ ส่ง feedback รอบสอง
tmux send-keys -t refactor-auth \
  'Also add unit tests for the new JWT verify function' Enter

sleep 20 && tmux capture-pane -t refactor-auth -p -S -60

# จบงาน — ออกจาก Claude แล้วเก็บ session
tmux send-keys -t refactor-auth '/exit' Enter
tmux kill-session -t refactor-auth
⚠️ ข้อควรระวัง: อย่าลืม kill session เมื่อจบงาน — session ที่ค้างไว้กิน resource และอาจสร้างความสับสนเมื่อรัน task ใหม่ในไดเรกทอรีเดิม

5. Test-Driven Development กับ Agent

วินัยสำคัญที่สุดของ engineering workflow กับ agent: ห้ามให้ agent เขียนโค้ด production โดยไม่มี test คุมทิศทาง — ใช้รูปแบบ RED-GREEN-REFACTOR:

  • RED — Engineer เขียน failing test เองก่อน กำหนด contract ที่ชัดเจน
  • GREEN — ให้ Claude Code implement จนกว่า test จะผ่าน ไม่มากไม่น้อยกว่านั้น
  • REFACTOR — เมื่อ test เขียวแล้ว ค่อยให้ agent (หรือ human) ปรับโครงสร้าง โค้ดให้สะอาดขึ้น โดย test ต้องเขียวตลอดขั้นตอนนี้

TDD Loop: ตัวอย่างคำสั่ง

# RED: engineer เขียน failing test เอง (ไม่ให้ agent เขียน)
pytest tests/test_discount.py
# FAILED — apply_discount() not implemented

# GREEN: ให้ Claude Code implement จนผ่าน
claude -p 'Implement apply_discount() in src/pricing.py so that \
  tests/test_discount.py passes. Do not modify the test file.' \
  --allowedTools 'Read,Edit,Bash(pytest*)' \
  --max-turns 8

# verify
pytest tests/test_discount.py -q
⚠️ กฎเหล็ก: ห้ามให้ --allowedTools รวม permission แก้ไฟล์ test ในรอบ GREEN — ถ้า agent แก้ test ให้ผ่านง่ายๆ แทนที่จะแก้โค้ด นั่นคือ false green ซึ่งเป็นอันตรายมาก เพราะ test ที่ผ่านไม่ได้แปลว่าโค้ดถูก แค่แปลว่า test ถูกดัดแปลงให้ผ่านง่ายๆ

6. Session Continuation

งานยาวข้ามหลาย session ต้องใช้ flag เหล่านี้แทนการเริ่ม context ใหม่ทุกครั้ง:

Flagใช้เมื่อไหร่
-c, --continueสาน conversation ล่าสุดในไดเรกทอรีปัจจุบัน
-r, --resume <id>resume session เฉพาะเจาะจงด้วย session ID
--fork-sessionresume แต่แตก session ID ใหม่ (เก็บ history เดิมไว้)
# เริ่มงาน เก็บ session_id จาก JSON output
claude -p 'Start refactoring the database layer' \
  --output-format json --max-turns 10 > session1.json

SID=$(python -c "import json;print(json.load(open('session1.json'))['session_id'])")

# มาต่อวันถัดไปในไดเรกทอรีเดียวกัน
claude -p 'Continue and add connection pooling' \
  --continue --max-turns 5

# หรือ resume แบบเจาะจง id / fork เพื่อลองแนวทางอื่นโดยไม่ทับของเดิม
claude -p 'Continue' --resume "$SID" --max-turns 5
claude -p 'Try a different pooling strategy' \
  --resume "$SID" --fork-session --max-turns 10

7. Cost / Performance Discipline

Automation จริงต้อง set flag เหล่านี้เสมอ — อย่าปล่อย default:

Flagทำไมต้อง set
--max-turnsกัน agentic loop ที่ไม่มีจุดจบ — งาน automation ต้องมี upper bound
--max-budget-usdcap ค่าใช้จ่าย API ต่อ run โดยตรง
--effort low/highงานง่ายใช้ low ลด latency/cost, งานซับซ้อนใช้ high เพื่อความแม่นยำ
--allowedToolsจำกัด blast radius — งาน review ไม่ควรมีสิทธิ์ Write/Bash
# งาน review เบา ๆ: effort ต่ำ, turn จำกัด, ไม่มีสิทธิ์แก้ไฟล์
git diff | claude -p 'Quick style review' \
  --effort low --max-turns 3 --allowedTools ''

# งาน implement ที่ซับซ้อน: effort สูง, budget cap ชัดเจน
claude -p 'Implement the rate limiter per docs/rate-limit-spec.md' \
  --effort high --max-turns 15 --max-budget-usd 2.00 \
  --allowedTools 'Read,Edit,Write,Bash(pytest*)'
⚠️ อย่าลืม: ไม่ set flag พวกนี้ = agent มีสิทธิ์เต็ม + ไม่มี turn limit = เสี่ยง runaway cost และแก้ไฟล์เกิน scope ที่ตั้งใจ

สรุปโมดูล

  • Feature loop: branch → prompt → review diff → iterate → commit → PR — review เสมอ ไม่ trust blind
  • AI-DLC ครอบ feature loop ไว้ระดับ sprint: Ideation → Inception → Construction → Operation, ไม่เชื่อ agent report ต้อง verify ด้วย test จริง
  • PR review: pipe diff เข้า claude -p เป็น first-pass ก่อน human review
  • Refactor ใหญ่ที่ต้อง human-in-the-loop → interactive mode ผ่าน tmux
  • TDD: agent implement ได้เฉพาะเมื่อมี failing test คุมทิศทางเสมอ
  • งานยาวข้าม session ใช้ -c/-r/--fork-session
  • Automation จริงต้อง set --max-turns, --max-budget-usd, --effort, --allowedTools เสมอ
